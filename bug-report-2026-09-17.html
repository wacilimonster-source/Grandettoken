严重 · 014SAPI 业务失败被判定为「取数成功」

app/core/src/providers.rs:116–117(同源问题见 providers.js:81)
复测:已修复
改为 code_ok && active_ok(两个字段各自 unwrap_or(true) 后取与), 逻辑与报告建议一致。用 rustc 单独编译复刻表达式跑真值表 7/7 PASS, 其中 code:false + is_active 缺失已由 true 变为 false; 新增测试 four_s_api_business_failure_is_invalid 覆盖 code:false 与 is_active:false 两条路径。实测 cargo test 27 个测试全绿(26 → 27)。
现象
4SAPI 返回 {"code": false, "msg": "…"} 这类业务失败、但响应体里仍带着 data.total_granted / total_available 时,应用把它当成取数成功渲染 —— 不显示错误、不标注「上次快照」,直接把这组数字当成实时余额。
根因
有效性判定写成了「两个条件各自兜底为 true,再做或运算」,而 is_active 字段在 4SAPI 的正常响应里根本不存在,于是右边的 unwrap_or(true) 恒定给出 true,把左边正确的 false 吞掉。|| 与 unwrap_or(true) 组合在一起使判定失效。
// providers.rs:116 —— 现状
valid: body.get("code").and_then(|c| c.as_bool()).unwrap_or(true)
    || path(body, &["is_active"]).and_then(|c| c.as_bool()).unwrap_or(true),

实测真值表(用 rustc 单独编译该表达式复刻):

code      is_active   -> valid
Some(true)  Some(true)  -> true
Some(true)  None        -> true
Some(false) None        -> true   ← code:false 却判为有效
Some(false) Some(true)  -> true
Some(false) Some(false) -> false
None        None        -> true
为何漏网
现有测试 four_s_api_converts_points 只覆盖 code: true 的正常分支; four_s_api_falls_back_when_fields_missing 覆盖的是「缺 data 字段」的另一条分支。 code: false 这条路径没有任何测试。设计稿 providers.js 里的 code === true || is_active !== false 有同样的缺陷,说明是设计阶段就带进来的。
修复方向
把「字段缺失」与「字段为假」分开:code 存在时以它为准,不存在才回落到 is_active,两者都没有才默认通过。同时补一个 four_s_api_code_false_is_invalid 测试锁住行为。
修复后效果
  • 4SAPI 返回业务失败时,界面走「取数失败 + 显示上次成功快照 + 标注时间」的正确路径,而不是把过期数字当实时余额。
  • 与项目自己立的核心契约「取数失败绝不能降级成正常值」在 4SAPI 这条路径上真正对齐。

严重 · 02贴边吸附在紧凑条 / 胶囊形态下串味,竖条被挤没

app/src/styles.css:236–246(docked 规则)vs 250 / 255 / 293(形态规则)
复测:已修复
把 body.docked 那组规则整体移到样式表末尾,并补了注释说明「同优先级按源码顺序取后者」这个坑。 用真实 Chromium 对修复前后的 styles.css 做 A/B 渲染(8×64 视口,同一份 DOM):
· 修复前 form-compact docked → 竖条 0×64(被挤没)、list=flex、cctl=flex
· 修复前 form-pill docked → 竖条 8×50(被压矮)、pill-body=flex
· 修复后三种形态 → 竖条均 8×64,其余元素全部 display:none
原症状被完整复现并消除,不再是「坐标断言通过、视觉没核对」。
现象
在紧凑条或胶囊形态下把窗口拖到屏幕边缘吸附,窗口确实缩成 8×64,但被隐藏的表单内容又被显示了出来: chip 行 / 胶囊内容挤进 8px 宽的窗口,flex 收缩把 .dock-body(那条状态色竖条)挤成 0 宽 —— 竖条直接看不见;胶囊形态下还会把 body.form-pill 的深色底与 999px 圆角盖到 body.docked 的透明背景上,出现一块不该有的深色圆角块。只有从面板形态吸附才是正确的。
根因
CSS 层叠顺序错误。body.docked .xxx{display:none} 写在文件前部(236–246 行),而 body.form-compact .list / body.form-compact .cctl / body.form-pill .pill-body 写在后面,选择器优先级完全相同(都是 0-2-1), 同优先级下后出现的胜出 —— 于是「隐藏」被后面的「显示」覆盖。

用脚本解析 styles.css 并计算层叠胜出规则,实测输出:

body="form-panel docked"      .list      -> none    [body.docked .list  spec 0-2-1]  正确
body="form-compact docked"    .list      -> flex    [body.form-compact .list  spec 0-2-1]  应为 none
body="form-compact docked"    .cctl      -> flex    [body.form-compact .cctl  spec 0-2-1]  应为 none
body="form-pill docked"       .pill-body -> flex    [body.form-pill .pill-body  spec 0-2-1]  应为 none
为何漏网
贴边功能的验证是对窗口坐标和拖动区属性做断言(窗口是否贴到边缘、data-tauri-drag-region 是否正确), 没有对「吸附后 8×64 窗口里到底渲染了什么」做可见性断言或截图核对,所以这层串味没被捕获。
修复方向
把 body.docked 那一组规则移到所有形态规则之后;或给 docked 选择器多加一个元素权重 (如 html body.docked .list)使其稳定胜出。不要用 :not(.docked) 去改形态规则 —— 那会把优先级抬到 0-3-1,反而压过 docked。
修复后效果
  • 三种形态吸附的结果完全一致:一条 8×64 的纯色竖条,窗口里不残留任何 chip / 胶囊 / 面板内容。
  • 竖条宽度不再被 flex 挤压,状态色始终可见、可点、可拖离边缘解除吸附。
  • 「三种形态都能拖到边缘吸附」这句承诺在视觉层真正成立,而不只是在坐标层成立。

严重 · 03取数失败清空本地推算的消耗,汇总条静默少算

app/core/src/fetch.rs:272(组视图)与 402(失败降级) · app/src/app.js:140–165(汇总)
现象
某个渠道一次网络抖动取数失败后:该行的「今日 / 本周 / 本月消耗」三格全部变成 ——;底部汇总条的金额无声变少,但提示文字仍写着「4 个渠道」,用户看不出少算了谁。
根因
两处叠加。①fetch_all 在失败降级时把缓存的 prev.valid 置为 false, 而 build_view 计算日/周/月消耗的前置条件是 result.valid && kind == Amount —— 于是三个值被一并置 None。但这三个数字来自本地 SQLite 快照,与本次网络请求毫无关系, 不该被网络失败连坐。②renderSummary 求和时把 null 过滤掉,但 「N 个渠道」里的 N 用的是未过滤的 am.length,导致分子分母口径不一致。
// fetch.rs:272 —— 消耗推算被网络状态连坐
let (day, week, month) = if result.valid && result.kind == Kind::Amount { … } else { (None, None, None) };

// app.js:142–147 —— 过滤了 null,但计数没跟着过滤
const am = CHANNELS.filter(c => c.kind === "amount" && c.hasKey && c.remaining !== null);
const vals = am.map(c => c[f]).filter(v => v !== null && v !== undefined);   // 少算的那个在这里被丢掉
const note = v === null ? "数据不足" : est ? "推算" : `${am.length} 个渠道`;  // 仍按全部渠道报数
修复方向
消耗推算只以 kind == Kind::Amount 为条件,去掉 result.valid; 汇总的「N 个渠道」改为按实际参与求和的渠道数计,并在有渠道被跳过时显式标注。
修复后效果
  • 一次网络抖动不再让「今日 / 本周 / 本月消耗」整片变成「——」;本地流水推算的数据继续可用。
  • 汇总金额与「N 个渠道」口径一致,不会出现「说 4 个渠道、只加了 3 个的钱」这种静默误差。
  • 渠道是否失联仍由行内的状态点 / 「上次快照」标注表达,信息不丢、也不误导。

中等 · 04胶囊数值与面板 / 托盘不一致(OpenCode Go)

app/src/app.js:497–502(胶囊)对照 183 / 43–52(面板与配色)
复测:已修复
renderPillFace 改用 remainRatio(c)(与面板、紧凑条、贴边竖条、状态色同源)。 Node 复算(构造「本月窗 96% / 最紧窗 9%」的数据):
· 修复前:胶囊 9.0% vs 面板 96.0% —— 数字与颜色互相矛盾
· 修复后:面板 / 紧凑条 / 胶囊 / 托盘四处均 96.0%
顺带把贴边竖条染色与面板大数字统一到同一口径。
现象
OpenCode Go 的三个限流窗口松紧不同时,同一个时刻面板显示「本月 80.0%」而胶囊显示「OC 10.0%」, 而且胶囊的数字和它自己的状态点颜色互相矛盾(数字看着快耗尽,点却是绿色)。
根因
口径在改版时只改了一半。面板 / 紧凑条 / 状态色 / 竖条统一走 mainWindow()(固定取「本月」窗), 而胶囊仍直接用 c.remaining —— Rust 侧的 remaining 是最紧窗口的剩余 (providers.rs:195–205)。于是同一份数据在两种口径下被显示成两个数。
// 实测:5 小时窗剩 10% / 本周剩 90% / 本月剩 80%
面板/紧凑条大数字: 80.0%      ← mainWindow() = 本月
胶囊大数字      : 10.0%      ← c.remaining = 最紧窗口
胶囊状态点颜色按: 80% -> ok      ← 数字说危险,颜色说健康
修复方向
胶囊改用 remainRatio(c)(与面板、托盘、竖条同源);百分比保留一位小数。 顺带让「自动:最紧张的一个」的挑选口径与显示口径保持一致。
修复后效果
  • 面板、紧凑条、胶囊、贴边竖条四种形态显示同一个数,来回切换不再「数字跳变」。
  • 胶囊的数字与状态点颜色永远自洽,不会出现「绿点 + 10%」这种自相矛盾的读数。

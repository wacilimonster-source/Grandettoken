WorkBuddy AI(国际版):积分展示 + 当日获取记录

产品设计 · 2026-10-23 · 依据来自本仓库既有取证(workbuddy.rs / weblogin.rs / 2026-10-13 签到调研)+ 待补的真机探针

一句话:把国际版接成第 10 个内置渠道(id workbuddy-ai),积分型,凭据读本机国际版桌面端, 展示剩余积分与当日是否已获取积分。国内版与它是两套账号、两套域名、两个渠道条目,不合并。 “当日获取”按余额正增量记账(国际版没有签到活动),每条记录带 source,界面如实标注“平台确认 / 按余额推算”。

0. 先说结论(六条)

#结论依据
1国际版必须是独立渠道,不是现有 WorkBuddy 的第二个域名 —— 两套账号、两份凭据,官方不支持跨区迁移(与 Qoder / Qoder 国内版同构)既有裁决weblogin.rs:16 裁决 6A;凭据 domain 判区
2凭据走本机桌面端 auth 文件,不走网页登录 —— 国际版被明确排除在网页登录之外代码现状weblogin.rs 只认 workbuddy.cn / codebuddy.cn
3取数复用同一个计费接口,基址换成 www.workbuddy.ai(备用 www.codebuddy.ai);extract_workbuddy 可直接复用半实workbuddy.rs:1482 已写好区域路由,响应结构待真机确认
4国际版没有签到活动:daily-checkin 回 10001 活动未开启,与国区“今天已签到”同码异义事实2026-10-13 调研;解析已按区域分支
5因此“当日获取”只能先用余额正增量判定,并标注“推算”;平台若另有发放接口,后续只换 source,不动表结构与界面设计取舍见 §3 D2
6记录落新表 credit_grants(不是 checkin_log):签到表记的是“尝试”,这里记的是“到账事件”,两者的重试/退避语义完全不同设计判断见 §6

2. 已经有什么 / 缺什么

已经有的(不用重写)

  • workbuddy.rs 已能读国际版凭据:is_global() 按 domain 判区
  • bases_for() 已把国际版路由到 workbuddy.ai / codebuddy.ai
  • 续期基址已按区域分开(chat_base())
  • extract_workbuddy() 解析积分包、到期、切片,可直接复用(响应同栈,字段待真机确认)
  • Outcome 七态、退避、幂等、done_today 由后端算的纪律
  • 渠道卡“读本机登录”的 UI 路径(authSource === "app")现成

缺的(本次要补)

  • 区域过滤的令牌:现在 desktop_tokens() 把国区与国际混在一个列表里
  • 获取事件表 credit_grants + 迁移 v4
  • 增量判定:从快照算当日正增量,写事件(幂等)
  • 渠道定义:ProviderDef 一条 + CHECKINS 不加(国际版没签到)
  • 界面:积分获取区块 + 30 天记录
不补会出事:如果新渠道直接复用 desktop_tokens(),每轮会先拿国区令牌打 workbuddy.ai —— 必然 401,再换下一份。签到侧已有“401 才换下一份”的逻辑(lib.rs:3111),不会报错, 但每轮多一次失败请求,日志里天天出现 cred-switch,真正的凭据失效反而被噪音埋掉。 所以 区域过滤是前置条件,不是优化。

3. 三个决策

D1 · 渠道形态

选项做法代价结论
A 独立渠道新增 workbuddy-ai,与 workbuddy 并列列表多一行;配置多一套键推荐 —— 账号本来就独立,合并只会让“这 1,240 分是谁的”说不清
B 卡内切区域一张卡,顶部切 国内 / 国际凭据、状态、签到全要按区分支;一处判错就串账否 —— 复杂度换不来收益
C 只记获取不显示余额不接渠道,只做一个“今日是否获取”的指示用户仍要开网页看余额否 —— 与产品定位(一屏看清余额)相悖

D2 · “当日已获取积分”怎么判

选项数据来源准确性现在能做吗结论
A 平台发放/活动接口若 workbuddy.ai 有 credit-records / activity 类接口准,含“活跃”与“充值”的区分未知 —— 国际版无签到,其它接口未取证探针发现即升级,表结构预留 source=api
B 余额正增量取数快照:相邻两次 remaining 的正差累加近似:能确认“今天多过 N 分”,分不清活跃发放与充值能,今天就能上先上这个,界面标“推算”
C 手动打勾用户自己在客户端领完回来点一下准,但要人记得能不做默认路径;只在“读不到凭据”时给一个自救入口(暂不做)
为什么 B 不违反“不误报”:它不参与余额渲染,也不说“你领到了”,只说“今天余额比之前多过 +100”。 措辞上把“获取”与“活跃获取”分开:界面写“今日新增”,长解释放在「?」里写明“按余额正增量推算,含充值”。 等 A 路线拿到接口,同一行改成“平台确认”,用户不需要重新学。

D3 · 记录口径

  • 按自然日 00:00 跨日(本地时区)。国际版没有活动周期,不引入 day_roll_hour 的复杂度; 若以后 A 路线发现活动有刷新时刻,再按渠道加一个字段 —— 那时也只改后端。
  • “哪一天”由后端算,前端不拿 new Date() 再算一遍。这是 0.1.5x 那条纪律 (done_today 的注释写得很清楚:前端算必错)。
  • 保留 30 天。签到流水是 7 天(那是“有没有漏领”),获取记录看的是趋势,7 天太短。

6. 数据模型与改动点

新表(迁移 v4,幂等)

CREATE TABLE IF NOT EXISTS credit_grants (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  channel    TEXT    NOT NULL,   -- workbuddy-ai
  day        TEXT    NOT NULL,   -- 本地自然日 YYYY-MM-DD(后端算)
  ts         INTEGER NOT NULL,   -- 观测时刻(秒)
  amount     REAL    NOT NULL,   -- 正增量
  source     TEXT    NOT NULL,   -- api | delta | manual
  from_bal   REAL,               -- 观测前后余额(便于解释,不参与判定)
  to_bal     REAL,
  UNIQUE(channel, day, ts)       -- 同一秒只记一条,重放不重复
);

判定规则(纯函数,可挂测试)

// 每次成功取数后调用;prev = 上一次成功快照
fn observe_grant(channel, day, now, prev_bal, cur_bal) -> Option<Grant> {
    let d = cur_bal - prev_bal;
    if d <= GRANT_EPS { return None; }          // 0.5 分以下不算
    Some(Grant { amount: d, source: Delta, .. })
}
  • 只对 workbuddy-ai 生效(以后其它积分渠道可复用,但要单独开开关)。
  • 不跨天合并:昨日最后一次快照 → 今日第一次快照之间的增量,记在今日(用户看到的是“今天到账”)。
  • 取数失败不写事件,也不推进 prev —— 否则中间漏掉的那段增量会被吞。
  • 超过 30 天自动清理(与快照同一套清理节奏)。

两处文案必须特判,不能照抄 app 型渠道:
① 状态行 —— 现有 app 型渠道拼的是「已读取本机登录 · {authLabel}」,而 auth_label() 对 App 返回「本机 WorkBuddy AI」, 拼出来会是「已读取本机登录 · 本机 WorkBuddy AI」。这条渠道单独拼成「已读取国际版登录 · 自动续期」。
② 卡片里那句 L1 —— 现有 app 型渠道写「只读复用本机登录,不写回、不刷新」。 但这条链路会续期(refreshToken 到期前自动换 accessToken,成果存在我们自己的库里、不写回客户端文件), 写「不刷新」是错的。这条要写「只读复用,自动续期」。

7. 红线

  1. 不把推算说成确认。source=delta 必须显式标注,措辞用“今日新增”而不是“今日活跃获取”。
  2. 不把“无活动”说成“已领”。10001 在国际版是“活动未开启”,国区是“今天已签” —— 解析必须带区域,现有 parse_workbuddy_for_region 已经是这个形状,别绕开它。
  3. 不显示成 0。取数失败沿用上次快照 + 时间 + 真实错误,获取记录停更但不归零。
  4. 隐藏即停。隐藏渠道后不请求、不读凭据、不写事件(取数侧已有闸门,新链路要跟着走)。
  5. 区域错配不得报“凭据失效”。国区令牌打国际域名是 401,要静默换下一份,不能弹“登录已过期”。
  6. 记账幂等。同一时刻重复写不产生第二条;进程重启、补跑、时钟回拨都不重复计。

9. 已确认(2026-10-23)

#问题结论
1“活跃获取积分”在国际版里到底是什么形态?每天要对话一次才会有 +30 积分 —— 自动到账,没有可点的领取动作。所以走 D2-B(余额正增量),并把 25–35 认作活跃窗口(取数间隔里的消耗会把净增量压下来)
2“今日未获取”要不要做成提醒?不做。没有可执行动作的提醒等于骚扰
3记录保留 30 天够不够?够
落地后的口径(与代码一致): core::grants::ACTIVITY_GRANT = 30.0 / ACTIVITY_TOL = 5.0 —— 增量落在 25–35 之间算“活跃奖励”,≥0.5 的正增量一律记事件(含充值,但界面标“非活跃”)。 阈值集中在 grants.rs 一处,以后平台改额度(比如 +50)只改这个常量。

10. 没凭据自动隐藏（2026-10-23 追加）

上一条的遗留问题：没装国际版桌面端的人会看到一行「未检测到登录」—— 纯噪音。 裁决：没检测到凭据就自动隐藏，检测到再自动恢复。两条边界缺一不可：

边界为什么落点
只在从没取到过数时藏曾经正常取过数、这次瞬时读不到（客户端正在写文件、凭据管理器 RPC 卡一下）就藏起来，用户会以为配置丢了 —— 那种情况应该继续走「沿用旧快照 + 标注时间」fetch_all 的 creds.is_empty() 分支里缓存中没有该渠道那一支
用户点过眼睛就彻底让位没有这一条，「点了显示、下一轮又被系统藏回去」比没有自动隐藏更让人火大Config::user_touched_channels：点眼睛（任意方向）即记一笔
为什么名单里只有国际版：判据不是「有没有凭据」，而是「没凭据是否稳定等于没装」。 Trae / Codex / Qoder 的凭据会瞬时读不到，加进去会让配置时隐时现；国际版没有网页登录路径 （裁决 6A），没装桌面端就永远看不到数据 —— 这才符合"没装就等于不存在"。

界面区分两种"隐藏"：ChannelView.auto_hidden 让"系统藏的"和"用户藏的"说不同的话 —— 卡片状态写「未检测到登录 · 已自动隐藏(登录后自动出现)」，眼睛变成显示； 点它只记 userTouchedChannels、不写 hiddenChannels （写进去就变成用户主动隐藏，再也不会自动恢复）。

实现见 PROGRESS.md 同日条目。

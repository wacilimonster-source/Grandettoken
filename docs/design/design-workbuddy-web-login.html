二、恢复方案：在挂件里登录一次 WorkBuddy 网页账号

WorkBuddy 网页控制台（www.workbuddy.cn/profile/plans-usage）打的就是我们现在这个接口，鉴权头也是 Authorization: Bearer <token>。我从它的前端包里挖清楚了令牌怎么来的：

1
用户在挂件里点「登录 WorkBuddy 账号」→ 挂件开一个独立小窗，加载 https://www.workbuddy.cn/login?platform=usercenter&redirect_uri=…plans-usage（网页登录入口，微信扫码 / 手机号，跟你在浏览器里登录一样）。
2
登录成功后站点会带着令牌跳回控制台。我实测它的取法：?token=… 这个 URL 参数被读进 sessionStorage["growth-center-token"]，之后每个请求由拦截器加上 headers.Authorization = `Bearer ${token}`（来自 download.codebuddy.cn/web/usercenter/…/config-wXDbhNun.js）。
3
挂件在这个窗口上预先注入一段脚本（用 Tauri 的 initialization_script，源码 tauri-2.11.5/src/webview/webview_window.rs:945 已确认存在），钩住页面的 fetch 与 XMLHttpRequest.setRequestHeader，第一个 Bearer 令牌一出现就拿到。URL 参数、sessionStorage 两种取法作为备用判据。
4
脚本把令牌交给挂件：走一次哨兵跳转 https://tokenscope-capture.invalid/?t=<token>。挂件的导航监听（on_navigation，webview_window.rs:266）看到这个地址就拦下不发（域名是造不出来的 .invalid，令牌不会出网），解析出来存好。
5
令牌写入 Windows 凭据管理器（复用现成的 secrets 模块 + keyring 3），窗口自动关闭，卡片立刻开始出数。不进配置文件、不进数据库、不进日志——和其它渠道的密钥一个待遇。
6
以后每轮取数：优先用这份令牌；报 401/403 时提示「登录已过期，点这里重新登录一次」并一键重开窗口，而不是再让你去开客户端。

七、真机第一次跑就翻出的死锁（2026-10-08，v0.1.18）

症状：点「登录 WorkBuddy 账号」，窗口壳出来了，里面全白，而且此后整个挂件像死了 —— 连「刷新」都没反应。 第六节那句"还差你一次真机登录"验收的正是这里：静态检查和浏览器里的桩测都不可能发现它， 因为问题不在注入脚本、不在前端、也不在站点可达性，而在窗口是怎么被创建出来的。

环节结论
调用方式workbuddy_login 当时是同步命令；Tauri 的同步命令在主线程上就地执行，而它又是从 WebView2 的 WebMessageReceived（前端 invoke）里调起的。
卡在哪在 COM 回调里同步创建第二个 webview，CreateCoreWebView2Controller 的完成回调再也送不回主线程；wry 卡在 wait_with_pump 死等，主线程从此不处理任何消息。
为什么"全白"新 webview 的页面永远停在 about:blank：浏览器进程里已有它的目标，但连 CDP 手工 Page.navigate 都推不动。
为什么"整个挂件死了"主线程被占死，之后任何 invoke 都不再被处理 —— 用一条无关命令 get_channels 也超时即可证明，不是前端卡住。
取证依据窗口树：登录窗有 wry 的 WRY_WEBVIEW 容器，却没有 WebView2 的 Chrome_WidgetWin_1 / 渲染窗口（主窗口两样都有）。/json/list：invoke 后多出一个 about:blank 目标，40 秒不动，workbuddy.cn 目标始终不出现。
修法命令改成 async fn：async 命令跑在 async runtime 线程上，窗口创建变成投进事件循环的一条消息，上下文与"启动时按配置建主窗口"一致（那条路一直是通的）。lib.rs 里留了注释禁止改回同步。

修完在真机上重跑：登录页正常加载（微信 / 手机号 / 邮箱 / SSO 都在），注入脚本生效（__tsWbHook=1，fetch 与 XHR 包装都在）； 抓取链路两条都实测通了（sessionStorage 令牌、请求头 Authorization: Bearer …）—— 都是跳到哨兵地址、被拦下、写进凭据库、窗口自动关、渠道变「已登录」； 用户关窗则主窗口收到 {"ok":false,"cancelled":true} 且按钮恢复可点；测试注入的假令牌已删除，槽位回到空。仍然只剩上面那一条：真实令牌能不能被 get-user-resource 接受。

八、扫码登录成功却"没反应"：抓令牌的前提就是错的（2026-10-08，v0.1.19）

第七节把死锁修掉之后，用户真机扫码登录成功了 —— 然后窗口停在页面上"没反应"，手动关掉则提示「已取消登录」。 用 CDP 把控制台的请求逐条看下来，答案很直接：这个流程里根本没有 Bearer 令牌可抓。

本页第三节的假设真机实测
控制台请求带 Authorization: Bearer …没有。/console/*、/billing/meter/* 的完整请求头里都没有 Authorization。
令牌存在 sessionStorage["growth-center-token"]没有。登录后 sessionStorage 里只有 9c412d6095037d16 与 one-obs.login.attempt。
登录跳转带 ?token=没有。落地是 /login/ →（点一次账号）→ /profile/plans-usage。
（新发现）认证在哪httpOnly 的 session 与 session_2 两个 Cookie。缺任何一个都 401；只带其中一个也 401。
（新发现）还有第二道门网关按 User-Agent 分流：同一批 Cookie，浏览器 UA 200、客户端 UA（TokenScope/0.1）401。curl 逐项对照过。

改法（v0.1.19）：登录窗不再注入脚本、不再拦导航（页面是第三方的，挂件只负责看它走到哪儿）； 观察者每秒判一次"这份会话能不能真打通接口"，通了就关窗报「已登录」； 会话不落盘 —— 它住在 WebView2 的 profile 里，取数时现读。两个理由：凭据管理器的 blob 上限实测只有约 1280 字符（两个 Cookie 近 6 KB），而且平台一旦轮换 Cookie，存下来的副本会静默失效。 「清除登录」会一并删掉 profile 里的会话，并作废取数的 5 秒结果复用。

顺带拆掉一颗会崩掉整个挂件的地雷：cookies_for_url 内部是阻塞派发（worker 线程发消息给主线程， 再 rx.recv().unwrap() 等回信）。目标窗口正在销毁时回信永远不来，unwrap 直接 panic， 而 release 是 panic = "abort" —— 一次派发失败等于挂件原地消失（实测踩到：刚关掉登录窗就去读它的 Cookie， 日志里留下 RecvError）。现在所有要碰 webview 的调用都改成"投递到主线程 + 自己带超时地等"， 拿不到就当没读到、退回"未登录"，绝不 panic。

验证：已登录时点「登录」→ 窗口 1.2 秒自动关、读数照常（剩余 5462.54 credits）； 清除登录 → 会话 Cookie 消失、渠道变「未登录」；此时点「登录」窗口停在登录页，按 X 关掉 → 「已取消登录」、 按钮恢复、日志零 panic；把会话 Cookie 原样写回 → 读数立刻回来（证明不依赖任何本地副本）。 会话有效期实测 7 天（两个 Cookie 的 expires 都是 10-15），所以大约每周要重登一次。

取证与核对方式：直读你机器上的凭据文件与 ~/.workbuddy/keyblob；用 6 月那份明文令牌对两个域名各发一次真实请求（只读取数，无写操作）；查 tokenscope.db 快照序列定位断供时刻；从 app.asar 与网页控制台 JS 包反查加密方案与令牌来源。仓库代码只做了行号级引用核对，未做任何修改。

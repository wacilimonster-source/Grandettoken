一、研究结论:数据早就到了,只差展示

  • 真实响应(刚用你的 key 实测,只读账务接口):三个窗口都带 resetsAt,ISO 8601 UTC 格式 —— 后端 extract_opencode_go 已解析进 window.resetsAt 传给前端,前端从未渲染。启用它零取数成本;
  • 「本月」重置点是 10-13 14:20:48Z(带秒)—— 锚定开通日而非日历月,叫「本月」会误导,应叫「周期」;
  • 发现一处现存不一致:后端主数值取「最紧张窗口」(本周 82%),前端大数字取「本月窗口」(91%)—— 本设计顺带统一;
  • rolling 的 resetsAt 随滑动窗口滚动(5 小时窗口的结束时刻),不是固定周期 —— 倒计时语义与其他两个不同,但展示方式可以统一。

三、设计规则

  • 主数值 = 最紧张的那个窗口(剩余百分比最低 → 最先触发限流),大数字下方注明是哪个窗 + 倒计时:「本周窗 · 2天6小时后重置」—— 顺带修掉前后端口径不一致;
  • 每条窗口迷你条右侧加倒计时,档位化格式:<1h「37 分钟后」/ <24h「5.2 小时后」/ ≥1天「2 天 6 小时后」;60 秒轮询刷新,无需秒级跳动;
  • 倒计时是中性信息,不抢状态色(次级灰白)—— 重置快是好消息,别用红黄渲染;唯一例外:限流中且倒计时 <1h 时变绿「马上恢复」;
  • 组合预警(本设计最有价值的判断):最紧张窗口剩余 < 标红阈值 且 距重置 > 3 天 → 行内红字:「周期余量仅 x%,距重置还有 N 天 —— 省着用或等重置」;距重置 < 3 天不加红字(熬一熬就好),避免天天喊狼来了;
  • 展开详情每窗一行:剩余% + 相对倒计时 + 本地绝对时间(ISO UTC → 本地时区);
  • 命名「本月」→「周期」(实测锚定开通日);缺 resetsAt 兜底:未公开接口不保证字段常在,缺失时倒计时列显示「—」,其余照旧;
  • 实现面:纯前端(app.js 渲染 + 解析 ISO 时间),Rust 与配置零改动 —— Window.resetsAt 已在通道里。

四、待裁决

  • 1大数字口径:A 最紧张窗口+标注(推荐,上文即此)/ B 维持「本月/周期」窗不变,只加倒计时;
  • 2组合预警阈值:A 剩余<标红线 且 距重置>3 天才提示(推荐)/ B 只要剩余低于红线就带「距重置还有 N 天」后缀(更啰嗦但无阈值心智负担);
  • 3「本月」是否改名「周期」:A 改(推荐,符合实测)/ B 保持(用户语言更熟)。

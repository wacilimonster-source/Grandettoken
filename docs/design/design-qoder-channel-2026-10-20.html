Qoder 渠道:积分展示 + 每日打卡

产品设计 · 2026-10-20 · 证据来自本机 Qoder 桌面端 0.4.8(region=global)的实抓日志与真实接口调用

一句话:把 Qoder 作为第 8 个内置渠道接进来。它是积分型(Points)渠道 —— 展示剩余 Credits 与每个资源包的到期日,每日 10:00(UTC+8)自动领 100 Credits。 国内版与国际版是两套账号、两套域名、两个渠道条目,不合并。

0. 先说结论(六条)

#结论证据等级
1Qoder 的积分叫 Credits,是积分型渠道,逐资源包有到期日 —— 与 Trae 同族,不是金额型实测
2额度接口 GET {openapi}/api/v2/quota/usage,剩余在 addOnQuota.remaining(本账号)或 userQuota.remaining实测
3打卡接口 GET {openapi}/sash/api/v1/me/campaigns → POST …/{id}/claim,幂等(重复领返回 replayed:true,不重复发币)实测
4打卡每天 10:00(UTC+8)跨日 —— 官方活动描述原文写着「每日 10:00(UTC+8)刷新」实测
5凭据是 Electron safeStorage(auth.v1.dat,v10 + AES-256-GCM,DPAPI 保护的密钥),不是 WorkBuddy 式静态钥信封实测
6打卡不需要设备指纹(Cosy-Machine*)—— 只带 Authorization + Cosy-ClientType 即可实测
与 WorkBuddy 的关键差异:WorkBuddy 走「挂件内网页登录抓 Cookie」,Qoder 走「读本机桌面端凭据」。 Qoder 的凭据能自动续期(refreshToken 到 2027-10),所以不会像 WorkBuddy 那样每 7 天断一次。 这是本次设计里最省心的一点。

1. 国内版 vs 国际版:两个渠道,不是一个渠道的两个域名

两版的账号体系、域名、凭据存储目录全都不一样,且官方明确不支持跨区迁移。 所以做成 两个独立渠道条目(qoder / qoder-cn),各自独立开关、独立凭据、独立签到状态。

API 主机openapi.qoder.shopenapi.qoder.com.cn实测 两边未认证都回 401
官网qoder.comqoder.com.cn / qoder.cn实测

两个判别陷阱(务必不要这么写代码):
  • ❌ 不能用 product.json 的 desktopUpdateDownloadBaseUrl 或 endpoint-cache.json 判版本 —— 本机明明是 region=global(日志每条请求都打 "region":"global"、走 openapi.qoder.sh), 但这两个文件都写着 *.qoder.com.cn。用它判会判反。
  • ❌ 不能用凭据里的 email/user 猜区域。正确做法:用「哪个目录读到了凭据」+「哪个 API 主机应答了」双重判定(见 §4)。

1.1 为什么不做成「一个渠道 + 区域切换」

与 Trae 不同(Trae 只有国内站,X-User-Region: CN 是同一套接口的头部开关),Qoder 两版是 两套独立账号:同一个用户在两边可能是两个不同的账号(本机 uid 01a068b6… 是 global 的)。 做成一个渠道就必须回答「余额算谁的」,而答案只能是「各算各的」。所以拆两条。

最重要的一个坑:剩余积分有两个可能的字段,必须都读、按「哪个有量」取。
  • 本账号(personal_standard)userQuota.total = 0,量全在 addOnQuota(套餐赠送/加量包)。
  • 若只看 userQuota.remaining,本账号会显示 0 积分 —— 而实际还有 86。
  • 反过来,订阅用户(userQuota.total > 0)的量在 userQuota。
取值口径:remaining = addOnQuota.remaining + userQuota.remaining(两者都缺失才判取数失败, 不要用 0 顶替 —— 0 会被渲染成「已耗尽」)。
对照:同一次响应里 totalUsagePercentage: 0.15 与 addOnQuota.percentage: 0.15 一致(14/100 用掉 15%), 可作为「读对了字段」的交叉校验。

2.2 逐笔到期:本期只能做到「部分」

诚实说明:额度接口 只给汇总(userQuota / addOnQuota),没有逐笔到期明细。 社区资料提到逐资源包到期在 dedicated_resource_packages[].expires_at,但本机这次响应里没有这个字段 (账号是 standard 档,可能只有企业/更高档才有)。

所以设计分两期(见 §6):M1 先做汇总(剩余 + 已用 + 套餐档位),M2 再补逐笔。 M1 不做假承诺 —— 卡片上不画「哪笔什么时候过期」,只画总额,并在详情里如实写「逐笔明细本期未接入」。

3. 每日打卡

3.1 接口事实表

步方法与 URL请求头响应
① 查GET {openapi}/sash/api/v1/me/campaigns Authorization: Bearer
Cosy-ClientType: 10
User-Agent: Qoder
Accept: application/json		 {uid, showCampaign, claimable, campaignUrl, streak_days, campaigns:[…]}
② 领POST {openapi}/sash/api/v1/me/campaigns/{campaignId}/claim

两个实现细节是写代码时最容易错、且真机实测抓到的:
  • 查状态是 GET,不是 POST。用 POST 打 /sash/api/v1/me/campaigns 直接 404 (2026-10-20 真机踩到),GET 才是 200。所以"查/领"的 HTTP 方法必须逐渠道声明, 不能沿用 Trae/WorkBuddy 的"全是 POST"。
  • actionType 的真机拼写是 CLAIM_BENEFIT(带 E)。 早先照混淆 bundle 写成了少一个 E 的 CLAIM_BEFIT,后果是 has_campaign 恒为 false —— "今天可领"会被静默判成"本期无打卡活动",用户当天直接丢 100 分。 真机用例抓到后已改正,并留了别名表与回归用例 (qoder_action_type_is_claim_benefit_with_e)。

3.3 调度:10:00 跨日,不是 00:23

这是与现有两个渠道最大的不同,必须改 checkin.rs 的调度模型。 现有 scheduled_minute() 硬编码「00:23 + 0–20 分钟抖动」,对 Qoder 是错的 —— 10:00 之前跨日还没发生,那时去查会拿到昨天的状态,把「昨天已领」误判成「今天已领」,当天就静默丢分。

改法:把「当天刷新时刻」变成渠道定义里的一个字段。

// checkin.rs:由渠道定义决定跨日时刻,不再全局写死 00:23
pub struct CheckinDef {
    …
    /// 签到日的刷新时刻(北京时间的小时)。00 = 自然日;Qoder 是 10。
    pub day_roll_hour: u32,
}

// 抖动仍然保留:10:00 + 0–20 分钟,避免所有用户同一秒撞平台
pub fn scheduled_minute(day: &str, id: &str, roll_hour: u32) -> u32 {
    if roll_hour == 0 { return 23 + (hash % 21); }      // 老渠道:00:23–00:43
    roll_hour * 60 + (hash % 21)                        // Qoder:10:00–10:20
}
渠道刷新时刻调度窗口依据
Trae00:0000:23 – 00:43实测 沿用现状
WorkBuddy00:0000:23 – 00:43实测 沿用现状
Qoder / Qoder CN10:0010:00 – 10:20实测 官方活动描述 + startAt/endAt

签到日的定义也要跟着变:Qoder 的「今天」是「从 10:00 起算的那个活动周期」。 beijing_day() 仍返回自然日,但判幂等时要用活动周期(startAt 那一天的日期)作 key, 否则 09:59 和 10:01 会落进同一个自然日,当天第二次就不会再试。

4.2 为什么这条比 WorkBuddy 稳

WorkBuddy(现状)Qoder(本设计)
凭据来源挂件内网页登录 → webview Cookie 罐直接读桌面端 auth.v1.dat
寿命7 天绝对 TTL,到点必死accessToken 约 3 周 + refreshToken 约 1 年
能否续期不能(TTL 是绝对的)能(refreshToken)
用户要做的事每 7 天点一次「重新登录」正常用桌面端就不用管
可自动化否(登录要扫码)是(refresh 可机器代做)
但有一条硬依赖:用户必须装并登录过 Qoder 桌面端。 没装桌面端 = 没有凭据 = 渠道显示「未检测到 Qoder 登录」。 这与 WorkBuddy 的桌面端凭据那条路同口径(读不到不是错误,只是没有这条来源)。 不做「挂件内网页登录 Qoder」—— Qoder 网页版与桌面端是两套前端,再走一次 Cookie 抓取等于把 WorkBuddy 的 7 天坑重踩一遍,没有理由。

4.3 refresh 续期(可选,M3)

凭据里带 refreshToken,理论上可以在 accessToken 过期前自动续期,像 WorkBuddy 现在做的那样。 但本期先不做:accessToken 还有 3 周,先把 M1/M2 跑通;续期的接口路径本次未取证 (只知道 refreshToken 字段存在,不知道换 token 的端点),不做猜测性实现。

到期的处理:M1 只做「如实报过期 + 提示打开一次桌面端」,与 WorkBuddy 的 DesktopErr::Expired 文案同风格。

3bundle(app.asar,157 MB)全量可打印字符串里搜端点形状grant_type(109)、token_endpoint(109)、offline_access(12)、exchangeRefreshToken 等全部来自打包进来的 MCP OAuth 客户端库(handlers/token.js、server/auth/router.js 这些路径是那个库自带的),不是 Qoder 自己的认证链路差点被误导:这些字符串看着"像"答案,其实是第三方 SDK
4凭据文件里的 expiresAt 与 refreshTokenExpiresAt2026-11-10 / 2027-10-06 —— 两值不同,说明字段有独立语义,但客户端没有在 access 到期前换新的迹象字段存在 ≠ 有人在用
5文件 mtime 这条最硬:auth.v1.dat 的最后写入是 2026-10-19 11:41,而桌面端此后连续运行了约 33 小时(campaign 每小时轮询一次、全部 200)33 小时里每小时都在用同一份 token,文件从未被重写 → 客户端没有周期性刷新行为刷新的可观测副作用就是"这个文件被重写",它没发生
还要说清"没证到"的部分:上面第 5 条只证明非临近过期时不刷新, 不能证明"临近过期时也不刷新"。要回答那个,只能等 expiresAt 真的临近 (本机 2026-11-10),或人为把时钟拨过去 —— 后者会影响别的软件,不建议。
对我们的实现意味着什么:
  • 不做 refresh 自动续期 —— 没有端点可实现,硬做只能靠猜,而猜错会把用户登出(轮换 refreshToken 的经典坑)。
  • 过期处理保持现状:auth.v1.dat 里的 expiresAt 到点后如实报 「凭据已过期 · 打开一次 Qoder 桌面端」,由客户端自己在它认为合适的时候更新那份文件 —— 我们只读不写,不替它做决定。
  • 但要去真机确认"到期时客户端到底会不会自己更新":本机 access 到 2026-11-10, 届时开一次桌面端看 auth.v1.dat 的 expiresAt 有没有被推后。 这是唯一能验证「用户只要开着桌面端就不会断」的办法,也是我们文案的依据。

如果以后真要抓 refresh 请求,方法是这样(留给后续)

  1. 先定"什么时候会刷":本机 expiresAt 是 2026-11-10,refresh 若存在只可能在临近那时发生。 到那天开一次桌面端,先看 auth.v1.dat 的 mtime 与 expiresAt 有没有变 —— 变了说明会自己续(那我们的"打开一次即可"文案是对的),没变说明不会(文案要改成"重新登录")。
  2. 要抓包而不是读日志:日志只记它自己发起的请求;若刷新由别的进程(内嵌 webview / qodercli)发起, 主进程日志里看不到。用 Fiddler / mitmproxy 挂系统代理,过滤 openapi.qoder.* 与 qoder.com, 看有没有 POST 到非 campaign 的路径。注意这会把凭据暴露给代理进程,用完立刻卸证书。
  3. 优先用"副作用观测",别解 token:刷新的可观测副作用就是 auth.v1.dat 被重写 (token 变、expiresAt 推后)。比较前后 sha256 + expiresAt 就够了 —— 这条最省事,也最不碰敏感数据。§6.3 表里第 5 条用的就是这个方法。
  4. 不要为了验证"新旧 token"把它们解出来打接口:凭据会被带进更多地方,而收益只是"确认换了"。
  5. 不要把系统时钟整体往后拨来造场景:会影响别的软件,也可能触发服务端时钟校验而被判异常。
一句话总结这次取证:「refresh 端点」这个问题本身可能是错的问题 —— 应该问的是「Qoder 桌面端会不会自己续期」,而答案用文件 mtime 就能观测, 不需要端点、不需要解 token。这也是我们最终选择"只读不写、到期如实报"的依据。

9.1 「默认开」的两个必须说清的点

① 升级会不会把用户关掉的开关又打开?
不会。Config::sanitize() 只补缺的渠道(entry().or_insert_with()), 已有条目整条保留 —— 用户显式关掉的渠道保持关着。 但有一条要如实告知:老配置里从来没有 checkin 这个键时, 容器上的 serde(default) 会整份取新默认(全开)。也就是说 "从没碰过签到设置"的用户,升级后会开始自动签到。这是"默认开"裁决的直接后果, 已在 config.rs 的单测里钉住(existing_checkin_map_keeps_user_choices_and_backfills_new_channels)。

② 默认开会立刻发请求吗?
会,但受两道闸门约束:渠道被隐藏时不发(hidden_channels 同口径); 跨日时刻未到时不发。所以"装上就自动签到"的代价是明确的,且用户随时可在设置里关掉。

ZCode 渠道:每日赠送额度领取(用户口径「积分」)

产品设计 · 2026-11-06 · 证据来源:magpie #1001 实测记录、CreditDaddy 源码(社区实现)、本机 ~/.zcode/v2/credentials.json 结构实测

一句话:把 ZCode(Z.ai 官方 CLI/桌面端账号)接成第 11 个内置渠道,自动领取官方客户端里的每日赠送额度(Trust Build 等活动,用户口径叫「积分」)。 展示口径按用户要求收得很紧:只有「本应用当天领取成功」才显示渠道卡和积分,其余一切情况(无活动 / 已被官方客户端领走 / 验证码拦截 / 失败)整卡隐藏。 本地切换 ZCode 账号后,老账号的领取展示立即让位,新账号重新走自己的领取与展示。
先泼一盆冷水(期望管理):上游对领取接口部署了阿里云验证码(部分账号/时段强制)。 magpie 官方在 #1001 明确裁决:不做自动过验证码,只做只读提示。 本设计跟随这条裁决:v1 只做「不带验证码直领」——服务端未风控时直接成功;返回 3007 时放弃并隐藏,绝不尝试绕过。 所以这个功能不保证每天都领到,领不到的日子渠道卡就是不在——这恰好与用户「没领到就不展示」的要求天然一致。

0. 先说结论(八条)

#结论证据等级
1ZCode 的「积分」= 官方客户端的每日赠送额度(活动套餐),接口是 GET …/zcode-plan/billing/preview → POST …/zcode-plan/billing/claim,与 Trae/Qoder 的签到同族,融入现有 checkin.rs 框架社区实测
2赠送是token 额度不是货币积分:样例 plan zcode-v3-start-plan-trust-1006,grant_units=1 亿 token,模型 GLM-5.3-Flash,one_time、有效期约 24h社区实测
3展示口径:卡片仅在本应用当天 claim 成功(code=0 或 1003 且有本应用记录)时出现,大数字 = 今日领取数额(亿 token 格式);preview 为空 / 1003 无本应用记录 / 1005 / 3007 / 失败 / 无凭据 → 整卡隐藏产品决策
4仅 z.ai 国际版有此接口;bigmodel 国内版无 preview/claim(CreditDaddy 源码佐证)。本机当前 oauth:active_provider 即 z.ai,对得上本机实测+社区代码
5凭据读本机 ~/.zcode/v2/credentials.json 的 zcodejwttoken(Bearer),与模型注入读 config.json 同目录不同文件;账号指纹取 oauth:zai:user_info 的用户 id,取不到退化为 token 整串哈希本机实测
6账号切换:展示与账本全部按「日期+账号指纹」分账(沿用 key_fp 机制)。切换后老账号今日领取立即隐藏,新账号当天重查 preview、按自己的领取结果决定展示产品决策
7渠道 id 用 zcode。与模型注入的 Client::Zcode(inject.rs)只是同名、不同子系统:一个写 ~/.zcode/v2/config.json,一个读 credentials.json,配置键域不重叠,文档注明即可代码确认
8v1 不做:验证码自动化(永久)、bigmodel 国内版领取、z.ai 开放平台积分签到(/v2/billing/meter/daily-checkin,那是另一套体系,不属于 zcode 渠道)范围裁决

2. 上游接口与凭据取证

2.1 接口清单(z.ai 国际版)

用途方法 + URL说明
查可领活动GET https://zcode.z.ai/api/v1/zcode-plan/billing/preview?app_version={ver}&platform=win32-x64返回 data.plans[],已领过的账号返回空数组;data.server_time 秒级时间戳
领取POST https://zcode.z.ai/api/v1/zcode-plan/billing/claimbody {"plan_id":"…"};成功 code=0 且 data.plan 含 name/starts_at/ends_at
余额(回查用)GET https://zcode.z.ai/api/v1/zcode-plan/billing/balancedata.balances[] 含 total/used/remaining_units、show_name、expire_at;data.plans[] 按含 status==='active' 过滤。仅作回查证据,不渲染
验证码配置GET https://zcode.z.ai/api/v1/client/configs含 captcha enabled/region/sceneId。v1 只用来记日志,不做后续动作

2.2 请求头

Authorization: Bearer <zcodejwttoken>
User-Agent: ZCode/<app_version>
X-ZCode-App-Version: <app_version>      ← billing 接口对客户端版本有校验,过低直接 3001
X-Platform: win32-x64
X-Release-Channel: stable
X-Client-Language: zh-CN
X-Device-Mid: <稳定 UUID>               ← 首次生成后存 settings 表,之后不换
x-request-id: <每请求随机 UUID>

2.3 preview 返回结构(关键字段)

data.plans[]:
  plan_id: "zcode-v3-start-plan-trust-1006"
  name:    "ZCode Trust Build"
  priority
  entitlements[]:            ← 过滤 meter==='model_usage' && unit_type==='token'
    show_name:  "GLM-5.3-Flash"
    grant_units: 100000000  ← 1 亿 token
    period:     "one_time"  ← daily / weekly / monthly / one_time

2.4 业务错误码(一律按 code 判定,HTTP 200 不代表成功)

code含义本应用处置展示
0领取成功记领取证据(响应含 plan 明细),balance 回查做到账核对显示 ✓
1003该套餐已领取过本应用今天已有成功记录 → 按已领口径;无记录(官方客户端领的)→ 不是我们领的有记录→✓ / 无→隐藏
1001套餐不存在静默(活动下架)隐藏
1002活动已结束/暂不可领静默隐藏
1004不符合领取条件记日志隐藏
1005今日名额已用完按响应 data.plan.ends_at snooze,当天不再试隐藏
3001参数错误(常见于 app_version 过低)版本取证项(见 §7);重试一次后放弃隐藏
3007验证码校验失败硬边界:放弃,不绕过隐藏(+可选提示,见 §8-A)
401未登录/凭据失效Outcome::AuthNeeded,凭据指纹标失效隐藏
preview 为空 ≠ 无事可做(CreditDaddy 实测坑):服务端偶尔把活动从 preview 列表藏起来(2026-10-30 WEEKEND BUILD 实测 preview 空、按已知 planId 直领可成功)。 所以 empty-preview 时还差一步:对昨天领过的 planId 形态做一次试探性 claim,1001/1002 静默当没有,0 即成功。 v1 简化:只在「昨天成功领过某 planId」时做这一次试探,不维护硬编码活动清单。

2.5 本机凭据取证(2026-11-06 实测,值已脱敏)

~/.zcode/v2/credentials.json 顶层键:
  zcodejwttoken                     <string:387>   ← 领取用 JWT(Bearer)
  oauth:zai:access_token            <string:1919>
  oauth:zai:user_info               <string:330>   ← 账号指纹来源(用户 id)
  oauth:active_provider             <string:51>    ← 当前激活的提供方
  account-provider:coding-plan:…api-key           ← bigmodel 侧密钥(本设计不用)
  project-key-location:v1:…(4 条)                 ← 项目密钥定位(本设计不用)

本机 oauth:active_provider 指向 z.ai → 功能可用。若某天切到 bigmodel 激活,无 preview/claim 接口,渠道自然全程隐藏(CreditDaddy 源码:preview/claim 仅存在于 zcode.z.ai 域名)。

CreditDaddy 提到部分安装的凭据值是 enc:v1: 信封(AES-256-GCM 派生密钥)。本机当前为明文 JSON 值,但实现必须两者都兼容:值以 enc:v1: 开头走解密,否则直接用。

3. 展示设计:「领取到才存在」的渠道

3.1 展示谓词(全部满足才渲染渠道卡)

show = 签到开关开(settings.zcode.checkinEnabled)
     && 凭据可读且 active_provider=zai
     && 今天(自然日)本应用【按当前账号指纹】领取成功

四条任一不满足 → 整卡一个像素都不画(复用现有徽标三条硬规矩里的第 1、2 条精神:没开启不画、状态没读到不画)。这与 WorkBuddy 的 auto_hide_when_no_credential 是两种隐藏:zcode 的隐藏是展示规则,不写用户的 hidden 设置,两者互不污染。

3.2 卡片 mock

领取成功日(唯一可见形态)

ZCode ✓ 已签
+1亿 token
今日领取 · GLM-5.3-Flash · 有效期至 11-07 09:00
已领到 +100000000 token · 余额已确认到账(增量吻合)

大数字 = 今日领取的赠送额度(亿格式化),不是余额。数额来自领取前 preview 的 entitlements; 响应里 effective_at 晚于领取时刻时,次行标注「HH:mm 生效」,不因此隐藏——领取动作已成功,积分已是账户的。

其余一切日子

ZCode
(整卡不渲染)
无活动 / 已被官方客户端领走 / 验证码拦截 / 失败 / 无凭据 / 开关关

注意「已被官方客户端领走」也不展示:1003 且本应用无成功记录 = 不是我们领的。 这与全应用既有口径同源(「✓+100 会让人以为是我们领的」)——葛朗台只炫耀自己捡到的钱。

3.3 与既有 UI 部件的关系

部件zcode 的行为
卡片徽标(ckBadge)领取成功日画 ✓ 已签,数额进 tooltip(全应用统一规矩,不画 +N)
展开详情行(ckText)「已领到 +1 亿 token · 模型 GLM-5.3-Flash · 余额已确认到账(增量 +1 亿…)」;balance 回查失败时降级为「已领取(响应含活动明细)」
首页待签条(ckPendingStrip)自然跟随 CheckinState:有活动可领(retry:ready)→ 出现并带领取按钮;领完/无活动 → 消失。空 preview 记为 no-activity,不算「待签」
签到中心页照常记录全部事实(含「无活动」日、3007 日)——签到中心是账本,不是橱窗;隐藏规则只作用于首页渠道卡
积分到账行(grantLine)不适用(zcode 无「活跃赠送」语义,领取结果直接由签到行承载)

4. 领取流程(融入 checkin.rs 框架)

4.1 CheckinDef 声明

id: "zcode"
auth:          ZcodeLocal(新分支,见 §5)
status_url:    GET  https://zcode.z.ai/api/v1/zcode-plan/billing/preview?app_version={ver}&platform={plat}
claim_url:     POST https://zcode.z.ai/api/v1/zcode-plan/billing/claim      body {"plan_id":"{id}"}
day_roll_hour: 0(自然日;活动每日由服务端投放,preview 是唯一事实来源,无需本地跨日特殊化)

4.2 每日一次的编排(挂在现有自动签到节拍器上,无额外轮询)

  1. 闸门:开关关 / 无凭据 / active_provider 非 zai → 直接静默返回(渠道今日隐藏)。
  2. preview:可领 plans 为空 → 记 no-activity,结束(隐藏)。昨天有成功 planId 且今天 preview 空 → 按 §2.4 注做一次试探。
  3. claim:逐 plan 领取。code=0 → 进入回查;1003 → 查本应用今日记录;其余码按 §2.4 表处置。
  4. 回查:balance 的 active plans 出现刚领的 plan_id(或 balances 增量吻合)→ 到账确认。注意:effective_at 可能是当日 23:00,balance 暂无该笔不算失败——claim 响应里的 plan 明细(name/starts_at/ends_at)本身就是领取证据,回查只是加分证据。
  5. 落库:checkin_log 记「日期 + 账号指纹 + plan_id + 数额 + 证据」;快照按 key_fp 分账。

4.3 红线沿用(checkin.rs 头部三条,逐条对表)

  • HTTP 200 不代表成功 → 全按业务 code 判定(§2.4 表)。
  • 不把「点了按钮」说成「领到了」→ 证据 = claim 响应 plan 明细 + balance 回查,双证据落库。
  • 签到状态不参与余额渲染 → zcode 卡片大数字是「今日领取」语义,由签到到账数据驱动,不由 balance.remaining 驱动。

5. 账号切换设计

ZCode 的账号切换发生在官方客户端里(我们只读凭据文件),对葛朗台来说,切换 = credentials.json 内容变化。设计四件事:

#机制说明
1指纹 oauth:zai:user_info 解出用户 id 作指纹;解不出退化为 zcodejwttoken 整串哈希。每次领取流程开始时重读文件、重算指纹(文件变化即感知,不依赖事件通知)
2展示让位 首页卡片展示绑「今日+当前指纹」。切换瞬间,老账号今天领的积分立即隐藏(§3.1 谓词按当前指纹求值)——绝不出现「张三领的显示给李四看」
3状态隔离 CheckinState 的 doneToday/credits/streak 按「日期+指纹」计算:换号后新账号当天视为未领取,重走 preview→claim。历史 checkin_log/snapshots 按指纹分账,互不推算(沿用 key_fp 分段既有机制)
4多账号不会同时领 我们只读「当前激活」的那份凭据,不做多账号轮询(与 CreditDaddy 的多账号托管不同,葛朗台不存任何 ZCode 密钥副本)。用户在官方客户端切谁,我们就服务谁
与既有 App 型凭据的对比:Trae/Qoder 的凭据多份候选是「401 时逐份试」;zcode 只有一份活凭据(credentials.json 当前值),没有逐份试的问题,反而简单。Encountering 401(凭据失效,如官方端登出)→ AuthNeeded → 当日隐藏,等用户在官方端重新登录后自然恢复。

7. 风险与红线

风险处置
验证码风控硬边界:不绕过(magpie 官方裁决原文:「用程序去过 ZCode 的人机验证,本质上就是绕过它」)。3007 → 放弃 + 隐藏 + 记日志。CreditDaddy 用隐藏窗口跑阿里云 SDK 的做法不采纳:官方裁决点名、账号风控风险由用户承担、SDK 逆向维护成本高
版本校验(3001)billing 接口校验客户端版本。app_version 从 Windows 注册表 Uninstall 项读 ZCode DisplayVersion(CreditDaddy 同款做法),取不到回退保守值 3.14.3+。实现期先真机取证一次
频控挂现有签到节拍器,每日 preview+claim+balance 各 ≤2 次;1005 按 ends_at snooze;绝不加独立高频轮询
凭据安全token 与指纹不落日志、不落 JSON/SQLite 明文(secrets.rs 首行规矩);credentials.json 只读,绝不写回
命名冲突渠道 id zcode 与 inject 的 Client::Zcode 同名不同域(§0-7);若实现中发现前端字典键冲突,渠道 id 退让为 zcode-plan
claim 即证据的口径变化既有红线是「回查是唯一的成功证据」;zcode 因 effective_at 延迟到账,回查可能暂时空手。本文已在 §4.2 明确:claim 响应含完整 plan 明细时本身即领取证据,回查为到账加分证据——需在代码注释与 test 用例里固化,防止后人误改

8. 开放问题(待拍板,均已给推荐项)

#问题推荐
A3007(验证码拦截)或官方客户端已领走时,严格静默还是给一条轻提示? 卡片严格隐藏(符合「没领到不展示」);另加默认关闭的设置项「领取受阻提醒」,开启后当日首次受阻发一条系统通知,引导去 ZCode 客户端手动领
B展示单位口径:「+1亿 token」(原始事实)还是折算成抽象「积分」? 用 token 原始口径 + 模型名。折算积分需要凭空的汇率,和全应用「不编数字」的口径冲突
C多活动日(如 TRUST + WEEKEND 同日)怎么显示? 大数字取合计 token 数,详情行逐 plan 列明细
D非 token 单位的 entitlement(未来可能出现)怎么处理?跳过并记日志,不猜单位

签到「到账核对」二次校验

2026-10-24 · v0.1.67 · 前置:design-auto-checkin-2026-10-13

claim 之后的余额二次校验:用渠道自己的余额快照差值,给「今日已领」补一份 只见证、不裁决 的到账证据。判定链路一字不动。

为什么做

  • Trae / WorkBuddy 的签到接口经常不返回数额(0.1.5x 系列真机:credits = null 是生产常态), 界面只能说「平台未返回数额」—— 领没领到、领了多少,用户无从核对。
  • 签到渠道的余额快照本来就在每轮落库(fetch.rs → snapshots 表,provider id 与签到 id 相同), claim 成功后也已经触发 refresh_now。缺的只是把两条线在签到这一侧接起来。
  • grants.rs 已论证过余额差值作为证据的纪律(source: "delta" = 按余额推算,不当平台事实); 本设计把同一套纪律用在签到上。它与 providers::tracks_grants 的「到账记录」语义不同: 那个记所有到账(充值也进),这个只关心 claim 窗口内有没有见到增量。

红线映射(只见证,不裁决)

定位一句话:余额核对只能把结论「确认得更实」,永远不能否决或改写签到结论。
现有红线在本设计中的落法
① 按 code 判,不按文案判定链路完全不动,回查状态仍是唯一成功证据(run_checkin 的回查分支原样保留)。
② 不把「点了按钮」说成「领到了」推算出的增量在界面上永远带「按余额推算」标注,与 grants.rs 的 source:"delta" 同一条纪律。
③ 签到状态不参与余额渲染反向同样成立:核对结论绝不参与 done_for_day / signed_today / blocks_today,不改 last_code,不改徽标颜色。
明确不做: ① 不用余额增量把 confirming 升级成 claimed(余额分不清「我们领的」和「恰好充值」); ② last_credits 不回填余额观察值(checkin_month_credits 的「本月已领」只信平台字段); ③ checkin_log 流水表一期不动(核对结论落 diaglog,以后要进流水另开带 UNIQUE(channel, day) 的新表)。

数据模型

CheckinCfg(config.json,serde default + camelCase)加一个可选字段,无数据库迁移:

pub struct ArrivalInfo {          // core::checkin
    pub status: String,        // "pending" → "confirmed" | "unseen"
    pub baseline: f64,         // claim 前最后一份成功快照的余额
    pub baseline_at: i64,
    pub delta: Option<f64>,    // 确认时观察到的增量(confirmed 才有)
    pub observed_at: Option<i64>,
    pub day: String,           // 签到周期日(Qoder 含 10:00 跨日)= 核对截止线
}
  • 跨版本兼容:老配置 JSON 没有 arrival → serde default 兜成 None(有测试)。
  • 前端只收到今天的核对单(checkin_state_of 里按 a.day == today && last_day == a.day 过滤)—— 昨天的 confirmed 挂在今天的 already 上会变成误导。

流程(零新增网络请求)

  1. 基线 — run_checkin 在发起 claim 之前,读该渠道最新成功快照 (store::latest_snapshot,纯读库)。读不到 → 不核对(arrival = None)。
  2. 即时核对 — 回查判 Claimed 后,refresh_now 本来就会跑;跑完再读一次最新快照, 喂给 ArrivalInfo::observe。判出的三态写进 entry.arrival 落盘 + diaglog 一行。
  3. pending 核销 — settle_arrivals(挂在 refresh_now 与 poll_loop 的取数完成点, 零网络请求):对每个 enabled 渠道的 pending 单子,拿最新快照接着核;状态有迁移就落盘 + checkin-updated 事件。过签到周期日仍无增量 → unseen,不隔天追账。
锁纪律(N04):settle_arrivals 只改 checkin[id].arrival 这一项,读 live 配置合并回去,不整份克隆覆盖用户在签到跑动期间的其它改动。

判定口径(单向,只升不降)

观察落点为什么
delta >= 0.5(ARRIVAL_EPS,与 grants::GRANT_EPS 同值)confirmed有真实正增量 = 到账迹象。确认标准是「有正增量」而非「恰好等于 credits」—— 取数间隔里的消耗会把 +100 压低(与 grants::ACTIVITY_TOL 的容差思路同理)。
delta <= 0.5,未跨日pending发放可能延迟,或被同轮消耗抵消。不判失败。
未跨日一直 pending → 跨日仍无增量unseen截止。「未见增量 ≠ 没领到」,文案必须明说。
三态里没有「确认失败」。delta ≤ 0 不证明失败:+100 发放与 −120 消耗同轮,净增量就是负的 —— 判失败等于拿消耗当没发放。

界面文案(前端 ckArrivalNote)

状态ckText claimed 分支追加(替换原「· 已触发到账核对」)
confirmed,与平台数额吻合(|delta−credits| ≤ 5)· 余额已确认到账(增量 +N,与平台数额吻合)
confirmed,没吻合 / 平台未给数额· 余额已见增量 +N(按余额推算)
pending· 正在核对到账(随下一轮取数更新)
unseen· 余额未见增量(可能被消耗抵消,不代表没领到)
没有核对单(老版本后端 / 没取到基线)· 已触发到账核对(旧文案兜底)
  • 同一句话进 ckBadgeTip;徽标颜色、doneToday、「N 个没签」计数一概不读 arrival。
  • already(平台侧已签,不是我们领的)不核对 —— 没有「到账」可确认;同日早先 claim 留下的核对单保留。

边界

情况处理
发放延迟claim 当轮 pending,后续每轮取数继续核(最长到跨日)。
消耗抵消+100 与 −80 同轮 → delta=+20 仍 confirmed;+100 与 −120 同轮 → pending/unseen,不误报。
充值混入一期接受:文案永远带「按余额推算」;基线通常只有几分钟旧,窗口很小。
换账号签到渠道是会话/本机登录态,取数侧基本不落指纹(fp 分段帮不上忙),靠周期日截止 + 文案标注兜底;误报后果仅一句展示文案。
渠道隐藏 / 开关关闭settle_arrivals 只处理 enabled 且未隐藏的渠道,与 run_checkin 闸门同口径。
claim 后没取到基线不核对,arrival 留空,界面落回旧文案。

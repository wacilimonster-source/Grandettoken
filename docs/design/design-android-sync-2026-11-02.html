结论：方向合理，修正协议与授权边界后再进入 M0保留“桌面取数 → 白名单 DTO → 加密 Gist → 手机只读”的架构。业务决策已确认：匿名慢速、登录提速、统一同步平台标签、电脑同步历史、隐藏仅影响当前来源，签到汇总纳入开发计划。原型为交互示意，授权页与协议尚未实现。本文验收项均为待验证，未勾选不代表测试失败。

已由用户确认

  • 始终按平台合并，只显示最新一条，不求和。不同账号也按此规则，接受其中一个账号不展示；改显示名不会拆行。
  • 多电脑限定同一个 GitHub 账号。每台电脑单独取得该账号授权；同步码不授予 Gist 写权限，不复制其他电脑的 OAuth 令牌。
  • 手机增加 GitHub 登录以支持频繁刷新。保留匿名慢速模式（前台默认 5 分钟），登录可选（前台默认 60 秒）。

手机 GitHub 登录流程（方案）

  1. 先扫描同步码。本地严格校验长度、版本、CRC 后取数，至少验证一份有效密文才原子保存新组；配对失败保留原组。空组不能证明密钥正确，桌面必须先发布可验证快照。
  2. 展示提速入口。配对完成页：“登录 GitHub，开启每分钟刷新”；次按钮“暂不登录，5 分钟刷新”。设置 → GitHub 连接提供相同入口。登录账号与同步组分开，手机可使用不同于电脑的 GitHub 账号。
  3. 使用 Device Flow。单独注册手机专用 OAuth App 并开启 device flow；APK 只包含公开 client_id，不包含 client_secret。POST https://github.com/login/device/code，不请求 gist、repo、user、邮箱等 scope；只读取公开可访问的 Gist。必须在 M0 用真实 Secret Gist 验证无 scope 的授权读取和额度头。
  4. 打开官方授权页。App 展示 GitHub 返回的 user_code、倒计时、“复制授权码并打开 GitHub”与“取消”。通过系统浏览器 / Custom Tab 打开 https://github.com/login/device，不在 App 内收集 GitHub 密码。说明复制的授权码不是同步码，二者不可混淆。
  5. 等待授权。按返回 interval 轮询 token endpoint；authorization_pending 继续，slow_down 增加间隔，access_denied / expired_token 停止并提供重试。离开页面取消本次流程；恢复页面后按过期时间处理，禁止无界后台轮询。
  6. 验证并启用。GET /user 显示所连 GitHub 账号，再以 Bearer token 读取已配对 Gist，检查 X-RateLimit-*。全部成功后加密保存 token；前台默认 60 秒轮询（可选 1 / 2 / 5 分钟），后台仍为 WorkManager 15 / 30 / 60 分钟尽力调度，不承诺准点。
  7. 异常与退出。401 停止使用 token，保留缓存，提示重新登录并降为匿名 5 分钟策略；403 不一律视为限流，区分权限与额度；429 按限流处理。退出登录删除本机 token、取消旧任务并重新调度匿名任务，不退出同步组；提供 GitHub 官方应用授权管理入口供撤销授权。退出同步组清除该组密钥、缓存、ETag 和序号水位，不自动撤销 GitHub 登录。
手机专用 OAuth App 不与桌面写入授权共用，避免历史授权 scope 被扩大复用；校验实际返回 scope，发现非预期写权限则不保存并引导撤销授权。这里的“只读”来自最小 OAuth 权限和手机请求路径，而 AES 共享密钥本身不区分读写者；若持码者另有中继写权限，仍可能伪造有效密文。

必须落实的技术优化

  1. 稳定平台标识。增加 platformId 作为合并键，id 仅表示本机渠道。内置平台用协议枚举；现有 custom-1/custom-2 是本机编号，绝不能跨机当平台键。自定义平台使用用户选择的统一“同步平台标签”确定 platformId；同标签合并，改显示名不改变身份，不上传 URL 或凭据指纹。按有效 updatedAt 排序；相同时间按 source 字典序确定性选取整条记录，禁止跨来源拼接余额与消耗。
  2. 区分心跳、观测和读取。at 表示发布，updatedAt 表示最后成功取数，receivedAt 表示手机读取；304 不能刷新观测时间。stale = 上游失败或观测超时，与手机网络失败分开；组里一条新鲜渠道不能掩盖其他陈旧渠道。时效阈值依据取数周期与协议容差，不能随手机前后台刷新周期变化。
  3. 防覆盖与回环。只 PATCH 本来源文件，不整份回写 files，不回发组内合并结果。source 使用随机 128 位标识；复制安装目录需重新生成 source。发布与序号持久化串行；先持久化序号及本次密文再发送，超时重试使用原密文。seq 更小拒绝，相同 seq 且相同密文视为幂等，相同 seq 不同密文报冲突。新安装无历史水位，不能承诺识别所有回放。
  4. 补齐加密契约。M0 固定 HKDF salt、UTF-8 info、AAD 字节编码、base64url 无填充规则、16 字节 GCM tag。建议按 relayId + source + keyEpoch 派生来源子密钥，96 位 nonce 用系统 CSPRNG；外壳版本参与认证。keyEpoch 初始 0；新组重置而不循环递增一字节。golden fixtures 覆盖错误密钥、AAD、截断和篡改。
  5. 明确本地安全存储。Android Keystore 保存本机包装密钥，以它加密同步主密钥、OAuth token 与缓存，密文进应用私有目录；主密钥做 HKDF 时只短暂进入内存。Keystore 不作为任意字节保险箱。敏感文件排除备份/迁移，密钥失效时重新配对；退出组取消 WorkManager 并清除缓存。诊断禁止包含 token、同步码、Authorization、余额与原始响应。
  6. 修正轮换语义。创建新 Gist + 新主密钥，先发布并验证，再切换本机；所有其他电脑和手机重新加入。失败保留原配置。旧中继停止写入；删除旧中继单独确认。无法远程清除旧手机缓存，也无法保证旧手机知道新组存在。新组创建后若其他电脑仍写旧组，必须提示迁移未完成。
  7. 补齐单位与统计口径。渠道必须携带 unit/currency；金额精度统一十进制定点字符串，缺失为 null，拒绝 NaN/Infinity。按币种分组汇总，积分和配额不参与金额合计。若展示折合 CNY，必须另定汇率来源、时间与缺失规则。day/week/month 携带 periodStart/periodEnd/timeZone；跨时区不同窗口不得直接相加。
  8. 电脑同步历史（已确认）。桌面随快照发布最近 7 天脱敏聚合历史，新手机首次加入即可读取已有历史。按 platformId 和统计窗口确定性去重，同平台同窗口取最新修订，不跨来源求和或拼接成虚假连续记录；缺口保留 null，详情显示“历史不足”。历史与余额使用相同加密、白名单和资源限制，不上传原始请求、账号或逐笔敏感记录。
  9. 防截断和资源耗尽。检查 Gist 顶层与文件级 truncated；限制来源文件数、单文件和响应总字节、数组长度。超限显示不完整，不更新为完整视图；只处理匹配命名规则的文件。若回退 raw_url，只允许经验证的 HTTPS GitHub 内容域名，限制重定向且不转发 Authorization。404 表示不存在或不可访问，不能断言已删除。
  10. 自由文本仍可能泄密。显示名也可能含邮箱、URL 或密钥，白名单结构无法自动保证“零泄露”。同步显示名需单独净化、限制长度、默认内置名称；导出预览和哨兵泄露测试同时覆盖自由文本。禁止直接序列化 ChannelView，其含 auth_label、error、extra 等敏感字段。

本轮确认的业务决策

  • 匿名模式保留。扫码即可使用，前台默认 5 分钟；可选登录 GitHub 提速至默认 60 秒，后台均为 15 / 30 / 60 分钟尽力调度。
  • 统一同步平台标签。自定义渠道在桌面选择统一标签映射为 platformId；同标签始终合并，修改显示名不改变合并身份。
  • 历史由电脑同步。发布最近 7 天脱敏聚合历史，手机不以加入时间作为历史起点；桌面历史不足时明确显示缺口。
  • 隐藏/取消发布只影响当前电脑。当前来源的新完整快照移除对应渠道及历史，不下发全组隐藏标记；其他来源仍可发布、展示。旧缓存需保留缺失/陈旧提示，不能声称远程删除所有历史副本。
  • 签到汇总必须列入开发计划。覆盖桌面明细发布、跨来源去重、手机汇总、跨日重置和异常验收。不得取任意最新来源的 total/done 冒充全组统计；平台多账号如何计数及“已完成/未知/不支持”的最终口径在 M0 设计任务中细化，开发前确认，不自行认定为按平台一项。

01产品定位它解决什么问题，不解决什么问题

桌面端已经能回答“哪个渠道快没钱了”。手机端的价值不是把桌面面板缩小，而是离开电脑时仍然能看一眼：出门前确认余额、收到“跌破红线”提醒后点开看是哪一家、在另一台电脑上确认家里那台机器是否还在正常取数。

核心用户故事

  • 我在外面，想知道同步组里所有电脑的 DeepSeek 还剩多少钱。
  • 我有两台电脑，想把它们的数据合成一份来看。
  • 手机收到“余额跌破 ¥10”，点开能看到是哪个渠道、什么时候的数据。

明确不做

  • 手机不能改配置、不能填密钥、不能签到。
  • 不做设备列表、设备切换或“数据来自哪台电脑”。
  • 不做实时推送（GitHub 中转本身没有推送通道）。
  • 不做账号体系、不做多人共享同一个同步码。
  • 不在手机上保存 GitHub PAT。

成功标准

  • 扫码后 5 秒内看到同步组的合并数据。
  • gist 里搜不到任何密钥、Cookie、邮箱或本机路径。
  • 组内某台电脑休眠/断网时，手机明确显示“陈旧”，绝不显示“余额 0”。
  • 手机丢失后，电脑端轮换同步码即可让旧码失效。

一个同步码 = 一个同步组 组内没有“主设备”或“从设备”。每台电脑都是写入者：只写自己的 gt_<source>.json，因此不会互相覆盖；同时它也会读取组内全部文件，用于组状态与可选的合并预览。手机只是消费者：读取全部文件、解密、按渠道合并成一份列表。手机界面不出现设备名，也没有设备切换。

关键事实：Secret Gist 可以匿名读取 GitHub 的 secret gist 不会出现在发现页或你的主页列表里，但知道 gist ID 的人可以直接通过 API 读取它。不要把 gist ID 的长度当作官方保证的熵；它只是定位符，不是安全密钥。我们再把内容整体加密，于是“知道 ID”最多只能拿到一段密文。这就是手机端不需要账号的原因。

电脑端要做的事

  • 点击 “连接 GitHub”，通过系统浏览器在 GitHub 官方页面授权，仅申请 gist scope；不要求用户创建或填写 PAT。
  • 浏览器授权取得的 OAuth token 存 Windows 凭据管理器，服务名建议 TokenScope:sync。
  • 首次创建 secret gist；之后每台电脑只 PATCH 自己的文件。
  • 读取组内全部文件，用于组状态与可选的合并预览。
  • 发布间隔默认 1 分钟；只从本机取数生成 DTO，禁止把合并结果再次发布。哈希不含 seq/at/nonce；最长 15 分钟发布一次心跳（技术建议），渠道 updatedAt 不随心跳变化。

手机端要做的事

  • 只保存同步码里的 32 字节密钥（Android Keystore）。
  • GET gist → 解密全部文件 → 按渠道合并 → 本地缓存。
  • 匿名前台默认 5 分钟、登录默认 60 秒；后台 15 分钟起。
  • 遇到 403 限流自动退避，不弹错误轰炸。

2.2 需要如实说明的代价

  • 不是实时。最快也就是 60 秒一次，后台 15 分钟。余额监控够用，但别期待“秒级”。
  • 同一渠道会合并成一条。如果两台电脑配置了同一个渠道，手机取 updatedAt 最新的一条；如果两台电脑配的是不同账号，也只会显示最新的那个。v1 不按设备或账号拆行；自定义平台按统一同步平台标签合并，改显示名不拆行。
  • Secret Gist 不是私有仓库。知道 ID 的人能读到密文；gist API 响应里可能带所有者登录名。介意的话，只能换成私有仓库 + 手机令牌，但那就不满足“手机免账号”了。
  • GitHub 可能被墙或限流。这是可选功能，默认关闭；开启时明确告知会向 github.com 发起请求。
  • Gist API 单文件内容超过 1 MB 可能截断。这不是存储上限；客户端必须检查文件级与列表级 truncated，不能把截断内容当作完整快照。

4.3 桌面端浏览器授权（替代手填 PAT）

已确认的产品流程桌面与手机均通过 GitHub 官方浏览器页面授权；桌面必须授权才能发布，手机保留匿名慢速。v1 桌面采用与手机一致的 Device Flow，不提供手填 PAT 入口。授权得到的 OAuth token 是内部凭据，不作为用户填写项。
  1. 连接。设置 → 同步 → GitHub 连接，未连接时显示“连接 GitHub”，说明“用于发布加密同步数据”。用户点击后创建本次授权请求；浏览器未授权前不创建 Gist、不上传数据。仅开启同步开关不直接打开浏览器。
  2. 显示授权码。使用独立的桌面 OAuth App（维护者注册并开启 Device Flow），请求 GitHub device code，scope 仅为 gist。桌面程序只内置公开 client_id，不内置 client_secret；与手机只读 OAuth App 分离。弹层显示 user_code、有效期、“复制授权码并打开 GitHub”、“重新打开授权页”和“取消”；同步码与此次短期授权码明确区分。
  3. 官方浏览器授权。用户主动点击后复制 user_code 并通过系统默认浏览器打开 https://github.com/login/device；若复制失败仍显示可手动输入的授权码。程序不收集 GitHub 密码或二次验证码，不使用内嵌网页登录。提示只输入本机刚发起的授权码，并核对官方授权页上的应用名称和 gist 权限。
  4. 等待与取消。按响应 interval 轮询 token endpoint，authorization_pending 继续等待，slow_down 按新的 interval 降速；拒绝、授权码过期、device_flow_disabled、网络失败有独立状态与重试入口。只允许一个在途授权；取消/关闭弹层/退出程序停止轮询并丢弃 device_code，重试申请新码。若取消后收到迟到 token，不保存、不启用同步。倒计时采用 GitHub expires_in，不固定写死。
  5. 验证账号与权限。取得 token 后 GET /user 获取账号 ID/login，并检查实际授权 scope；缺 gist 或出现非预期额外 scope 时不完成连接，引导用户在 GitHub 撤销旧授权后重试。连接卡显示“已连接 @账号 · gist 权限”，便于确认浏览器登录了哪个账号；账号信息只用于本机授权状态，不进入同步载荷或通用导出诊断。
  6. 创建或加入。验证成功且安全保存凭据后，再让用户选择“创建同步组”或“输入同步码加入”。创建使用 public=false；加入时校验密文和 Gist owner.id，必须等于当前授权账号 ID。账号不一致则保留原组，提示“请使用创建该同步组的 GitHub 账号重新授权”；不通过试写别人的 Gist 检测权限，不自动另建空组冒充加入成功。
  7. 保存与发布。token 由 Rust 端直接写入 Windows 凭据管理器，不经过前端 JS、URL、日志、配置或剪贴板；前端仅接收状态、账号与错误码。先完成凭据保存及本地组配置原子提交，再启动发布；保存失败提示本机安全存储不可用，不报告“连接成功”。每台电脑独立授权同一 GitHub 账号，手机登录仍可使用其他账号。

gist scope 可读写授权账号的 Gist，不能限制为单个同步组文件。授权前应如实说明这一权限范围；客户端只操作本同步功能创建或明确加入的 Gist。Device Flow 沿用手机方案；GitHub 对普通原生客户端更推荐 PKCE，当前选择为统一无回调交互，M0 应验证流程并记录该取舍，未来可保持界面不变迁移至 PKCE。

重新授权、断开与远端撤销

  • 重新授权：保留当前连接，暂停发布，在临时授权上下文中验证新 token；成功后原子替换。失败/取消恢复原连接。已有组只接受相同 GitHub 账号，切换账号需先明确退出当前组，不删除旧中继。
  • 失效：401 停止请求，显示“GitHub 授权已失效，请重新授权”，保留组信息和本机数据，不循环登录。若 token 返回 expires_in，保存到期时间并提前提示；v1 不申请 offline_access、不依赖自动刷新 token，过期走重新授权。403 区分权限缺失和限流，429 按响应头退避。
  • 断开连接：用户确认后停止本机读写任务、清除本机 OAuth 凭据与登录状态；保留组信息和同步密钥以便同账号重新授权，不删除 Gist，也不影响其他电脑和手机。单独的“退出同步组”才删除本机组密钥。界面明确区分暂停同步、断开连接和退出组。
  • 撤销远端授权：提供 GitHub 官方应用授权管理页入口；说明撤销桌面 OAuth App 授权可能使其他已授权电脑也失效。普通本机断开不自动执行全局撤销，不在客户端内置 client_secret 调用管理接口。

开发与验收补充

M0 完成独立桌面 OAuth App 注册、Device Flow 与 gist scope 实测、同账号多电脑读写及不同账号拒绝加入；M1 提供 Rust 端授权会话、凭据管理器与任务暂停/恢复；M2 完成授权弹层、账号展示、重新授权和断开。验收覆盖浏览器未打开、复制失败、授权拒绝/过期/slow_down、取消迟到响应、重复点击、错误账号、权限不足、凭据保存失败、401、403/429，以及断开不影响其他节点。所有 token/device_code 不进入前端状态、日志或诊断。

11验收标准能上线前必须全部满足

  • 桌面浏览器授权：无需 PAT 输入；同账号授权后创建/加入，取消/失败不破坏原连接，token 不进入前端或日志。
  • 手机免账号：全新安装、未登录 GitHub，仅凭同步码即可看到同步组与余额。
  • 零密钥泄露：gist 中所有文件解密后均不包含 API Key、Cookie、邮箱、Windows 路径；自动化测试覆盖。
  • 多电脑：3 台电脑各自写入，互不覆盖；手机展示合并视图，同一渠道取最新，不跨数据源求和。
  • 不区分设备：手机界面没有设备列表、设备名或设备切换；只有一份合并面板。
  • 多手机：同一同步码可被多台手机读取；没有服务端注册状态。
  • 失败不归零：取数失败、离线、限流、解密失败都有明确状态，数字不会被渲染成 0。
  • 轮换有效：新组使用新密钥；旧码不能解密新数据。旧组可能仍可读到历史，不能承诺旧手机识别轮换。
  • 请求预算：匿名 5 分钟、登录 60 秒，后台至少 15 分钟；验证共享预算和响应头退避，不承诺连续刷新绝不限流。
  • 无障碍：核心流程仅用 TalkBack 可完成扫码/输入、查看合并面板、打开详情。
  • 无敏感诊断：导出的诊断文本只有时间、状态、错误码与文件大小。
  • 桌面端无回归：关闭同步时，现有取数、面板、胶囊、托盘行为不变。
  • 历史同步：新手机可读取电脑已有近 7 天聚合历史；跨来源去重，缺口不补 0，取消发布仅影响本来源。
  • 签到汇总：按 M0 确认口径验证跨来源去重、跨日重置、失败/未知状态，不相加各来源总数。
  • App 更新：每天自动检查、用户点击下载、系统确认安装、稳定版可跳过；签名错误阻止安装，升级保留数据。详见第 14 节。

13已定决策与剩余风险这版设计的核心变化，以及还没解决的取舍

已定

  • 数据模型：同一个同步码就是一个同步组；电脑读写，手机只读。
  • 界面：手机不区分设备，只有一份合并面板；没有设备列表。
  • 中继：Secret Gist，内容端到端加密。
  • 手机：匿名慢速可用，GitHub 可选登录提速。
  • 刷新：前台轮询；后台 15/30/60 分钟可选。
  • 开源：同仓库 monorepo，Android 顶层工程，协议放 contract/。

剩余风险与处理

  • 同渠道不同账号：合并时只保留最新的一条，可能少显示一个账号。这是已确认取舍；改显示名不改变合并身份。
  • Secret Gist 元数据：API 响应可能带所有者登录名。可接受则用主账号；介意则后续增加“中继专用小号”引导。
  • 未登录限额：60 次/小时。匿名 304 仍纳入预算；登录后可每 60 秒读取，必须带 ETag 并处理 403/429。
  • 后台限制：Android 15 分钟是硬下限；不做常驻前台服务，避免耗电与通知栏污染。
  • 同步码泄露：当作密码处理；电脑端提供轮换与删除中继。

14Android 检查更新客户端已实现 · 签名双版本升级待验收

用户已确认通过本项目 GitHub Releases 分发 APK；默认每天自动检查一次，只提示；用户点击后下载并交给 Android 系统确认安装。v1 仅稳定版，可稍后处理或跳过，不强制更新。匿名用户与登录用户均可检查更新，无需先加入同步组。

14.1 入口与检查策略

  • 设置 → 数据与关于：显示当前 versionName / versionCode、“检查更新”、“自动检查更新”开关（默认开）、最近成功检查时间和更新状态。未配对空状态也提供“关于与更新”入口。
  • 启动或回到前台时，若距离上次自动尝试已满 24 小时，异步检查一次；检查不阻塞扫码、面板和同步。v1 不增加专门的后台唤醒：App 长期未打开时，下次打开再检查，不承诺每天固定时刻运行。
  • 每次自动尝试先记录时间，失败也节流，避免反复打开触发请求风暴；另存最近成功检查时间。手动检查不受 24 小时限制，但同一检查在途复用、连续点击节流，并遵守服务端退避截止时间。自动关闭后仍可手动检查。
  • 发现新版本在设置入口显示更新标记，面板给非阻断提示，不自动弹全屏、不自动下载。自动失败保持安静；手动失败显示明确原因与重试入口，不能报“已是最新”。
  • 更新卡包含版本、发布日期、APK 大小、更新说明、“下载更新”、“稍后”、“跳过此版本”。跳过按 versionCode 保存，仅抑制该版本自动提醒，更高版本重新提示；手动检查仍可看到被跳过的版本并主动更新。

14.2 完整交互流程

  1. 检查。空闲 → 检查中 → 已是最新 / 有更新 / 当前系统不支持 / 检查失败。仅 versionCode 大于本机且满足系统版本、架构和稳定渠道的版本可推荐；相同版本不重复安装，不提供降级。
  2. 下载。点击“下载更新”才联网获取 APK；移动数据下显示大小并确认“使用移动数据下载”。展示已下载字节、总大小、进度和“取消”；取消后可重试，不触发安装。下载与校验时继续显示已有面板。
  3. 验证。下载至应用管理的临时目录，先核对受信发布清单与文件 SHA-256/大小，再验证 APK 签名、applicationId、versionCode、minSdk 和兼容架构；禁止安装任意 APK 或依赖文件扩展名判断。验证失败删除产物，显示错误码和重新下载入口。
  4. 安装授权。校验通过后显示“安装更新”。点击后检查 canRequestPackageInstalls()；尚未允许时解释“需要允许 Grandettoken 安装此更新”，由用户选择进入系统的“允许来自此来源的应用”设置。返回后重新检查，未授权则保留“待安装”，不循环拉起权限页面。
  5. 系统安装。通过 FileProvider content URI 和临时只读授权调用系统安装器，不暴露 file:// 路径，不静默安装。系统确认界面由用户完成；拒绝、取消、存储不足、签名不匹配、系统策略阻止时保留旧版可用，给出对应说明。不得建议卸载旧版来绕过签名错误。
  6. 完成确认。交给安装器只代表“已交给系统”，不能提示安装成功。下次启动核对实际安装 versionCode，确认成功后清理旧 APK、更新提示和过期跳过记录；保留同步组、密钥、GitHub 登录和通知设置。安装前完成在途本地事务，数据库迁移必须支持从上一个发布版本直接升级。

14.3 Android 独立发布清单

桌面现有 latest.json 由 Tauri 使用，Android 不复用其格式，也不使用仓库 /releases/latest 判定手机版本。建议采用独立固定发布标签 android-stable，其资源 android-latest.json 定位最新 Android 稳定版；APK 放在不可变的 android-vX.Y.Z 发布下。标签和清单需在开发时新增，当前尚不存在，不能将建议 URL 当作已可用服务。

字段约束
schemaVersion / channel清单结构版本；v1 只接受 stable，未知主版本停止解析并提示手动查看官方发布页
applicationId / versionName / versionCode包名固定；versionName 供展示，versionCode 全局严格递增并用于比较，不按字符串排序
publishedAt / notes / releasePageUTC 时间；更新说明按纯文本渲染并限制长度；发布页限定本项目官方 Releases
minSdk / artifacts[]每个产物声明 ABI、sizeBytes、sha256、downloadUrl；首版优先 universal APK，避免选错架构；缺匹配产物显示不兼容
keyId / payload / signature签名外壳：payload 为 base64url 编码的原始 UTF-8 JSON 字节，signature 为对解码后原始字节的 Ed25519 签名；校验通过后再解析，不对重新序列化 JSON 验签

内置独立的 Android 更新清单验签公钥；APK 使用长期保管的 Android release 签名密钥，与桌面 Tauri 密钥分开。SHA-256 只能证明文件与清单一致，不能替代 APK 签名与受信清单验签。首版固定签名证书，不设计自动换签；未来轮换需单独设计兼容的签名沿革和公钥过渡。

14.4 网络、安全与异常

  • 清单和安装包均从官方 HTTPS 入口下载，限制清单大小、APK 总大小、超时及重定向次数。GitHub 资源会跳转至资源域名，客户端必须校验官方资源域名白名单；不把 OAuth token、同步码或 Authorization 传给发布下载链路及重定向目标。
  • 更新功能不消耗 Gist 同步调度预算；若实现需要调用 GitHub REST API，则必须计入共享账号/IP 限额。使用 ETag 和本地缓存，304 只复用已验证清单；匿名 304 不假设免主限额。403/429 按响应头退避。
  • 进程被结束、网络切换或超时后可重新下载；v1 不要求断点续传。持久化任务标识和下载状态，重入时核对文件完整性，不产生多个下载。临时文件失败/取消后清理，已验证待安装 APK 最长保留 7 天，重试安装前重新校验。
  • 清单 404、缺产物、签名不符、未知版本、网络失败均视为检查/下载失败，不报告“已是最新”；保留最近可信状态。已知更新无法下载时可打开官方发布页，但不自动切换未验证镜像。
  • 普通更新不强制；遇到同步协议主版本不兼容时保留缓存，说明无法展示的部分并给更新入口，不清空数据、不阻断其余可用功能。发行人撤回损坏版本时发布更高 versionCode 的修复包，不自动降级。
  • 诊断仅记录检查时间、阶段、版本号与规范错误码，不含完整下载查询串、OAuth token、同步码或原始响应。

14.5 发布流程与开发任务

沿用本项目 GitHub Releases 托管方式，另建 Android 打包/签名/清单发布流程。发布顺序：构建签名 APK → 验证证书与版本 → 上传不可变版本资源 → 匿名验证资源可下载 → 生成并签名更新清单 → 最后更新 android-stable 指针。清单切换时若资源短暂缺失，客户端保留旧可信状态并允许重试；不得覆盖已发布同 versionCode 的 APK。Android 发布不能改变桌面 latest.json，桌面发布也不能覆盖 Android 指针。

  • M0：固定 applicationId、versionCode 规则、清单 schema、验签向量、官方资源域名和发布指针；验证与桌面更新发现互不干扰。
  • M3：关于与更新入口、自动/手动检查、更新卡、跳过版本、下载进度和取消、安装权限引导、系统安装器交接。
  • M5：长期签名密钥及离线备份、发布流程、真机覆盖升级、数据库迁移、下载清理和异常验收。最终里程碑完成前必须具备可用的检查更新闭环。

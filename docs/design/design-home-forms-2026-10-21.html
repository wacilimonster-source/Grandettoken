0. 摘要

一句话结论：现在的问题不是"形态不够"，而是四种形态各自算各自的真相。

面板里已经有一套很完整的"失败保留快照 + 标注更新时间"的纪律（.rhint.stale）， 但这套纪律只存在于面板：切到紧凑条，那行提示被 CSS 直接 display:none； 切到胶囊，连位置都没有；切到吸附条，只剩一块颜色。 于是产品花了最大力气做的"不撒谎"，在用户最常看的两种形态里全部失效。

0.1 四条结论

  1. 形态数量是对的，分工是错的。四种形态现在更像"同一个东西的四种尺寸"。应该改成四个问题： 面板 = 哪里出事了；紧凑条 = 最紧的是谁；胶囊 = 还能不能干活；吸附条 = 现在要不要点开。一个形态只回答一个问题。
  2. 最大的漏洞是状态，不是布局。"新鲜 / 陈旧 / 鉴权失效 / 取数失败 / 未配置 / 已用尽 / 限流"七种状态，目前散落在 toneOf、dotCls、valid、limited、updatedAt 五处，各自解释。 结果是同一个渠道在四种形态里可能给出三种结论。
  3. 金额型渠道的"紧迫度"根本没算。remainRatio() 没有分母就返回 null， toneOf() 把它当 ok，胶囊自动挑人时 ?? 2 把它排到最后。 一个只剩 ¥0.03 的充值型渠道，会永远显示绿色、永远不会被胶囊选中。对一个"余额挂件"，这是核心场景失效。
  4. 我们有一个别人都没有的东西，却放在最看不见的地方。扫了 25+ 个 GitHub 同类项目， 没有任何一个做每日签到。而本产品的签到徽标只在面板的行里、和一条"有未签才出现"的提示条里； 紧凑条里聚合提示条被隐藏、只剩芯片上一枚 8.5px 的小徽标；胶囊里则完全没有。全部签完时提示条直接消失——"完成"和"坏了"长得一样。
本设计的主张：把"紧迫度"从一个散落在四个渲染函数里的临时判断，升级为后端算好的一条统一视图模型 （state / tone / urgency / bindingWindow / eta / age），前端四种形态只负责"画"，不再负责"判断"。 这跟项目里已经用过的两条纪律是同一个方向：签到的 doneToday 由后端算（前端零日期运算）、 详细日志开关由后端持有（前端不自己存）。同源，才不会各说各话。

3.2 七条可以直接抄的规律

R1 · 一个"最紧"，比九个"都还行"有用。
need-more-tokens 的菜单栏只显示最接近用完的那个；LLM-Usage-Desktop-Widget 的顶栏是 Claude 99% Codex 13%；AIQuotaBar 的顶卡永远是最危险的那个。 理由很朴素：380px 宽的一条，用户只给 200ms。能回答"现在能不能干活"的，只有一个数。
→ 落到本产品：胶囊与吸附条都只回答"最紧的是谁"，但必须按紧迫度挑，不是按百分比挑。
R2 · 陈旧要"保留原值 + 标记"，不能归零，也不能留白。
LLM-Usage-Desktop-Widget 的两级写法最精确：有缓存就 ? stale ⚠ 上次的数，没缓存才只报错。 KimiCodeBar 的做法是"照常展示最近一次成功的数据，顶部出现一条提示横幅"。 oh-myusage 把"缓存回退"单独标出来。
→ 本产品面板里已经有这个纪律（.rhint.stale），但折叠形态里全丢了。这是本设计的第一优先级。
R3 · 失败是"一个 muted 的破折号"，不是"整块变灰"。
LLM-Usage-Desktop-Widget 的紧凑行里，失败的供应商就是 —（muted），布局一点不变； pane 明确写"查询失败如实显示为错误状态，不伪装成灰色的未知额度"。 Grafana 把 No data / stale / N/A 分成三种。
→ 本产品现在把"未配置 / 失联 / 没数"都压成灰点和「——」，语义糊在一起。
R4 · 颜色必须配形状或文字，不能单独承重。
ai-dock 直接给了四种折叠样式当逃生门；claude-code-usage-monitor 用电池这个全世界都懂的隐喻； Uptime Kuma 的四个状态各有自己的图形。
→ 本产品的状态点已经有"空心环 / 斜杠"两个形状变体（做得对），但 ok / warn / bad 仍然只靠色相区分。
R5 · 长窗打满时，短窗必须镜像，否则界面在撒谎。
pane v0.8.5 的原话：周/月额度打满时，短周期环直接镜像墙状态（100% + 刷新倒计时）， 消除"5 小时环还绿着，但请求全被拒"的假象。
→ 这是本产品最严重的一个正确性问题，见 D03。
R6 · 贴边形态的默认是"一条缝"，不是"一个小窗"。
Pulse 闲置时折成 sliver；kimi-plan-monitor 拖到边缘收成细边、鼠标靠近再展开； ai-dock 自动隐藏成一条 thin strip；Developer-Island 缩成 5px 的 notch。 四个项目、四种实现，结论一致。
→ 本产品的 8px 竖条方向是对的，但信息量为零，见 D10。
R7 · 用户要的从来不是"更多数据"，是"更少但更准"。
openusage 那条 issue 被作者改了标题，原话是 "tui interface is insanely complicated … in reality I only need about 2 numbers per provider"。 一个 624 次提交、支持 37 个供应商的项目，最后被用户要求退回两个数。
→ 本产品每行九个元素（含折叠行里的第三段），正好站在用户诉求的反面。

3.4 真正的空白区：签到

扫完 25+ 个项目，没有一个是做每日签到的。

它们全都在解决"我用了多少 / 还剩多少"，这是被动读取。 签到是另一件事：它是用户每天主动做一次的动作，有完成态、有重置时间、有连续天数、有"今天还没做"的焦虑。 它需要的恰好是一个一直在屏幕上的东西——也就是本产品。

而本产品已经有了：Trae / WorkBuddy / Qoder 的自动签到、四态徽标、退避、平台侧已签的区分、后端算好的 doneToday。 这是唯一一个别人抄不走的差异点。但它现在被放在了最看不见的地方： 面板的行内、和一条"有未签才出现"的提示条；紧凑条里聚合提示被隐藏、只剩行内小徽标，胶囊里完全没有；全部签完时提示条消失。
设计上的直接后果：签到必须在四种形态里都有位置，而且要有一个"全部完成"的状态。 不是加一个页面，是加一个永远存在的进度：2/3。 它同时是提醒（还有 1 个）和奖励（已经 2 个），而且是这个产品每天被打开一次的理由。

4. 问题清单

严重度口径：P0 会让用户读到错的结论，或让核心场景失效； P1 每天都会遇到、每次都要多一步； P2 打磨；P3 可选。 每条都标了证据位置，方便直接核对。

P0D01 "陈旧"只在面板里存在，另外三种形态会把旧数字当成新数字
证据
面板每行都有 .rhint（app.js:597-600），但紧凑条把它 display:none 掉 （styles.css:502）；胶囊没有任何时间信息；吸附条只有一个颜色（renderDock）。
影响
取数失败后，同一份快照在面板里写着"12 分钟前的成功快照"，切到紧凑条/胶囊就变成一个看起来很正常的数字。 产品花了最大力气做的"失败不撒谎"，在用户最常看的两种形态里全部失效。
判据
把网络断开 3 分钟，然后在四种形态里各看一眼：能不能分辨"这是旧的"。现在只有面板能。
P0D02 金额型渠道算不出紧迫度，于是永远被当成"健康"
证据
remainRatio() 在没有 claim.amount 时返回 null （app.js:192-205）；toneOf() 拿到 null 直接返回 "ok"（:253-254）； sortChannels() 把它丢进 4000 桶（:333-334）； 胶囊自动挑人时 (remainRatio(a) ?? 2)（:1204）——2 比任何真实比例都大，等于排到最后。
影响
一个只剩 ¥0.03 的充值型渠道：绿点、没有进度条、排在还剩 ¥88 的渠道后面、胶囊永远不选它。 这是一个"余额挂件"在余额这件事上的核心失效。
判据
造一个 remaining = 0.03、无 claim 的渠道，它必须是胶囊的首选，且不能是绿色。
P0D03 短窗限流了，大数字还在报长窗的余量——界面在撒谎
证据
大数字固定取 mainWindow(c)（后端用 main 标记的那个窗，OpenCode 是"周期"）， remainRatio() 也取它；c.limited 只影响状态点（dotCls，:272）。 三个窗口各自的红色只画在展开区的迷你条里。
影响
5 小时窗已经 0%（请求被拒），面板大数字仍是"周期剩 80%"，紧凑条与胶囊也只显示 80%。 用户看到的是一个绿色的 80%，然后所有请求失败。这是最伤信任的一类 bug。
判据
任一窗口 status = rate-limited 时，四种形态的主数字都必须变成那个窗口的 0%，并带"限流 · 2h 后恢复"。
P1D04 最贵的一条横带，回答的是次要问题
证据
renderSummary() 三格：今日 / 本周 / 本月消耗（app.js:376-380）。整条 55px， 占内容高的 10%。"总余额"从来没有作为汇总出现过。
影响
用户打开面板的第一眼是三个"花掉的钱"，还得自己往下扫九行才知道"还剩多少、哪家快没了"。 而"花了多少"是可以在底栏用一行字说清的东西。
P1D05 "完全展开"其实只展开了一个角：8 个可见渠道只看得到 3 个
证据
2.3 节：原按样式表推算单行 84px、一屏 4.7 行；真机测量单行 101–166px、列表可视高 431px， 一屏只有 3 行（§2.6）。首行展开时（展开体高 482px）其余渠道全部被挤出屏外。
影响
排序不只是"顺序"，它决定了谁有资格出现在第一屏。而现在的排序恰好把最危险的那类（无分母的金额）放到最后。
P1D06 九行长得一模一样，没有"需要处理 / 其余"的分层
证据
所有行共用 .row；每行 9 个元素（含第三段 useHtml）；没有分组、没有分隔、没有"紧急行更大"。 排序用 4000 / 5000 / 9999 三个魔法数把百分比、金额、积分、失败、未配置硬塞进一条数轴（app.js:325-335）。
影响
Kimi 还剩 88%，4SAPI 还剩 24%——两行视觉重量完全相同；而只剩 ¥0.03 的那行，和它们也完全相同。 "扫一眼"这个动作在这种列表上不成立。
P1D07 紧凑条按"最宽"降级，方向反了
证据
fitCompact() 的 strip(0,1) / strip(1,2)：每次都挑当前最宽的 chip 去名字 / 舍小数 （app.js:1142-1152）；最后从尾部开始收进 +N（:1153）。
影响
最紧的渠道通常名字最长、数值最长（"Claude 8% · 2h"比"Kimi ¥88"宽），于是它第一个被去掉名字。 而降级顺序与"哪个渠道最该被看见"完全无关。
P1D08 聚合签到进度在紧凑条里消失，胶囊里连单个徽标都没有
证据
styles.css:425：body.form-compact .ckstrip, body.form-pill .ckstrip{display:none}。 紧凑条里徽标本身还在 .rhead .n 里（被压到 8.5px），但"今天还差几个"的聚合进度没了； 胶囊整个 .list 都不显示，签到为零。
影响
全赛道只有本产品有签到，而用户 80% 的时间待在紧凑条/胶囊里：紧凑条只剩芯片上一枚小 ✓（看不出总数、看不出还差谁），胶囊里完全为零。
P1D09 全部签完时，界面什么都不说
证据
ckPendingStrip() 在 pending === 0 时返回空字符串（app.js:4161-4168）。
影响
"今天全签完了"和"签到功能没开 / 读不到状态 / 坏了"，在界面上是同一种表现：什么都没有。 日常仪式没有完成反馈，就没有闭环，也就没有明天再来的理由。
P2D10 吸附条只有一色，而且在用户看不见的时候每 8 秒换一次颜色
证据
renderDock() 取 PILL.list[PILL.idx]（app.js:2256-2265），背景是一整块渐变色； 吸附态下胶囊脸被隐藏。补充条件（复核 2026-10-22）：轮播定时器里有一句 if (!document.body.className.includes("form-pill")) return（app.js:2635）—— 只有"进吸附前是胶囊形态"时索引才每 8 秒推进；面板 / 紧凑形态下吸附，那一色是冻住的。
影响
8px 宽的一条，没有身份、没有数值；颜色自己变，用户不知道它代表谁。它唯一能回答的是"有点不对劲"，而这恰好是它回答得最含糊的。
P2D11 同一个手势，在四种形态里做四件不同的事
证据
面板点行 = 展开详情；胶囊单击 = 速览；紧凑条点 chip = 展开面板；吸附条悬停 = 展开。 没有右键（全文件没有 contextmenu 监听），没有双击；键盘只有一种形态切换： Esc 在面板 ⇄ 胶囊之间来回（app.js:3868-3889），到不了紧凑条；行本身有 keyActivate 支持 Enter/Space（:2319-2332）。
影响
用户无法形成"再深一层"的肌肉记忆。每换一种形态，都要重新学一遍。
复核
2026-10-22

P2D12 颜色是阈值唯一的承重结构

P2D13 "还能用多久"已经算出来了，但只在最深的角落里出现

5. 设计原则

下面六条是这次所有取舍的依据。出现分歧时，按序号靠前的优先。

P1 · 一个形态只回答一个问题。
面板 = 哪里出事了？紧凑条 = 最紧的是谁？胶囊 = 现在还能不能干活？吸附条 = 要不要点开？
推论：任何"因为这里有地方所以也放上去"的信息，都要被删掉或降级。
P2 · 风险先行，不是数值先行。
排序、配色、大小、轮播顺序，全部按"离出事有多近"决定；百分比、金额、积分不在同一条数轴上比大小， 而是先分桶（故障 → 比例 → 绝对额 → 积分 → 健康），桶内再比。
推论：不能再出现"因为算不出比例，所以算健康"。
P3 · 状态同源：一处判定，四处渲染。
七种状态（新鲜 / 陈旧 / 鉴权 / 失败 / 未配置 / 已用尽 / 限流）由后端算一次，四种形态只负责画。 前端不再各自解释 valid / limited / updatedAt。
推论：同一个渠道在四种形态里的结论必须永远一致；不一致就是 bug，不是"形态差异"。
P4 · 颜色不单独承重。
每一种状态都必须同时有形状或文字。形状优先于颜色，因为形状在灰度下也成立。
推论：状态点从"两套形状"扩展到"每态一个形状"；吸附条的分段也用纹理区分陈旧。
P5 · 降级按重要性，不按宽度。
装不下时，先牺牲最不重要的；最紧的那一条永远保持完整（图标 + 名称 + 数值 + 时间）， 宁可让第二个渠道先失去名字。
推论：紧凑条的降级顺序必须由 urgency 决定，而不是 offsetWidth。
P6 · 不加形态，只加层次。
四种形态已经覆盖了"面积"的全部档位（560 / 46 / 46 / 8）。缺的不是第五种，是每一层里的第二层信息： 悬停、速览、分组、展开。
推论：所有新需求先问"能不能放进现有四层的某一层"，不能才考虑新形态。

6. 新方案

6.1 先有"真相"，再有四种画法

四种形态之所以会各说各话，是因为每个渲染函数都在自己解释数据： toneOf 解释一次、dotCls 解释一次、autoPick 解释一次、renderDock 又解释一次。 本设计的第一件事，是把"解释"收拢成一个视图模型，四种形态只做投影。

6.1.1 紧迫度：先分桶，再比大小

百分比、金额、积分是三种不同的量纲，不能塞进一条数轴。现在的做法是给它们各发一个魔法数 （4000 / 5000 / 9999），结果是"算不出比例的金额"和"积分"被当成同一类，而"只剩 ¥0.03"被判成健康。 改成五个桶，桶内才有可比性：

桶谁进来桶内怎么排主数字为什么
T0 需要动作 限流 · 鉴权失效 · 低于余额底线 · 取数失败 限流 → 鉴权 → 低于底线 → 失败 绑定窗的 0% / — 这四种都是"现在就得做点什么"，不是"观察一下"
T1 有比例 有配额窗口的百分比；有 claim.amount 的金额 剩余比例升序 百分比 唯一可以跨渠道直接比大小的量
T2 只有绝对额 没有分母的金额（充值型） 绝对余额升序 金额 没有分母 ≠ 健康。比不了比例，就比钱
T3 积分 kind = points 近 7 天过期占比降序，再看绝对额 分数 积分的风险是"过期"，不是"余额低"（现有逻辑，保留）
T4 其余 健康、未配置、已隐藏 自定义顺序 数值 / — 不参与"最紧"的评选
三个直接后果：
① 胶囊的"最紧"= 第一个非空桶的第一个，不再用 ?? 2 把没有比例的渠道排到最后。
② 金额也需要一条底线：设置里加一个「余额底线」（默认 ¥10）。低于它，进 T0；没有它，"¥0.03 算不算危险"永远取决于用户。
③ 桶与桶之间不比大小。"T1 里剩 90% 的渠道"和"T2 里剩 ¥500 的渠道"谁更紧，是一个没有答案的问题——所以不回答，按桶序展示。

签到是唯一一个"别人没有、我们有"的东西。它现在的问题是位置全错：
有未签时，它在面板顶部占一整条（26px），制造一次布局跳动；没有未签时，它消失； 在紧凑条里，聚合提示条被 CSS 隐藏，只剩行内一枚 8.5px 的小徽标；在胶囊里，整个列表都不显示，签到为零。结果就是：用户只在"有事"的时候看到它，从来感受不到"完成"。

形态签到怎么出现占多少
面板 · 风险带签到 2/3 + 3 段迷你条（已签绿 / 待签琥珀 / 未签灰）风险带第三格，不加高
面板 · 行行尾独立一列：✓ / +100 / !；不挤名称、不参与余额配色约 22px 宽
紧凑条✓ 2/3 chip，固定在 +N 左边约 40px
胶囊展开按钮右上角一个 4px 琥珀点（有未签时）；tooltip 写"还有 1 个渠道没签到"0（浮层）
吸附条某段对应的渠道有未签时，该段顶部叠 2px 琥珀细线0
四个状态不变，只补一个"完成态"：
已签（✓）· 可领（+100，可点）· 待签（灰）· 需处理（! 去登录）——这四态和现有实现一致。
新增第五个聚合态：全部完成 ✓ 3/3。它在风险带里是暗绿色，不弹提示、不播放动画， 只在从 2/3 变成 3/3 的那一次扫过一道 300ms 的微光，然后安静地待着。

为什么"全部完成"值得一个位置？因为签到的本质是日常仪式，不是告警。 仪式的闭环是"我做完了"，不是"没有红点"。一个每天都会被完成的动作，如果完成后界面什么都不说， 用户第二天就不会再想起它——而这恰好是这个产品唯一能形成日活的东西。

场景现在新方案
冷启动 一行"加载中…"或"正在取数…首次启动需要几秒" 骨架列表：6 行占位（灰块图标 + 灰条名称 + 灰条数值），不闪、不循环；每取到一个渠道就点亮一行。 底栏写"正在取数 2/9"。

7.1 把"判断"收进后端的一个纯函数模块

新增 app/core/src/view.rs（名字可议）：输入现有的 Channel，输出一个 ChannelView。 不碰网络、不碰 DOM、不读时钟以外的外部状态，所以可以用 cargo test 全覆盖。

pub struct ChannelView {
    pub state: ViewState,        // Fresh | Stale | Auth | Error | NoKey | Exhausted | Limited
    pub tone: Tone,              // Ok | Warn | Bad | Off
    pub tier: u8,                // 0 需要动作 / 1 比例 / 2 绝对额 / 3 积分 / 4 其余
    pub urgency: Option<f64>,    // 同桶内可比；跨桶不比较

    pub age_secs: i64,

再加上一个列表级的输出：order: Vec<String> 与 risk: Option<String>（最紧的那一个）。 前端不再调用 sortChannels、toneOf、remainRatio、dotCls 去做判断， 只按 order 排、按 state 画。

为什么不放在前端？三个理由：
① 这个项目的前端没有单测，只有 node --check；把 7 种状态 × 5 个桶的判定放在 JS 里，等于没有回归保护。
② 项目已经两次把"唯一真相"放到后端：签到的 doneToday（前端零日期运算）、详细日志开关（后端持有）。 这次是同一个模式。
③ 只有一处判定，才可能保证"四种形态结论一致"——这正是 D01/D02/D03 的根因。

7.4 别踩这些坑

① 窗口几何是这块代码最脆弱的部分。项目里已有专门的几何队列（enqueueGeom）和大量"实测踩过"的注释： 胶囊速览把窗口撑高、吸附展开、紧凑条宽度随内容变。本次设计不新增窗口形变（+N 不做浮层就是这个原因）， 但面板行高从 84 变 36/56、风险带从 55 变约 66，仍然会改变面板内容高度。必须走同一条几何队列，并保留 min/max 钳位。

② 不要每次轮询都重排高度。行在"紧急 ↔ 普通"之间切换会改变高度，如果每次刷新都重建 DOM， 列表会抖。做法：同一渠道的行类型变化时，只切换 class（高度用 CSS 过渡），不重建节点。

③ 紧凑条的宽度测量要换顺序。现在是"三档各量一遍，再从最宽的开始降级"；新方案是"先预留风险 chip 的宽度， 再按 urgency 依次装入"。offsetWidth 仍要读，但只读一次（风险 chip 宽度随内容变，需要缓存 + 失效）。

④ 字号三档都要验。--u = 1.3 时正文有 max(11.5px, …) 兜底，行高不是线性增长； 表格里的 437/494 是推算值，实现后要真机量。

⑤ 不要动 SIZES.panel = [380, 560] 的契约。四种形态的窗口尺寸被 formSize() 与吸附几何共用， 改一个数会牵动吸附位置、托盘、紧凑条宽度三处。

9. 明确不做

不做为什么
第五种形态（悬浮球 / 灵动岛 / 桌面贴纸）四种已经覆盖了全部面积档位；再加一种，就要多维护 7 种状态 × 1 套几何。竞品加形态是因为它们只有一两种，不是因为我们缺。
首页放历史曲线展开区已经有 24h/7d/30d 与变动台账。首页的任务是"现在"，不是"趋势"。
币种自动换算后合并成一个总余额静默换算 = 在用户不知道汇率的情况下改了他的钱数。只并列（¥1,284 + $42），不合并。
多账号本期只预留数据模型（一个渠道可以有 N 个账号视图），不做 UI。四个竞品都在要，但它是独立的一块，不该和展示形态一起改。
供应商状态页 / 故障事件层有价值，但它解决的是"是它挂了还是我没钱了"，属于数据源扩展，不是首页形态。
自动切换形态（比如闲置自动收成胶囊）用户选了什么就是什么。自动变形会让人找不到窗口，而且和"吸附"的手动语义冲突。
给签到单开一个页面签到的价值在于"顺便看见"，不在"专门去管"。它应该是一个进度，不是一个目的地。
新增前端依赖 / 图表库 / 动画库现有的纯 CSS + 原生 DOM 足够；4 个 mock 级别的动效不值得引入一个库。
把四行做成可拖拽排序的仪表盘那是另一个产品（Grafana）。这里的排序必须是自动的、按风险的。

9.1 开放问题（需要拍板）

#问题建议
Q1总余额要不要把非人民币按汇率折算后并入？不并入。主数字只放人民币合计，非人民币在副行并列。折算必须显式（≈ + 汇率 + 日期），且默认关。
Q2紧急行最多显示几条？不设上限。如果 5 条都紧急，那 5 条都该变大——这时候列表滚动是对的。设上限反而藏了最该看的东西。

Q5「余额底线」默认 ¥10 合理吗？合理作为起点，但必须可改。不同渠道的量级差很多（DeepSeek 一次充 ¥50，4SAPI 一次充 ¥500），后续可以按渠道单独设。

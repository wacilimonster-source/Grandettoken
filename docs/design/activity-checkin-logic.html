这块面板需要让用户一眼看懂三件事

1
活动是不是新的？

用活动 ID、活动期和账号识别；只有首次出现或状态变化才提示，不让每轮刷新重复弹通知。

2
能不能由挂件直接领？

“活动可参与”与“接口可领取”不是一回事。客户端活动显示为“需客户端参与”，不能写成“无活动”。

3
领取算谁的？

Qoder 按账号日轮次；Trae 的名额按设备日计算；WorkBuddy 按账号和区域解释。结果文案必须带上范围。

自动领取关闭时继续监测；监测关闭时不发请求。升级后沿用旧配置与已确认状态，不因规则更新重新领一遍。
02 / 判定流程

四步处理，每一步都能解释原因

任一环节信息不足，都停在“暂时无法确认”，不猜着写入
01 · DISCOVER

读取并验证状态

检查 HTTP、业务码和必要字段；网络错误、登录失效、格式变化与“本期无活动”分开记录。

02 · CLASSIFY

识别活动与能力

取活动类型、状态、奖励、活动期和参与范围。直领、客户端参与、仅展示不是同一种状态。

03 · ACT

按用户设置执行

只对明确支持直领的奖励调用领取接口；客户端任务只提醒。每次领取使用刚取到的活动 ID。

04 · CONFIRM

回查并确认结果

根据平台回执和后续状态确认“已领”。请求发出但结果未明时显示“确认中”，不提前报成功。

05 / 优化建议

先补状态范围，再做统一展示

首期以规则可解释、升级兼容、无误领为验收重点
P0 · 状态模型

给结果补充参与范围

保存渠道、区域、账号/设备范围、活动 ID、周期、奖励、状态和最后检查时间。让“已领”可以解释为谁的哪一轮。

P0 · WorkBuddy 规则

按区域解释状态码

现有解析注释要求区分域名语义，但解析入口未显式接收区域；设计上把 region 纳入判定上下文，未知含义显示待确认。

P0 · Trae 规则

明确设备日名额

把设备级“今日名额已用”从账号级“已签到”拆开，避免批量账号逐个重试同一个已消耗的设备名额。

P1 · 监测体验

监测和自动领取独立开关

关闭自动领取仍可发现新活动；活动 ID / 账号 / 周期去重，只在新增、可领状态变化或结果变化时通知。

P1 · 结果确认

统一回查和到账核对

保留请求回执、平台状态回查与余额刷新结果。只有拿到明确平台确认才显示已领取；数额缺失就不补猜。

P2 · 维护性

保留渠道适配器，统一契约

每个渠道独立解析与业务码映射，对外输出统一状态；结构变更进入“暂时无法确认”，并带脱敏诊断信息。

已具备，可直接沿用

Grandettoken 已能识别 Qoder 的直接领取活动与客户端活动、保留活动历史、领取前重取活动 ID，并为国际版查询附加机器身份。此方案重点是扩展到统一的活动列表和状态范围，不重复重做这部分。

06 / 兼容与边界

升级不重领，未知不误判

沿用用户现有自动领取设置
场景处理原则
旧版保存了“已领”按历史事实保留；升级不会把它清成未领，也不会补发领取请求。
旧版保存了“无活动 / 需手动”只有活动识别规则有版本变化时重新查询；不把历史状态当作本轮实时结果。
活动数据有新字段或未知状态保留监测与诊断；停止自动写入，提示“暂时无法确认”，不降级成“无活动”。
活动只在客户端完成记录活动标题和发现时间；不给“已签到”计数，不重复提醒同一个活动。
领取成功但余额未刷新展示“平台已确认，余额同步中”；下一次余额刷新完成后再标记到账核对状态。

App 渠道卡新鲜度文案收敛

2026-11-13 · 范围：Android App 渠道卡 / 渠道详情
状态：已评审 · 2026-11-13 实施（代码已落地，验证见 §10）

问题一句话：每张正常的渠道卡都在副标题里写一次「刚刚」。正常数据本来就不需要报时——时间应该只在「很久没更新」或「取数失败」时开口。本方案把卡片上的时间从默认项改成异常项，并用一个纯函数收口三处阈值，避免再出现第三份「2 小时」常量。

结论先行：正常卡去掉时间片段；只有 ≥ 2 小时未更新、渠道被标记为较旧、取数失败、从未取到过 四种情况才显示。无协议、无数据库、无 PC 端改动，Android 侧约 1 个新纯函数文件 + 3 处 UI 调用点 + 1 组单测。

§1现状与证据

全仓 grep「刚刚」后在 Android 侧只剩两处用户可见来源，恰好都在卡片上。

§2为什么这是问题

1. 信息为零，却占满一行

正常刷新的卡占绝大多数。每张都写「刚刚」，等于每张都在说「我没坏」——用户读不到任何差异，副标题真正该承担的「类型 / 到期 / 推算」被挤到后面。

2. 注意力被平均分配

当一张卡 3 小时没更新、另一张 30 秒前刚更新，两者副标题都以时间开头，扫视时无法第一眼分出「哪张不能信」。

3. 三端规则不一致

同一份数据：PC 行正常时不写年龄，小组件正常时也不写；只有 Android 卡写「刚刚」。同一个产品，三种口径。

4. 详情页自我重复

首卡写「更新于 刚刚」，下面「数据说明」又写精确的「最后成功更新 11-13 14:05」。一处相对、一处绝对，信息重复且相对那处没有增量。

§3设计规则：时间只在异常时出现

先定判定，再定文案。判定按优先级从上到下短路，避免「失败 + 旧」被写成「数据较旧」。

状态判定卡片副标题追加详情页

3.1 阈值为什么是 2 小时建议

  • 项目里已经有两个成文的「2 小时」：通知规则 NotificationRules.STALE_SECONDS（通知文案就是「超过 2 小时未更新」）和小组件 WidgetFormatter.STALE_SECONDS。卡片沿用同一个数，用户收到的文字才一致。
  • App 前台 60 秒 / 5 分钟拉一次，后台默认 15 分钟一次；2 小时意味着连续错过 8 次以上后台刷新，属于真的异常，不是抖动。
  • 不想再新增第三份常量：本轮把三处收口到 ChannelFreshness.STALE_SECONDS，以后改阈值只改一处。

若评审认为 2 小时太晚，可改 1 小时或 30 分钟；规则形状不变，只改一个常量。不建议做成「按后台间隔动态算」，那会让文案随设置变化，用户无法预期。

3.2 为什么失败时还要带「上次」建议

「取数失败」只说明这一轮没成，不说明屏幕上这个数有多旧。带一句「上次 25 分钟前」，用户才知道能不能继续参考。不足 1 分钟时不写，避免又冒出「刚刚」。

3.3 结构上保证「刚刚」不会再回来

卡片用的不是通用 relativeTime()，而是 ChannelFreshness.timeLabel()：正常返回 null，失败分支最短只到「取数失败」，较旧分支最短只到「数据较旧」，两者都不会把 < 60 秒的差写成「刚刚」。单测里再加一条「0 秒到 7 天全扫一遍，标签不得包含『刚刚』」。

§6实现方案

6.1 新增一个纯函数文件P0

放在 android/app/src/main/java/com/wacil/grandettoken/sync/ChannelFreshness.kt，不依赖 Compose，now 作为入参，单测可直接给固定时间。

// 渠道卡/详情共用的“什么时候才配报时”规则。
// 正常返回 null；任何分支都不会产出「刚刚」。
internal object ChannelFreshness {
    const val STALE_SECONDS = 2 * 60 * 60L   // 与通知/小组件同口径

    enum class State { Fresh, Stale, Failed, Never }

    fun state(ch: ChannelSnapshot, now: Long): State = when {
        ch.errorCode != null -> State.Failed
        ch.stale || (ch.updatedAt > 0 && age(ch, now) >= STALE_SECONDS) -> State.Stale
        ch.updatedAt <= 0 -> State.Never
        else -> State.Fresh
    }

    // 卡片副标题追加项；null = 不显示。
    fun timeLabel(ch: ChannelSnapshot, now: Long): String? = when (state(ch, now)) {
        State.Fresh -> null
        State.Never -> "从未更新"
        State.Stale -> if (ch.updatedAt > 0 && age(ch, now) >= STALE_SECONDS)
            "数据较旧 · ${relativeTime(ch.updatedAt, now)}"
        else "数据较旧"
        State.Failed -> if (ch.updatedAt > 0 && age(ch, now) >= 60)
            "取数失败 · 上次 ${relativeTime(ch.updatedAt, now)}"
        else "取数失败"
    }
}

§8风险、边界与待裁决

8.1 风险与缓解

风险缓解
正常卡看不到时间，用户怀疑「是不是没刷新」刷新仍有 loading 条与数值变化；详情「数据说明」保留精确的「最后成功更新」。PC 行与小组件早已这样处理，没有反馈问题。
「数据较旧」但只有 5 分钟，用户觉得夸张只写状态不写年龄，不把「旧」和具体分钟数绑在一起；年龄只在 ≥ 2 小时时出现。
阈值 2 小时太晚单常量可调；改一处即可同步 App / 通知 / 小组件。
设备时钟异常未来时间按正常处理；负数年龄被 coerceAtLeast(0) 吃掉，不出现「-3 小时」。
顶部「N 个渠道数据较旧」横幅与「需要关注」分组仍只按同步载荷的 stale/error 标记统计；仅因年龄超标的卡不会自动进「需要关注」，也不会抬高横幅计数本轮不动排序与横幅口径，避免扩大范围。卡片自身仍会变黄点并写「数据较旧 · N 前」，异常可见；若评审要求三处同源，下一轮把 staleCount 与 ChannelOrdering.needsAttention 改用 ChannelFreshness.state。
无障碍：正常卡不再朗读时间时间本来就不是正常态需要朗读的信息；异常态文字仍可读，详情有绝对时间。列表项的 stateDescription 仍表达展开/收起。

8.2 附录：PC 端同款位置（不在本轮）

  • app/src/app.js:1694 详情弹层 caption 固定写「更新于 ${relTime}」→ 正常详情会显示「更新于 刚刚」。PC 渠道行 :845-847 已经只在异常时写年龄，所以这里只差详情弹层一处。
  • app/src/app.js:4475 顶栏 tbLive 的「刚刚」是刷新状态反馈（2026-11-05 用户明确要求整块可点），不是卡片数据年龄，不建议动。
  • 若评审要求跨端一致，可在 Android 落地后单独一个小 PR 改 app.js:1694：正常不写，异常写「更新于 N 前」。
  • 另外 ChannelDetailScreen 的「数据说明 · 最后成功更新」本来就给绝对时间，这是详情页的最终兜底，不要一起删。

8.3 评审确认的三点（已按默认落地）

#确认项落地值
1「很久没更新」的阈值2 小时（与通知、小组件同口径）。以后若觉得太晚，改一个常量即可。
2详情页是否一起改已一起改：首卡不再常驻「更新于 …」，异常年龄放进横幅。
3PC 详情弹层是否同步本轮未做，保持 App 单端可回滚；需要的话下一轮一行改动。
落地顺序（已完成前四步）：先加 ChannelFreshness 与单测（红→绿证明规则）→ 改卡片副标题与详情 → 收口通知/小组件常量 → 跑 Android 单测与 assembleDebug → 真机四态截图（待做） → 再决定是否碰 PC 详情弹层（未做）。

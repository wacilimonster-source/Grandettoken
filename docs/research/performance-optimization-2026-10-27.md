# Grandettoken 性能优化调研与实施方案

> 调研日期：2026-10-27  
> 代码基线：`abc540f`（v0.1.69，工作树干净）  
> 范围：常驻轮询、SQLite/历史计算、自定义渠道取数、前端常驻定时器与设置页元数据读取。  
> 调研阶段未修改产品代码；**Phase A–D 已按本方案实施**，结果见第 8 节。

## 0. 结论摘要

当前产品已经相当轻：空闲 8 秒采样 CPU 为 0，进程生命周期平均约 0.1% 单核；继续压低轮询频率的收益很小，还会牺牲实时性。真正值得做的是**缩短每分钟刷新时的 CPU 尖峰与最坏等待时间**，而不是追求更低的空闲占用。

| 优先级 | 优化项 | 证据 | 预期收益 | 风险 |
|---|---|---|---|---|
| **P1** | 每个金额型渠道的历史窗口改为**一次读取、内存复用** | 当前一轮最多 12 次重叠 SQL；实测单渠道 4 个金额窗口合计约 131 ms，4 个渠道约 525 ms | 无索引约减少 60%～70%；覆盖索引后约减少 85%～90% | 中；只读计算，可用旧实现做等价测试 |
| **P1b** | 增加 `(provider_id, key_fp, ts, remaining)` 覆盖索引 | 真实指纹查询 26.63 ms → 8.68 ms；169k 行建索引约 162 ms，数据库约 +6.8 MiB | 与 P1 叠加后进一步减少磁盘页访问 | 低；纯新增索引，不改数据 |
| **P2** | 自定义渠道与内置渠道**并行**、自定义渠道内部并发（并发上限 4） | 自定义渠道在全部内置渠道结束后串行执行；每个最长 8 秒 | 有慢速自定义渠道时，刷新最坏等待从“内置 + N×8s”变为“两者取最大” | 中低；保持顺序与错误语义即可 |
| **P2** | 前端峰谷倒计时 1 秒定时器改为分钟对齐；设置页密钥尾号/来源按需刷新并缓存 | 1 秒一次全 DOM 扫描；设置页打开时每分钟重复读 N 次 keyring | 定时器回调 3600 次/小时 → 60 次/小时；滚动刷新不再重复 RPC | 低～中；缓存需明确失效点 |
| **P3** | 合并启动时 `get_channels` + `home_view` IPC | 同一轮数据、同一份视图被分两次请求 | 少一次 IPC 与视图重算 | 低收益，暂不做 |
| **不推荐** | 降低轮询频率、改 WebView2 启动参数、换数据库、升级依赖、改 release 编译参数 | 空闲 CPU 已接近 0；内存由 WebView2 主导 | 收益不确定或会破坏行为 | 高 |

**“保证不产生额外 bug”的工程含义**：无法数学证明零缺陷，但本方案把改动限制在**只读计算/调度层**，不碰密钥、更新、安装、数据库写入语义；每项都要求旧实现与新实现逐值等价、单独发布、失败即回退。绝对不做的改动（如修改通知节流、失败降级、密钥来源）不在本方案内。

## 2. 已确认的瓶颈

### 2.1 历史窗口重复读取（P1，最大确定收益）

`app/core/src/fetch.rs` 中：

- `amount_windows()` 一次计算 6 个区间（`fetch.rs:1541-1582`），每个区间都走一次 `Store::consumption_since*`；
- `gap_from()` 再查 3 次窗口覆盖（`fetch.rs:1660-1673`）；
- 92 天逐日覆盖查 1 次；
- 申请制状态查 90 天跳升（`fetch.rs:1497-1536`）；
- 近 7 天日均查首条时间 + 窗口消耗（`fetch.rs:587-605`）。

这些区间**互相重叠**，但每次都重新执行 `rows_between`（`store.rs:413-446`），把相同历史行重复读进内存。已在此前体检中登记为 O-1，目前仍在。

### 2.2 覆盖索引缺失（P1b）

`idx_snap_fp(provider_id, key_fp, ts)` 不含 `remaining`，命中索引后仍需回表。用一个真实指纹查询 93 天数据：

- 现状：26.63 ms，使用 `idx_snap_lookup` 后回表过滤；
- 新增 `(provider_id, key_fp, ts, remaining)` 覆盖索引：8.68 ms，计划变为 `COVERING INDEX`；
- 建索引 162 ms，数据库 22.5 MiB → 29.2 MiB（仅新增一条覆盖索引）；
- 再加一条不带指纹的覆盖索引会到 36.0 MiB，但金额型渠道实际都有指纹，**不需要第二条**；
- `ANALYZE` 对该计划没有进一步收益，不建议自动执行。

### 2.3 自定义渠道串行且排在内置渠道之后（P2）

`fetch.rs:2606-2627`：内置 9 个渠道全部 `join_all` 完成后，才逐个读取自定义渠道凭据并依次请求。每个请求 8 秒上限，N 个自定义渠道最坏增加 N×8 秒。它们彼此独立、也不依赖内置结果，完全可以并行。

### 2.4 前端常驻定时器与设置页重复 RPC（P2）

- `app.js:165-176`：每 1 秒查询整个文档的 `[data-peakcd]` 并 `JSON.parse`。而 `peakCountdown` 只显示“X 小时 Y 分”，分钟精度足够。
- `app.js:2276-2301`：设置页打开时，每轮渲染都会 `fillKeyHints()`，对每个已配置渠道发一次 `key_hint`。
- `app.js:2373-2391`：随后 `fillKeySources()` 又对每个 `keyring` 渠道串行发 `key_source`，并重新读一次引用表。
- 结果是设置页停留期间，每分钟重复 N 次凭据管理器 RPC，余额刷新会顺带触发与余额无关的秘密元数据读取。

### 2.5 已排除的“伪优化”

| 方向 | 为什么不做 |
|---|---|
| 把 1 分钟轮询降到 5 分钟 | 空闲 CPU 已接近 0；会直接降低余额实时性，违背产品定位 |
| 优化 Rust `Vec`/`clone` | 9 个渠道、每轮数据量很小；收益低于噪声，增加回归面 |
| 降低 WebView2 进程数 / 加启动参数 | 未公开保证，可能破坏托盘、透明窗、动画；当前 375 MB 是 Chromium 正常成本 |
| 换连接池 / 多线程读 SQLite | 写少读多，单一 `Store` 锁只持续几十毫秒；池化带来一致性风险，收益低 |
| `opt-level=3`、改 LTO | 需完整基准证明；会增加二进制/构建时间，当前 CPU 瓶颈在 SQL 页访问 |
| 升级依赖 / 引入 ORM | 与本轮目标无关，回归面过大 |

## 3. 实施方案

### Phase A：历史窗口单次读取（P1）

#### A1. 目标与边界

- 只改 `app/core/src/fetch.rs`、`app/core/src/store.rs`；
- 不新增/修改表、不写数据库、不改快照落库顺序；
- 每轮每个金额型渠道**只读一次**历史，之后在内存中切出所有窗口；
- 保留旧实现作为回退路径与测试基准。

#### A2. 具体设计

新增（`store.rs`）：

```rust
pub struct HistoryRow {
    pub ts: i64,
    pub remaining: Option<f64>,
}

pub fn history_between(
    &self,
    provider_id: &str,
    key_fp: Option<&str>,
    from_ts: i64,
    to_ts: i64,
) -> Result<Vec<HistoryRow>, String>;
```

SQL 必须按 `key_fp` 分两条明确语句，而不是 `? IS NULL OR key_fp=?`：

```sql
-- Some(fp)
SELECT ts, remaining FROM snapshots
 WHERE provider_id=?1 AND key_fp=?2 AND ts>=?3 AND ts<=?4
 ORDER BY ts ASC;

-- None（保持旧语义：不限指纹）
SELECT ts, remaining FROM snapshots
 WHERE provider_id=?1 AND ts>=?2 AND ts<=?3
 ORDER BY ts ASC;
```

注意：历史读取**不要**在 SQL 里过滤 `remaining IS NOT NULL`。旧 `window_coverage` 统计所有快照行，而消耗计算只看有余额的行；因此一次读出 `Option<f64>`，再在纯函数中分别处理，才能保证覆盖/缺口口径不变。

把现有公式原样抽成纯函数（不要重写公式）：

- `consumption_since_rows(rows, from_ts, now_ts) -> Option<f64>`
- `consumed_in_window_rows(rows, from_ts, to_ts) -> f64`
- `window_coverage_rows(rows, from_ts, to_ts) -> WindowCoverage`
- `daily_coverage_rows(rows, from_ts, to_ts, tz_offset) -> Vec<DayCoverage>`
- `last_jump_rows(rows, from_ts, min_delta, target, max_gap) -> Option<i64>`
- `first_ts_rows(rows, from_ts) -> Option<i64>`

现有 `Store::consumption_since*`、`window_coverage`、`daily_coverage`、`last_jump_since*` 保持原签名不变，内部改为“查一次 + 调用纯函数”。这样 A 方案失败时可以回到完全相同的旧行为。

`fetch.rs` 的 `build_view()` 改为：

1. 只对 `has_amount` 的渠道计算一次时间锚点：
   `today0 / week0 / month0 / prev0 / now2`；
2. 取最早需要的起点：
   `min(prev0 - 86400, now2 - 92*86400, now2 - 90*86400)`；
3. 调一次 `history_between`；
4. 在同一份 rows 上算出 6 个消耗窗口、3 个缺口、逐日覆盖、7 天日均、申请制跳升；
5. 其中任一子计算需要“窗口起点前基线”时，仍按旧公式从全量 rows 中过滤 `from - 86400`；
6. 若历史读取失败，**整块**退回旧实现，不允许“部分新、部分旧”混算。

另外两处必须保持：

- `claim_for()` 不再内部调用 `now_ts()`，改由 `build_view` 传入同一个 `now2`；否则批量读取与单独查询可能跨秒，边界测试不稳；
- `key_fp = ""` 仍表示“不分段”，不能误改成 `key_fp = ''` 过滤。

#### A3. 不变量（必须逐条测试）

1. 无基线 → `None`，绝不变成 0；
2. 窗口内一条都没有 → `None`；
3. 窗口内只有一条 → `None`；
4. 充值/配额重置产生的负差值按 0；
5. 跨窗口起点按时间线性折算；
6. 所有金额保留现有 `(sum * 100).round() / 100` 口径；
7. 指纹 `Some / None / 空串` 三种作用域完全一致；
8. 缺口统计包含 `remaining IS NULL` 的行；
9. 日桶按传入时区，不用 SQLite `localtime`；
10. 快照读取顺序仍为 `ts ASC`，重复时间戳保持稳定顺序。

#### A4. 测试与验收

新增测试：

- **旧/新差分测试**：同一批行分别喂给旧实现和纯函数，断言 `Option` 存在性、所有 f64 位级相等、缺口/日覆盖/跳升时间完全相等；
- 固定夹具：空、单行、只有基线、跨月、2 月 28/29、3 月 31、闰年、00:00:00、23:59:59；
- 随机夹具：固定种子 500 组，含随机空洞、充值、重复时间戳、两个指纹交错；
- 查询次数：test-only 计数器确认每个金额渠道 **1 次**历史读取，而不是 12 次；
- 旧路径保留测试：强制让批量读取失败，断言回退结果与当前版本逐值相同；
- 极端数据：90 天 × 15 秒间隔（约 51.8 万行）时内存峰值可控；超过 50 万行自动退回旧路径，避免一次性占用过大。

性能门槛（同机、同一 169k 行数据库、重复 10 次取中位数）：

- 4 个金额渠道历史计算：**≤ 180 ms**（基线 525 ms）；
- 加上覆盖索引后目标 **≤ 80 ms**；
- 不允许任何快照/视图字段与旧实现在同一冻结时刻不一致。

#### A5. 回滚

- 无数据库迁移、无写入变化，回退只需恢复 `build_view` 的调用入口；
- 建议保留旧路径至少一个版本，批量失败可运行时自动回退；
- 若线上发现数值差异，发布**更高版本号**恢复旧入口，不能用旧版本覆盖 `latest.json`（当前更新插件不支持降级）。

### Phase B：覆盖索引（P1b，独立一步）

#### B1. 设计

新增索引：

```sql
CREATE INDEX IF NOT EXISTS idx_snap_fp_cover
  ON snapshots (provider_id, key_fp, ts, remaining);
```

- 该索引覆盖金额型渠道最常用的“渠道 + 当前指纹 + 时间范围 + 余额”读取；
- **不删除**现有 `idx_snap_fp`，先共用一个版本，避免计划回退；
- 不新增第二条不带指纹的覆盖索引：金额型渠道都有稳定指纹，额外 6.8 MiB 无对应收益；
- 不自动执行 `ANALYZE`（实测无额外收益）；
- 索引创建不能阻塞启动：即使创建失败，也只记录警告，继续使用旧计划；下次启动重试。

#### B2. 测试与验收

- `EXPLAIN QUERY PLAN` 断言批量历史查询命中 `COVERING INDEX idx_snap_fp_cover`；
- 全量 333+ 测试不变；
- 旧库（v4，缺列）升级测试：先迁移 `key_fp`，再建索引，顺序不能反；老库打开不能报 `no such column: key_fp`；
- 磁盘：数据库增长 ≤ 8 MiB；
- 冷启动：首次建索引在 169k 行下 ≤ 500 ms；超过 1 秒则不阻塞窗口显示，放后台完成（但查询仍可继续用旧索引）。

#### B3. 回滚

索引本身不影响正确性，可直接保留；若怀疑计划变慢，删除该索引即回到旧版本，无需迁数据。

### Phase C：自定义渠道并行（P2）

#### C1. 设计

`fetch_all()` 当前顺序：

```
内置渠道 join_all → 自定义渠道串行 → 写库/组视图
```

改为：

```
内置渠道 join_all ─┐
                   ├─ 同时等待 → 写库/组视图（按原顺序）
自定义渠道并发 ────┘
```

要求：

- 用 `tokio::join!` 同时驱动内置与自定义两组 future；
- 自定义渠道最多同时 4 个（`buffer_unordered(4)`），避免用户配置几十个渠道时瞬间并发；
- 结果带回原始下标，最终按配置顺序排列，界面顺序不变；
- 每个渠道仍走原有的 `secrets::channel_key` + `spawn_blocking`；
- 缺少密钥、隐藏、探活模式的语义完全沿用；
- 单个失败/超时不取消其他渠道，错误文案保持原样。

#### C2. 测试与验收

- 2 个本地 loopback HTTP 端点各延迟 150 ms：串行 ≥300 ms，并行 <250 ms；
- 3 个端点中一个超时：总耗时不超过单个 8 秒超时 + 误差，而不是 24 秒；
- 结果顺序、`hasKey`、`hidden`、`probeOnly`、错误字符串全部与旧逻辑一致；
- 隐藏渠道仍不发请求、不读凭据；
- 原有自定义渠道单元测试全过。

#### C3. 风险与回滚

- 风险主要是外部端点被同时访问；并发上限 4、5 分钟轮询，频率仍低；
- 回退只需恢复串行循环，无数据迁移。

### Phase D：前端定时器与设置页元数据（P2）

#### D1. 峰谷倒计时

`app.js:165` 的 1 秒 `setInterval` 改为：

- 分钟边界对齐的 `setTimeout`（60000 - 当前毫秒）；
- `render()` 完成后立即刷新一次；
- 继续只改 `textContent`，不重建行；
- 窗口从托盘唤回时立即刷新一次，避免隐藏期间停摆。

显示精度本来就是分钟，视觉与文案不变。收益：每小时的定时器回调从 3600 次降到 60 次。

#### D2. 设置页密钥元数据缓存

当前 `refreshChCards()` 每次轮询都会：

1. `renderChCards()` 重建卡片；
2. `fillKeyHints()` 每渠道一次 `key_hint`；
3. `fillKeySources()` 每渠道一次 `key_source` + 一次引用表读取。

改为：

- 新增 `KEY_META[id] = { hint, source, at }` 与同步回填函数 `paintCachedKeyMeta()`；
- `renderChCards()` 重建后用缓存**同步**填回尾号/来源，不产生 RPC；
- 仅当缓存缺失或超过 TTL（建议 5 分钟）时才异步刷新；
- 明确失效点：`set_key`、`delete_key`、`clear_key_ref`、`set_key_ref`、`vault_save`、`vault_delete`、`openManage()`；
- 正在输入时不重建的现有保护保持不变；
- 任何读取失败仍显示原错误提示，不能把“读不到凭据”显示成“未配置”。

#### D3. 测试与验收

- jsdom：设置页连续 10 次 `render()`，`key_hint` / `key_source` 调用次数只在首次 >0；保存密钥后缓存失效，下一次会重新读取；
- 峰谷倒计时仍显示分钟文案，DOM 重建后立即恢复；
- 实机检查设置页滚动、输入草稿、密钥显示/隐藏、引用来源切换无变化；
- 不改变任何余额、签到、通知逻辑。

#### D4. 回滚

前端缓存全部在内存中，刷新/重启即失效；回退只需恢复每次 render 都调 `fill*` 的旧行为。定时器改动可直接恢复 1 秒间隔。

### 4.4 为什么这套方案不容易引入新 bug

- **只读优先**：Phase A/B 不改任何写入路径、快照语义或凭据路径；
- **旧实现保留**：旧函数继续存在，作为 fallback 与测试 oracle；
- **失败整块回退**：批量历史读取失败时不做部分新旧混算；
- **无 schema 语义变化**：只新增索引，失败不阻塞启动；
- **按文件隔离**：A/B 只动 store/fetch；C 只动 fetch 编排；D 只动前端；
- **一次只发布一项**：出问题能定位到单个变更，而不是“性能优化大礼包”；
- **不降级发布**：更新链路不支持降级，所以每次回滚都是发布更高版本并关闭新路径。

## 6. 遗留观察项（本轮不做）

- `checkin_state` 对每个未完成渠道串行探测凭据；启动时可能增加首屏等待，但它同时承担“把失败原因说清”的职责，改动需要重新设计提示时序，暂不动。
- WorkBuddy 国内版/国际版会在同一轮重复扫描凭据文件与账户号（`workbuddy.rs:1292-1382`、`fetch.rs:2386-2394`）。实际文件很小且 key 有 6 小时缓存，收益低；且缓存凭据有登录切换后的陈旧风险，暂不做。
- 启动时 `store.prune()` 在主线程执行；当前 169k 行下开销不构成瓶颈，等有实际慢启动样本再处理。
- 合并 `get_channels` + `home_view` 为单 IPC 属于低收益改动，暂不做。
- WebView2 内存与进程模型没有安全、可验证的优化路径；不通过启动参数“省内存”。

## 7. 最终建议

先做 **Phase A**。它是唯一一个既有明确代码证据、又有可量化收益、还能用旧实现逐值对照的优化；不涉及数据库结构、凭据、网络语义或界面行为，风险边界最清楚。若 A 的差分测试和 48 小时运行都通过，再做索引与调度优化。当前产品空闲性能已经很好，不建议为了“看起来更快”去改轮询频率或 WebView2 架构。

# 产品设计 · 排查日志（可观测性）体系

> 2026-10-21 · 依据 0.1.52 代码实读（`app/core/src/diaglog.rs` 及全部 34 个写入调用点、`app/src-tauri/src/lib.rs`、`app/src/app.js`）

---

## 0. 先说人话

现在这个挂件**有**日志，但日志是"半边"的：

- **WorkBuddy 那一路记得很细** —— 找 exe、读凭据文件、解信封、比对 keyId、续期失败，
  29 处埋点，出了事基本能还原现场。
- **其余 8 个渠道几乎不记** —— 失败时日志里只有"取数失败"四个字，没有 URL、没有状态码、
  没有耗时、没有响应长什么样。
- **往第三方客户端写配置那一整块（`inject.rs`，286KB）一个字都没记** ——
  而这一块的爆炸半径最大：写坏了是 Trae / DSH / ZCode / WorkBuddy 罢工，不是挂件自己少个数字。
- **凭据管理器坏了也不记** —— 这恰恰是最该记的：它是"读不到密钥"和"你没配密钥"的分界点。

所以现在的局面是：**最难查的那几类问题，日志里恰恰没有线索。**

而且日志本身还有几个洞（带点的 JWT 不遮、限流键漏了渠道维度）——
**在补洞之前扩日志，等于把泄漏面和噪声量一起放大。**

这个设计要解决的是两件事，按顺序：

1. **先把现有的洞补上**（第 0 期，半天，不做这个后面全是白干）
2. **把"半边日志"补成"完整因果链"**（第 1~4 期）——
   让任何一个"某渠道取不到数 / 某个数字不对 / 客户端配置写坏了"的问题，
   都能靠一段日志**还原出当时的每一步决策**。

## 1. 现状盘点

### 1.1 已覆盖的（34 个写入调用点）

| 模块 | 埋点数 | 记了什么 |
|---|---|---|
| `app/core/src/workbuddy.rs` | **29** | exe 探测 → 凭据文件枚举 → 信封解密 → keyId 比对 → 续期成败 → 请求。**最完整的一路** |
| `app/core/src/fetch.rs` | 2 | 「没有可用凭据」、取数失败 |
| `app/src-tauri/src/lib.rs` | 2 | 签到结果一行、用户手动清空日志 |
| `app/core/src/appauth.rs` | 1 | Qoder 候选凭据为空 |

加上 `diaglog::startup_banner()`（版本 / exe 路径 / 日志目录 / 环境变量 / 本机盘符）。

### 1.2 完全没覆盖的（0 调用点）

| 模块 | 大小 | 为什么必须有日志 |
|---|---|---|

| `core/src/inject.rs` | **286KB** | 写 Trae / DSH / ZCode / WorkBuddy 的配置。**备份、回滚、校验、幂等**全在这里。写坏了是别人的软件罢工 |
| `core/src/checkin.rs` | 66KB | 签到状态机：周期日、抖动、退避、响应解读。签到失败的用户只会说"没领到" |

### 1.3 五个结构性问题（比"没覆盖"更要紧）

| # | 问题 | 现在的样子 | 后果 |
|---|---|---|---|
| **S1** | **脱敏有洞** | `redact()` 的判据是 `run.contains('.')` 就不遮 —— 而 **JWT 天然带两个点** | 诊断日志里可能明文躺着 accessToken。而这份日志的官方用途就是"贴给support" |
| **S2** | **脱敏键值表太窄** | 只认 `session=` / `cookie:` / `bearer ` / `accesstoken=` / `refreshtoken=` 六种 | `{"accessToken":"…"}` 这种 JSON 形态、`?key=` 查询参数、`api_key`、`password` 全都不遮 |
| **S3** | **限流键漏了渠道维度** | 限流表只按 `key` 索引，渠道 id 被丢掉了 | 9 个渠道共用 `SEEN["channel"]` 一格 → 每次都被判成"状态变了" → **每 60 秒每渠道各写一行**，节流等于没开 |
| **S4** | **没有"这次运行"的标识** | 启动横幅写了一行就完了 | 用户说"昨天晚上坏的"，日志里 7 天前和今天的记录混在一起，分不清哪次运行 |
| **S5** | **界面文案与日志对不上** | 界面说「凭据失效 —— 打开一次客户端」，日志里写的是 `no-cred` | 用户报的那句话**在日志里搜不到**，两边对不上号 |

另外两个次要的：滚动只留 **1 代 / 2MB**（扩日志后一周前的问题就没了）；体检报告和日志是两套独立产物，不互相引用。

## 2. 目标：什么才算"全面"

### 2.1 一条完整的因果链

任何一个"某渠道取不到数"，日志要能回答这四个问题：

```
① 环境对不对？    → 这台机器上该有的东西在不在（exe、目录、注册表项、D 盘？）
② 凭据从哪来？    → 用了哪一份（手动填的？桌面端的？网页会话的？），为什么选它
③ 请求发出去了吗？→ 打了哪个 URL、什么方法、返回什么状态码、多久、响应长什么样
④ 结果是什么？    → 解析出了什么值 / 为什么解析不出来 / 有没有写进快照
```

现在的日志只覆盖了 ① 的一半和 ② 的一部分。

### 2.2 三条硬约束（不可协商）

| 约束 | 具体要求 | 怎么保证 |
|---|---|---|
| **绝不泄密** | 密钥、Cookie、Token 一律不落原文 | 结构化字段**白名单制**（只有列在白名单里的键能进日志）；自由文本走加强版 `redact` |
| **绝不拖慢取数** | 日志不能成为取数路径上的瓶颈 | 全部 IO 走后台线程 + 环形缓冲；写失败熔断；单行有长度上限 |
| **绝不写满磁盘** | 总量有硬上界 | 单文件上限 + **多代滚动** + 内存环形缓冲（高频事件只留内存） |

### 2.3 明确不追求的东西

- **不追求"什么都记"**。记一堆无用信息会把真线索埋掉 —— 这正是现在 `workbuddy.rs` 29 处埋点
  带来的副作用（那一路太啰嗦，反而淹没了真正的那一行）。
- **不追求"能离线分析"**。不引入日志框架、不引 tracing、不加结构化 JSON 落盘。
  理由：目标是"用户把一段文本贴回来"，人眼可读的文本 > 需要工具才能解析的格式。
- **不追求"在本地存用户的所有行为"**。这是余额监控挂件，不是行为审计。

## 3. 总体方案

### 3.1 分层模型

```
L0 环境      启动一次：版本、exe、数据目录、盘符、关键环境变量、已装客户端探测结果
   ↓
L1 决策      选了什么、为什么选：用了哪份凭据、选了哪个域名、为什么换下一个
   ↓
L2 交互      打出去的那一下：URL / 方法 / 状态码 / 耗时 / 响应字节数 / 响应结构摘要
   ↓
L3 结果      拿到了什么：解析出的值、快照写没写进去、界面最终显示成什么
```

**L2 是现在最大的空白** —— 而它恰恰是排查"接口怎么了"最需要的。

### 3.2 统一事件结构

所有埋点收敛到一个入口，输出统一格式的一行：

```
2026-10-21 09:14:22.481+08:00  L2  [4s3f9a2c] fetch  4sapi    http    url=api.4sapi.com/v1/usage  method=GET  status=200  ms=142  bytes=318  shape={data:{total_available:…}}  key=fp:8a1c9f2e
```

| 字段 | 作用 | 说明 |
|---|---|---|
| 时间 | 毫秒 + 偏移 | 已有，用户说"九点多"要能对上 |
| **级别** | `L0`~`L3` | 见 3.3 |
| **会话 ID** | `4s3f9a2c` | 一次启动一个，8 位十六进制。解决 S4 |
| **范围** | `fetch` / `wb` / `inject` / `checkin` / `db` / `ui` | 哪个子系统 |
| **渠道** | `4sapi` | 哪个渠道（没有就空） |
| **阶段** | `http` / `parse` / `snapshot` / `cred` | 哪一步 |
| **码** | `E_HTTP_401` | 见 6.3 错误码表。**界面和日志共用** |
| **字段** | `key=value` | 结构化，键名走白名单 |

格式保持**一行一事**、**人眼可读**、**键=值**可 grep。三条都重要：
用户贴回来的文本要能直接看，support 也要能 `grep E_HTTP_401`。

### 3.3 级别与"要不要落盘"

| 级别 | 含义 | 落盘 | 节流 |
|---|---|---|---|
| **L0** | 一次运行一次 | 总是 | 不需要 |
| **L1** | 关键决策（换凭据、换域名） | 总是 | 按 (范围,阶段) 去重 |
| **L2** | 每次 HTTP 交互 | **只在"值得留"时**：非 2xx、超时、耗时 > 2s、响应形状异常 | 同一 (渠道,URL,状态码) 5 分钟一条 |
| **L3** | 成功的结果 | **不落盘**，只进内存环形缓冲 | — |

**关键取舍：成功路径不落盘。**
理由：挂件最坏情况（面板展开、一分钟一轮）下 9 个渠道一天就是 **12960 次请求**。
全部落盘的话，2MB 只能撑 3 小时，
真正出问题时能查到的历史早就被冲掉了。

改成：**成功的事件只进内存环形缓冲**（最近 2000 条 / 16MB），
一旦发生失败，就把**失败前后的上下文**（环形缓冲里最近的 N 条）一起落盘。

这解决了"扩日志"和"日志量"之间的根本矛盾：**平时不占盘，出事时才有现场。**

```
【失败现场】4sapi 取数失败 · 2026-10-21 09:14:22 · 会话 4s3f9a2c
  ↑ 前 20 条上下文（内存环形缓冲里的，成功的事件也在里面）
  ↑ 失败事件本身
  ↓ 后 5 条上下文
```

## 4. 六个关键设计决策

### 决策 1：先修脱敏，再扩日志（前置，不可跳过）

**理由**：现在往日志里多写一行，就多一分泄漏风险。**先扩日志后修脱敏 = 顺序错了。**

要改的三处（对应 S1 / S2）：

1. **`is_secret_run` 的判据反过来** —— 先看"像不像令牌"，再看"是不是路径/域名"：
   - 点数 ≥ 2 的长串 → **一律遮**（JWT 特征）
   - 长度 ≥ 32 且含数字或大写 → 遮
   - 长度 ≥ 32 的**全小写**串 → 也遮（现在漏了）
   - 明确的路径 / 域名 / UUID / 错误码 → 不遮

2. **`redact_keyed_values` 换成"键名表 + 通用分隔符"**：
   - 键名表扩到：`access_token` / `refresh_token` / `id_token` / `api_key` / `apikey` /
     `x-api-key` / `token` / `secret` / `client_secret` / `password` / `passwd` /
     `authorization` / `cookie` / `session` / `sessionid` / `sid` / `csrf` /
     `atRestSecretKey` / `credential`
   - 分隔符不再只认 `=` 和 `:`，**JSON 形态的 `"key": "value"` 也要遮**
   - 值是引号包裹时，**跳过引号继续扫值**（现在扫到 `"` 就停，值等于没遮）

3. **加一道"结构化字段白名单"**：埋点 API 只接受 `&[(&str, &str)]` 形式的字段，
   键名不在白名单里就**直接丢掉**（不是脱敏，是不许进）。
   白名单：

   ```
   url, method, status, ms, bytes, host, path, shape, code,
   channel, source, kind, unit, remaining, used, total,
   key_fp, cred_len, cred_source, attempt, index, count,
   file, dir, reason, err_kind, level, session, stage
   ```

   **凡是叫 `key` / `token` / `secret` / `password` / `cookie` 的，一律不在白名单里。**

### 决策 2：单点埋点 —— `fetch_once` 是 9 个渠道的唯一出口

**这是整个方案性价比最高的一步。**

`app/core/src/fetch.rs:727` 的 `fetch_once()` 是全部 9 个内置渠道**唯一**的 HTTP 出口：

```
fetch_all（并发 9 渠道）
  └─ fetch_channel（按 attempt_order 依次试多个域名）
       └─ fetch_once ← ★ 在这里埋一次，9 个渠道全覆盖
            ├─ 建请求（GET/POST、Authorization/Cookie/UA、额外头）
            ├─ req.send() ──────────── 状态码 / 超时 / TLS 错误
            ├─ read_body_capped ────── 字节数 / 超限 / 读失败
            ├─ serde_json::from_slice ── 不是 JSON / 解析失败
            └─ def.extract(&body) ───── 业务失败 / 解析出的值
```

**在 `fetch_once` 的五个分支各埋一行 L2，全渠道一次覆盖。**
不需要去改 9 个 extractor，也不需要去改 `providers.rs`。

> 精确一点说：`fetch_once` 是**内置 9 个渠道取余额**的唯一出口。
> 签到（`checkin.rs:898`）、自定义渠道（`custom.rs`）、价目表（`models.rs:555`）、
> 汇率（`fx.rs`）、凭据续期（`workbuddy.rs:1514` / `qoder.rs:498`）各有自己的 HTTP 路径，
> 各自补一个埋点即可（见 5.4 与 6.4）。

**收益**：从"8 个渠道没日志"变成"9 个渠道全有 HTTP 细节"，
工作量是**改一个函数**，不是改九处。

### 决策 3：错误码表 —— 界面和日志共用一套

解决 S5（用户报的那句话在日志里搜不到）。

**规则：界面上显示的每一句"出错原因"，背后都有一个码；日志里必须有那个码。**

用户报"它说凭据失效" → support 让他抄一下码 → `grep E_AUTH_401` 就能定位。

这样做的额外好处：界面上"凭据失效 / 登录过期 / 没配置密钥 / 接口结构变了"这四句话
今天混在一堆自然语言里，**用户分不清该做什么**。有了码，就能同时做两件事：
界面上按码渲染不同的行动建议，日志里按码聚合统计。

**不要**为此引入新依赖 —— 一张 `const` 表 + 一个 `fn` 就够。

### 决策 4：会话 ID + 一键诊断包

**会话 ID**：启动时生成一个 8 位随机串，写进启动横幅，之后每行都带。
用户报问题时只要说"会话 4s3f9a2c"，就能精确定位那一次运行。

**诊断包**（一键导出）解决"用户要手动复制 600 行"这个摩擦：

```
点「导出诊断包」→ 生成一个 .zip（或单个 .txt）→ 路径直接弹出来
```

内容：

| 块 | 来源 |
|---|---|
| 环境快照 | 复用 `startup_banner` 的内容（版本 / 盘符 / 环境变量 / 已装客户端） |
| 体检结果 | 复用 `run_diagnostic` 的报告（**现在是两套产物，合并成一份**） |
| 事件日志 | 最近 30 分钟的全部事件，或最近 2000 行 |
| 失败现场 | 若有失败，附带失败前后的上下文块（3.3 里的那种） |
| 脱敏说明 | 一行"本包已脱敏，但请仍当作敏感信息处理" |

**"体检 + 日志合并成一份"是重点**：现在用户要贴两样东西（体检报告 + 日志），
support 也要人工对。合并成一份，用户只贴一样。

### 决策 5：分级 + 环形缓冲（磁盘只留值得留的）

见 3.3。补充两点：

- **内存环形缓冲**用 `VecDeque`，容量按"条数 × 平均行长"算，**固定上限 16MB**。
  不能无界 —— 挂件是 7×24 常驻。
- **落盘时带上缓冲区的上下文**：失败事件落盘时，把缓冲里它**前 20 条 / 后 5 条**一起写。
  这就是"现场"的意思 —— 单看"HTTP 401"没用，
  看"401 之前我们换过域名、换过凭据"才知道是谁的问题。

### 决策 6：注入类操作单独一档（爆炸半径最大的地方）

`inject.rs` 往**别人的软件**里写配置，失败了不是"数字不对"，是"Trae 打不开了"。

这类操作必须记，而且要记全：

| 记什么 | 为什么 |
|---|---|
| 目标客户端 + 目标文件路径 | 知道动的是谁 |
| 备份目录 | 出事要能回滚 |
| 改了哪些键（**键名 + 新旧值**，值走白名单） | 知道改了什么 |
| 校验结果（读回来是什么） | 知道写成功没有 |
| 回滚结果（回滚了没有、回滚后校验过没有） | 知道现在安不安全 |
| 幂等判定（这次是不是"没变化所以没写"） | 区分"写了"和"跳过" |

**必须记"没变化"那一种** —— 用户说"我什么都没干它自己坏了"，
日志里只有"跳过（无变化）"才知道真相。

## 5. 落地清单（分五期）

### 第 0 期：把洞补上（半天，**必须先做**）

| 编号 | 改动 | 文件 |
|---|---|---|
| 0.1 | `redact()` 的判据反转 + JWT 规则 + 全小写长串 | `core/src/diaglog.rs` |
| 0.2 | `redact_keyed_values()` 扩键名表 + 支持 JSON 形态 | `core/src/diaglog.rs` |
| 0.3 | 限流键加上范围（`(scope, key)` 组合） | `core/src/diaglog.rs` |
| 0.4 | 补单测：JWT 必须遮、`{"accessToken":"x"}` 必须遮、`?key=` 必须遮、全小写长串必须遮 | `core/src/diaglog.rs` |

> **验收**：拿一批真 token（JWT / base64 / 带 `=` 的 / 全小写的）跑一遍 `redact`，
> 断言**一个都不出现在输出里**；再拿一批路径 / 域名 / UUID 跑一遍，断言**一个都没被误伤**。
> 这两条断言要同时成立 —— 只满足前一半的脱敏会把最有用��信息也毁掉。

### 第 1 期：结构化 + 单点埋点（2~3 天）

| 编号 | 改动 |
|---|---|
| 1.1 | 新增 `Event` 结构与 `emit_event()` 入口；`write` / `write_keyed` 保留为兼容层，内部转成事件 |

## 6. 详细设计

### 6.1 事件 API

```rust
// app/core/src/diaglog.rs

/// 级别。
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum Level { Env, Decision, Wire, Result }

/// 一次事件。字段走白名单：键名不在白名单里直接丢弃（不是脱敏，是不许进）。
pub struct Event<'a> {
    pub level: Level,
    pub scope: &'a str,      // fetch / wb / inject / checkin / db / ui
    pub channel: Option<&'a str>,
    pub stage: &'a str,      // http / parse / snapshot / cred / backup / verify / rollback
    pub code: Option<&'a str>,   // E_HTTP_401 …
    pub fields: &'a [(&'a str, &'a str)],
}

/// 记一条。自由文本字段（`msg`）走 redact；结构化字段（`fields`）走白名单。
pub fn event(scope: &str, ev: Event<'_>);

/// 兼容层：老代码继续用 write / write_keyed，内部转成事件。
pub fn write(scope: &str, msg: &str);
pub fn write_keyed(scope: &str, key: &str, msg: &str);
```

**为什么保留兼容层**：34 个调用点不用一次全改。
先加新的（`event(...)`），再逐步把老的换掉 —— 每换一个都是净收益。

### 6.2 脱敏规则表

| 输入形态 | 处理 | 例 |
|---|---|---|
| JWT（`a.b.c` 三段，每段 ≥ 8） | **遮** | `eyJhbGci…` → `«secret len=216»` |
| ≥32 字符含数字或大写 | **遮** | `sk-abc…` → `«secret len=40»` |
| ≥32 字符**全小写** | **遮**（现在漏了） | `abcdef…` → `«secret len=32»` |
| `key=value` / `key: value` | **遮 value** | `api_key=xxx` → `api_key=«secret len=8»` |
| JSON 形态 `"key": "value"` | **遮 value**（现在漏了） | `{"accessToken":"x"}` → `{"accessToken":"«secret len=1»"}` |
| `?key=xxx` / `?token=xxx` | **遮 value** | `?key=abc` → `?key=«secret len=3»` |
| `Authorization: Basic xxx` | **遮**（现在只认 Bearer） | → `«secret len=16»` |
| URL 路径段 | **不遮** | `…/v2/billing/meter/get-user-resource` 保留 |
| 域名 / 文件名 | **不遮** | `api.trae.cn` 保留 |
| UUID | **不遮** | `5f2b9c1e-…` 保留 |
| HTTP 状态码 / 短错误码 | **不遮** | `HTTP 401 code 10085` 保留 |
| Windows 路径 | **不遮** | `D:/Programs/WorkBuddy/WorkBuddy.exe` 保留 |

**验收方式**：一张"必须遮 / 必须留"各 20 条的对照表，做成单测。
**这两列都要全绿** —— 少遮一条是事故，多遮一条是把线索毁掉。

### 6.3 错误码表（初稿）

| 码 | 含义 | 界面给用户的建议 | 记什么细节 |
|---|---|---|---|
| `E_NO_CRED` | 没配任何凭据 | 去渠道卡填一把 | 渠道、类型 |
| `E_CRED_UNREADABLE` | 凭据管理器/文件读不到 | 打开一次客户端 | 读失败的路径、错误 |
| `E_CRED_EXPIRED` | 凭据被平台拒绝 | 重新登录一次 | 状态码、凭据来源 |
| `E_HTTP_4xx` | 客户端错误 | 看具体码 | URL、状态码、耗时 |
| `E_HTTP_401` / `E_HTTP_403` | 未授权 | 重新登录 | URL、状态码、凭据来源、响应摘要 |
| `E_HTTP_429` | 限流 | 等一会儿 | URL、重试建议 |
| `E_HTTP_5xx` | 服务端错误 | 稍后再试 | URL、状态码、耗时 |
| `E_TIMEOUT` | 超时 | 检查网络/代理 | URL、耗时、预算 |
| `E_TLS` | 证书校验失败 | 检查代理/系统时间 | 域名 |
| `E_BODY_NOT_JSON` | 响应不是 JSON | 接口结构可能变了 | 状态码、**响应前 200 字符**（脱敏后） |

| `E_DB` | 数据库错误 | — | 表名、错误 |
| `E_INJECT_*` | 写第三方配置失败 | 见各自码 | 客户端、文件、阶段 |

**`E_BODY_SHAPE` 记"顶层键名列表"** 是重点：
接口改了字段名时，这是唯一能看出"原来叫 X 现在叫 Y"的线索，而且**不含值、不泄密**。

| # | 标准 | 怎么验 |
|---|---|---|
| A1 | 任何渠道取数失败，日志里能看到 URL、状态码、耗时 | 断网 / 改一个域名试 |

## 8. 风险与红线

| 风险 | 对策 |
|---|---|
| **日志泄密** | 第 0 期先修脱敏；结构化字段白名单；`redact` 双向对照表测试；诊断包页脚写明"仍当作敏感信息处理" |
| **日志量撑爆磁盘** | 成功不落盘；内存环形缓冲固定 16MB；磁盘多代滚动有硬上界；写失败熔断 |
| **日志拖慢取数** | IO 全在后台线程；单行长度上限；节流按 (范围,渠道,阶段) |
| **日志变噪音，真线索被埋** | 分级 + 落盘只留"值得留的"；`workbuddy.rs` 那 29 处顺带收敛（见下） |
| **用户被"要不要开日志"烦到** | 默认档就够用；详细日志是**默认关**的开关 |
| **为了日志改坏业务代码** | 埋点必须是**旁路**：写日志失败、字段超长、缓冲满，都不能影响主流程 |

### `workbuddy.rs` 那 29 处怎么办

**不是删，是收**。那一路的埋点是"过程流水"，日志已经被淹了。
建议：

- 把 29 处按 §3.1 的四层归类，**L0/L1 保留**（那是真正有排查价值的环境与决策）
- **L2 过程流水降级**成"只在失败时才记"（现在的 `write_keyed` 节流已经做了大半，
  但因为限流键漏了渠道维度，实际上没节流成功 —— 第 0 期的 0.3 修好后它会自然收敛）
- 最终目标：那一路从 29 处降到 **10~12 处**，但**信息密度更高**

## 9. 明确不做的事

| 不做 | 理由 |
|---|---|
| 引入 `tracing` / `log` 等日志框架 | 目标是"贴一段文本回来"，人眼可读 > 需要工具解析 |
| 结构化 JSON 落盘 | 同上；且 JSON 会被现有 `redact` 漏掉更多形态 |
| 记录用户的每一次点击 / 窗口操作 | 这是余额监控挂件，不是行为审计 |
| 把日志上传到服务器 | 项目原则：**无遥测、无云同步**。日志只留在本机，用户自己决定给不给 |
| 记录完整响应体 | 体积大 + 泄密面大。改成"状态码 + 字节数 + 顶层键名列表" |
| 给每个 extractor 单独加日志 | `fetch_once` 单点埋点已经覆盖；再分散只会更乱 |

## 10. 一句话总结

**现在的日志是"半边"的**：WorkBuddy 那一路很细，其余 8 个渠道和整个注入模块几乎是空白，
而这两块恰恰是最难查的。

**方案的核心是四步**：

1. **先补洞**（第 0 期，半天）—— 脱敏有洞、限流键漏渠道维度。**不做这步，后面全是白干。**
2. **单点埋点**（第 1 期）—— `fetch_once` 是 9 个渠道唯一的 HTTP 出口，
   在那里埋一次，8 个渠道的空白一次补齐。改一个函数，不是改九处。
3. **分级 + 环形缓冲** —— 成功的事件不落盘、只进内存；一旦失败，把**失败前后的上下文**一起落盘。
   这样"日志量"和"信息量"不再对立。
4. **错误码 + 诊断包** —— 界面和日志共用一套码（用户报一个码我就能定位），
   体检和日志合成一份，用户只贴一样东西。

**做完之后的标准是**：用户报"某个渠道取不到数"，
support 让他点一下「导出诊断包」，拿到的那一份文本里能直接看出
**是环境不对、凭据不对、接口变了、还是我们自己的 bug** —— 不用再追问第二轮。

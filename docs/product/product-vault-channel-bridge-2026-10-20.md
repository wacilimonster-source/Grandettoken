# 产品设计 · 密钥箱与渠道密钥互通

> 2026-10-20 · 依据本机代码实读(0.1.47)+ Windows 凭据管理器实况

## 0. 先说人话

**现在**:渠道密钥和密钥箱是**两个互不相通的池子**。

- 渠道密钥:一个渠道一把,存在凭据管理器的 `TokenScope` 服务下,键名 = 渠道 id。
- 密钥箱:自由平台 + 标签,存在 `TokenScope:vault` 服务下,键名 = 随机 uuid。

用户想"把渠道密钥存进箱子"、"用箱子里的钥匙喂给渠道"、"知道某个箱子里哪把正在被哪个渠道用",**现在一件都做不到**。

**要做成什么**:一个渠道的密钥**有且只有一个来源**,但这个来源可以是"直接填在渠道卡上",也可以是"引用密钥箱里的某一条"。**同一把密钥不存两份**,改了箱子里的那把,渠道立刻跟着变。

## 1. 现状:两套并行的存储

| | 渠道密钥 | 密钥箱 |
|---|---|---|
| 凭据管理器服务名 | `TokenScope` | `TokenScope:vault` |
| 键名(account) | 渠道 id,如 `4sapi` | 随机 uuid(v4 形状) |
| 索引在哪 | 无(渠道 id 本身就是键) | SQLite `vault_items` 表 |
| 索引字段 | — | `id, platform, label, hint, note, created_at, updated_at` |
| 界面 | 渠道卡上的输入框 | 设置页「密钥箱」标签页 |
| 能引用对方吗 | ❌ | ❌ |

**为什么现在是两个池子**:`secrets.rs` 的注释写得很清楚 ——

> 密钥箱用**另一个服务名**:与渠道密钥分开,删渠道密钥不会碰到密钥箱里的条目,反之亦然。

这是**有意为之的隔离**(防止"删渠道密钥"顺手删了箱子里的一堆条目),不是遗漏。但它把"互通"这个需求整个挡在外面了。

## 2. 问题拆解:「互通」其实是四个不同的动作

用户嘴里说的是"互通",拆开看是四件不同的事,难度差别很大:

| # | 动作 | 用户会怎么说 | 难度 |
|---|---|---|---|
| A | **存进箱子**:把渠道上填的密钥,顺手在箱子里也存一份 | "这把我也要存一份" | 中 |
| B | **引用**:让渠道用箱子里的某一把,不再单独填 | "用我箱子里的 4SAPI 主号" | 中 |
| C | **查引用关系**:看某把箱子里的钥匙正被哪些渠道用 | "这把给谁用了?" | 中 |
| D | **换池子**:把渠道现有的密钥整体搬进箱子 | "我不想在两处填" | 低(是 A 的特例) |

**核心判断**:真正的价值在 **B(引用)**。A 只是"存两份",反而制造了**两份不同步的真相**——改了箱子那把,渠道还在用旧的那把,用户以为改了其实没改。

所以设计的主线是 **B**,A/C/D 是围绕 B 的配套。

## 3. 核心设计:渠道密钥的「来源」抽象

### 3.1 数据模型:把"值"和"引用"分开存

**现状**:渠道密钥 = 凭据管理器里 `TokenScope/<渠道id>` 的一串明文。

**新设计**:渠道密钥变成一个**三元组**:

```
(渠道 id, 值来源, 值)
```

- 值来源 = `inline`(直接填在渠道卡上)或 `vault:<uuid>`(引用箱子里的某一条)
- 值本身**永远存在凭据管理器里**,不落 SQLite、不进配置文件

### 3.2 凭据管理器里的布局(这是最关键的一处)

```
TokenScope/4sapi            ← inline 时:渠道 id 直接存值(保持现状,老用户零迁移)
TokenScope:link/4sapi        ← vault 引用时:存 "vault:<uuid>" 这个指针
TokenScope:vault/<uuid>      ← 箱子里那把的真实值(位置不动)
```

**为什么不统一成一种**:老用户已装 0.1.47,`TokenScope/4sapi` 里已经有值。
统一布局就要迁移 —— 迁移本身能做(读旧值写新位置),但**多一次动用户密文的机会**。
而"两种布局并存"其实很自然:`inline` 保持原样,`vault:` 是新增的一种。

### 3.3 引用怎么解析

```
读渠道 4sapi 的密钥:
  1. 读 TokenScope/4sapi
     2. 若不存在 → 该渠道没配密钥
     3. 若值以 "vault:" 开头 → 取出 uuid,读 TokenScope:vault/<uuid>
        4. 那条也不存在 → 引用断了(箱子里那条被删了)
     5. 否则就是 inline 的值本身
```

**断链怎么处理**:引用指向的箱子条目被删时,渠道卡要显示
「引用的密钥箱条目已删除」,**而不是**"没配密钥"或"凭据失效"——
这两种说法会把用户引到完全错误的方向(去渠道卡重填,而不是去箱子看)。

## 4. 界面设计

### 4.1 渠道卡上:密钥来源二选一

```
4SAPI                                    [已配置]
┌──────────────────────────────────────────────────┐
│ 密钥来源                                            
│ ( ● ) 直接填在这里    [ sk-••••••••3f2a ]        │
│ ( ○ ) 从密钥箱选       [ 4SAPI / 主号      ▾ ]     │
│                                                   │
│                    [ 保存 ]  [ 清除登录 ]          │
└──────────────────────────────────────────────────┘
```

- 选「直接填」→ 就是现在的输入框,**零学习成本**
- 选「从密钥箱选」→ 下拉列出该平台的箱子条目;没有该平台条目时给一个
  「去密钥箱新建」的跳转(而不是空下拉)

### 4.2 渠道卡上:引用时的行内操作

选了箱子条目之后,渠道卡上多两处:

```
│ 密钥来源                                              
│ ( ● ) 直接填在这里                                    │
│ ( ○ ) 从密钥箱选    [ 4SAPI / 主号  ▾ ]  [换一把]     │
│                     正在使用 ·••••••••3f2a · 建于 10-12 │
└──────────────────────────────────────────────────┘
```

- **换一把**:不离开渠道卡就能换引用(下拉直接切)
- **显示正在用的那把的尾号**:让用户确认"对,就是这把"

### 4.3 渠道卡上:存进箱子

密钥箱里已有该渠道条目时,给一个反向入口:

```
4SAPI  [已配置]
  ...
  ✓ 这把钥匙也在密钥箱里(4SAPI / 主号)  [ 改用那把 ]
```

「改用那把」= 切到引用模式。**一键完成互通**,不用去两个页面。

### 4.4 密钥箱里:显示"被谁用了"

```
4SAPI                                    2 把
─────────────────────────────────────────────
主号 · ••••••••3f2a                        
  建于 10-12 · 备注:充值用的那个              
  🔗 正被 4SAPI 渠道使用                     
     [ 复制 ] [ 显示 ] [ 改 ] [ 删 ]         

备用号 · ••••••••9c1b                        
  建于 10-15                                  
  (未被任何渠道使用)                           
     [ 复制 ] [ 显示 ] [ 改 ] [ 删 ]          
```

**引用关系怎么查**:不能靠"扫所有渠道的密钥值比对"—— 密钥不落库,查不了。
必须**建一张索引**:记录「哪些渠道引用了哪个 uuid」。这张表不含密钥值,
只含 id 之间的引用关系,可以安全落 SQLite。

### 4.5 删箱子条目时的拦截

删除一个**正被渠道引用**的箱子条目时,必须拦:

```
┌──────────────────────────────────────────┐
│ 这把钥匙正被 1 个渠道使用:                 │
│   · 4SAPI                                 │
│                                          │
│ 删掉它,4SAPI 就没密钥可用了。              │
│                                          │
│ [ 先把 4SAPI 改成用别的 ]  [ 仍然删除 ]   │
└──────────────────────────────────────────┘
```

「仍然删除」允许存在(用户可能就是要断掉),但**必须显式二次确认**,
且删完之后渠道卡立刻显示"引用的条目已删除",而不是静默变成"没配密钥"。

## 5. 关键裁决(✅ 2026-10-20 用户已全部批准)

**用户裁决:全部按建议来。**

| # | 问题 | 裁决 | 理由 |
|---|---|---|---|
| 1 | 互通的主线是「存两份」还是「引用」? | ✅ **引用** | 存两份会造出两份不同步的真相,用户以为改了其实没改 |
| 2 | 引用关系怎么存? | ✅ 单独一张引用表(SQLite) | 密钥值不落库,只能靠 id 关系反查 |
| 3 | 凭据管理器布局统一吗? | ✅ **不统一**,`inline` 保持原位 | 老用户零迁移;少一次动用户密文的机会 |
| 4 | 箱子条目被渠道引用时能删吗? | ✅ 能,但要二次确认并说清后果 | 拦死会让用户没法清理;静默删会让人一头雾水 |
| 5 | 一个渠道能引用多把吗? | ✅ **不能**,一把 | 渠道的凭据候选顺序是它自己的语义(手动 → 桌面端 → 网页),多把会让优先级说不清 |
| 6 | 同一个箱子条目能被多个渠道引用吗? | ✅ **能** | 「主号」这种标签天然就是一物多用 |
| 7 | 引用模式下,手动粘贴的密钥还要留吗? | ✅ 引用模式下**清掉** | 留两份又是两份真相;但要先提示"切换会覆盖你手填的" |

### 实现时对设计师的一处偏离(第 2 条)

原稿写的是"引用指针存凭据管理器(`TokenScope:link/<渠道id>`)",**实装改成存 SQLite 表**。
理由:反查「这把被谁用」需要按 `vault_id` 查渠道,放凭据管理器就只能把每个渠道的条目
全读一遍(O(n) 次系统调用);放表里一句 `SELECT` 就够,且**表里不含任何密钥值**,
安全口径不变。

一致性后果(已接受):用户删掉箱子条目后,表里的引用会**留着变成断链** ——
这正是裁决 4 想要的「显示引用的条目已删除」,而不是静默退回"未配置"。所以**不清理断链**。

## 7. 不做什么(明确排除)

- **不做「一个箱子条目同时当多个渠道的密钥」** —— 裁决 6 说能,但那是"同一把钥匙喂给多个渠道",
  在密钥箱里已经是"多平台多标签"的自然用法,不必再抽象一层。
- **不做密钥同步/云同步** —— 与项目既有的"无云同步"红线一致。
- **不做箱子的导入导出** —— 导出即明文外泄,风险与收益不成比例。
- **不改凭据管理器的服务名** —— `TokenScope` / `TokenScope:vault` 是已装用户的既有落点,
  改名会让所有已存密钥"消失"。

# 产品设计 · 引用索引的对账机制

> 2026-10-21 · 覆盖体检报告的 N07 / N13 / N16 / N17 / N29 / N30
> 面向:不看代码也能读懂

## 0. 一句话

**我们存了两份"谁用了哪把钥匙"的记录,但从来没核对过它们。**

## 1. 先讲清楚现在有两份记录

想象一个图书馆:

- **书架** = Windows 凭据管理器。书(密钥)真的在这儿。
- **索引卡** = 我们自己的数据库里那张小表。它只是抄了一份"谁借了哪本"。

具体到这个功能:

| | 存在哪 | 里面是什么 | 角色 |
|---|---|---|---|
| **指针** | 凭据管理器 `TokenScope:link/<渠道>` | 一行字:`vault:<条目id>` | **真凭实据** |
| **索引** | SQLite 的 `vault_refs` 表 | 两列 id | **为了查得快而抄的副本** |

为什么要有索引?因为要回答"这把钥匙被哪些渠道用着",如果只有指针,就得把每个渠道
挨个问一遍;有了索引,一句 SQL 就够。

**问题在于:抄的那份,从来没人去核对。**

## 2. 于是索引会说谎 —— 五条走偏的路

| # | 什么情况下会走偏 | 用户看到的 |
|---|---|---|
| ① | 切引用时,指针写成功、索引写失败 | 索引还指着**旧**那把 → "正被谁使用"说错 |
| ② | 取消引用时,指针删了、索引没删 | 索引说"有人用",其实没人 |
| ③ | 删自定义渠道时忘了清索引 | 渠道都没了,密钥箱还显示"正被 custom-1 使用" |
| ④ | 数据库被删/重装,凭据管理器还在 | 索引全空 → 密钥箱列表**一片空白**,可那些密文其实还在硬盘上 |
| ⑤ | 凭据管理器被清(比如手动删过),数据库还在 | 索引说"有人用",渠道其实已经没钥匙了 |

**最难受的是 ④**:密文还在,但列表空着 —— 你**看不到也删不掉**它们。
这不是显示问题,是"数据在但够不着"。

## 3. 还有一个更直接的坑:删之前不拦

删一把正被渠道用着的钥匙时,现在是**浏览器里**靠索引判断"有没有人在用"。

于是:

- 索引读失败 → `loadVaultRefs()` 把错误吞掉、列表清空 → **提示彻底消失,直接删掉**
- 索引本身已经不准(上面五条)→ 拦了个寂寞
- 后端其实早就写好了 `vault_ref_channels` 这个命令,**但前端一次都没调用过**

删完之后渠道当场变"引用的条目已删除"。用户不知道发生了什么。

## 4. 修法的核心:定一条规矩

> **书架永远说了算。索引卡只是副本,随时可以重抄。**

这一条定下来,后面全是它的推论。

### 动作 1:启动时重抄一遍索引

应用启动后(界面已经能用了,不挡着),后台做一件事:

```
把每个渠道的指针挨个读一遍
  → 有指针的,写进索引
  → 没指针的,索引里不留
一次替换掉整张表
```

这样无论上次是怎么走偏的(①②③⑤),**下一次启动就自己好了**。

代价:启动时多 N 次凭据管理器读取(N = 渠道数,现在 10 个左右)。
放在界面渲染之后、后台线程里,用户感觉不到。

### 动作 2:抄索引失败,不能让正事失败

现在"切到引用"这条命令里,指针和索引是**一起成败**的 —— 索引写失败会让整个操作报错,
可指针其实已经写成功了。用户看到"切换失败",但实际已经切过去了。

改成:

- 指针写成功 = **操作成功**(用户要的事办成了)
- 索引写失败 = 记一个"待重抄"的标记,下次启动自动修
- **绝不**因为索引写失败就说"操作失败"

### 动作 3:要紧的判断,直接看书架

"这把钥匙正被谁用着"这个问题,在**删除前**必须问准。所以:

- `vault_delete` 自己在后端**扫真实指针**得出清单,不查索引
- 有渠道在用 → 返回"正被 XX、YY 使用",要求前端二次确认
- 前端确认后带一个"我确认了"的标记再调一次

索引读坏了也不影响这个判断 —— 因为它压根不看索引。

### 动作 4:切引用前,先确认密文真的在

现在切到某个箱子条目之前,只查了索引(`store.vault_get`),**没查凭据管理器里
密文还在不在**(`secrets::vault_get`)。

这两处是会分开的:比如你在 Windows 凭据管理器里手动删过那一条。

后果很具体:代码会先把**你手填的那把删掉**,然后切到一个死引用上 ——
渠道从"能用"变成"没密钥"。这是**操作把人搞坏了**。

改成:动任何东西之前,先确认密文在。不在就明确报错,让人重新录入。

## 5. 还要顺手修的三处

| # | 问题 | 修法 |
|---|---|---|
| **N16** | 删掉箱子条目后,渠道卡还显示"正在使用这把",最长 60 秒才变 | 删完立刻刷新渠道卡 + 作废取数的 5 秒缓存 |
| **N29** | 新建自定义渠道时不清引用指针,而且 id 会复用被删渠道的 → 新渠道继承了上一个渠道的孤儿指针,用的是**别人的密钥** | 写值前先清引用(和 `set_key` 一样);id 改成单调递增不复用 |
| **N30** | `vault_ref_channels` 注册了没人调;`vault_ref_of` 零调用 | 前者用在动作 3 里做真拦截;后者用在动作 1 的重抄里 —— 死代码变成了对账的主力 |

## 6. 做不到的部分(必须说清)

**凭据管理器里的"孤儿指针"扫不出来。**

如果某个渠道被删了(比如 N02 之前删的),它的指针还留在凭据管理器里。
我们能读到"某个渠道的指针",但**没法列出"凭据管理器里一共有哪些渠道的指针"** ——
keyring 这个库不提供枚举能力。

所以:

- 已知渠道(内置 + 当前配置里的自定义渠道)的指针 → **能对账**
- 已删除渠道留下的孤儿指针 → **扫不到,只能等以后清**

对孤儿的处理:N02 已经修了"删渠道时一并清",所以**以后不会再有新的孤儿**。
历史遗留的那几个,只能在用户碰巧重建同名 id 时被覆盖 —— 这是 N29 要修 id 复用的原因。

**诚实地说**:这一版之后,索引对"活着的渠道"永远是真的;对"已经删掉的渠道"
可能还留着幽灵行。幽灵行不会造成实际危害(那些渠道已经不在列表里),
但如果将来出现,得靠一次性的手工清理。

## 7. 验收清单

在真机上逐条确认:

1. 切到引用 → 密钥箱立刻显示"正被 XX 使用"
2. 取消引用 → 那句话立刻消失
3. 删自定义渠道 → 密钥箱里不再有"正被 custom-N 使用"
4. **手动删掉数据库文件** → 重启后密钥箱列表**正常显示**(重抄把索引建回来了)
5. 删一把正被用的钥匙 → **一定**弹确认并点名是哪个渠道
6. 切到一把密文已经不存在的条目 → 明确报错,**不会**把手填的那把搞没
7. 新建自定义渠道(即使复用了旧 id)→ 用的是**刚填的那把**,不显示"引用密钥箱"
8. 删箱子条目 → 渠道卡**立刻**显示"引用的条目已删除"(不用等 60 秒)

第 4 条是这次的核心:**把数据库删掉,索引能自己长回来。**

WorkBuddy 自动打卡失败 —— 根因与修复

排查报告 · 2026-10-20 · 全部结论来自本机真实数据库、真实文件与真实 HTTP 调用

根因一句话:WorkBuddy 的取数与签到用的是两份不同的凭据。 取数优先用「桌面端凭据」(还活着),签到却只用「网页 Cookie 会话」(已于 10-18 过期)。 于是同一个渠道,余额天天出数,打卡天天报 auth。

不是你操作的问题,是代码路径不一致。Trae 正常,正是因为它只有一条凭据路径,没有这个分叉。

2. 关键发现:两条路径用了两份凭据

2.1 取数路径(能出数)

core/src/fetch.rs 的 credentials(),对 AuthKind::WebSession 渠道按这个顺序收集候选:

① secrets::get(def.id)          // 用户手动粘贴的访问密钥(本机没有)
② read_desktop_tokens()          // ★ WorkBuddy 桌面端凭据(含 refresh 续期)—— 优先!
③ web_src(def.id)                // 网页 Cookie 会话 —— 兜底

源码注释写得很清楚(fetch.rs:1036):

// WorkBuddy:**桌面端凭据优先**。它比网页会话活得久(accessToken 28 天、
// refreshToken 30 天,且可续),而网页会话是约 7 天的绝对 TTL ——
// 2026-10-15 之后连续三天取不到数,就是网页会话到期、而界面仍报"已登录"。

2.2 签到路径(报 auth)

src-tauri/src/lib.rs 的 checkin_credential():

checkin::CheckinAuth::WebSession => {
    let session = wb_session_of(app, def.id)      // ← 只读网页 Cookie,没有桌面端这条
        .ok_or_else(|| format!("未登录 {} 账号 · 在渠道卡上登录一次", def.name))?;
    Ok(checkin::Cred::Web(session))
}
这就是根因。同一个渠道:
  • 取数会去读桌面端凭据(活着,能续期)→ 出数正常
  • 签到只读网页 Cookie(死了)→ 每次 401 → 归为 auth
而 checkin::Cred 枚举里根本没有「桌面端凭据」这一档 —— 不是配置问题,是这条路径从来没接上。

3. 实测证据:两份凭据的真实状态

3.1 网页 Cookie 会话:被网关拒绝(实测)

把挂件 WebView 里的 session / session_2 Cookie 解出来(WebView2 的 v10 加密, DPAPI 解 Local State 密钥后 AES-256-GCM),直接打接口:

目标结果
POST www.workbuddy.cn/v2/billing/meter/checkin-activity-statusHTTP 401 openresty/APISIX 网关页
POST www.codebuddy.cn/v2/billing/meter/checkin-activity-statusHTTP 401 同上
POST www.codebuddy.cn/v2/billing/meter/get-user-resourceHTTP 401 同上
401 + HTML 网关页 ≠ 业务错误。这是认证层就被挡下了(APISIX 网关),连业务代码都没进。 所以 Outcome::AuthNeeded 判得完全正确 —— 凭据确实失效了,不是误判。

顺带排除了两个可能:① 不是接口迁移(否则会 404);② 不是路径写错(新旧两代路径全试过,全是 401)。
一个必须说准的细节:这份 Cookie 还没到期,但已经被拒。 Cookie 库里 session/session_2 的签发时刻是 2026-10-18 18:03:51、 到期时刻 2026-10-25 18:03:51 —— 也就是说 10-19 / 10-20 两次签到报 auth 时, 它在纸面上是有效的,却仍然被网关 401。

所以「等 7 天 TTL 到期」不足以解释这次失败 —— 更可能是这份会话在服务端已被作废 (例如 10-19 02:34 桌面端刷新凭据后,同账号的网页会话被顶掉)。 本次没有取到能定论这一点的证据,所以不写死原因。

但结论不变、而且更强:网页会话这条路既会到期、又会被提前作废,且都不可预测 —— 把签到押在它上面本来就不该。桌面端凭据(可续期、实测 200)才是正确的凭据来源。

3.2 桌面端凭据:活着(实测)

从 %LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\workbuddy-desktop.info 读凭据: 它被 $wbEncrypted 信封加密,用桌面端自己的 loggerGet() 取 atRestSecretKey, sha256 派生密钥、按 AAD 转录解开,拿到 accessToken 后直接打接口:

目标结果
POST /v2/billing/meter/get-user-resourceHTTP 200 {"code":0,"msg":"OK",…TotalCount:27…}
POST /v2/billing/meter/checkin-activity-statusHTTP 200 {"code":0,"data":{"active":true,"today_checked_in":true,"streak_days":15,…}}
这两条 200 是本报告最关键的证据。它同时证明三件事:
  1. 桌面端凭据现在就能用(余额能取、签到接口也能打);
  2. 签到接口没坏,路径也对 —— 坏的只是签到用的那份凭据;
  3. 换用桌面端凭据后,打卡立刻就能成功。
另外接口自己说 today_checked_in: true, streak_days: 15 —— 用户其实每天在桌面端正常签到, 只有挂件这一侧因为拿不到凭据而空转。

3.3 顺便验证:签到接口对请求头不挑剔

用桌面端 token,故意换五种请求头组合打签到接口,全部 200:

AuthorizationUser-AgentX-Client-Platform结果
Bearer ✅桌面端 UA有200
Bearer ✅浏览器 UA有200
Bearer ✅桌面端 UA无200
Bearer ✅浏览器 UA无200
Bearer ✅不带无200

结论:决定成败的只有那份 Bearer 凭据,头部细节不是问题。修复不需要动请求构造。

4. 修复方案

一句话修法:让签到和取数用同一份凭据。 把 checkin_credential() 的 WorkBuddy 分支改成「先桌面端、后网页 Cookie」, 与 fetch.rs::credentials() 的顺序对齐。

4.1 具体改法(三处)

#文件改动
1core/src/checkin.rs CheckinAuth 加一档,或让 Cred::Web 承载桌面端 token。
注意:Cred::Web 目前把非 cookie: 前缀的值当 Bearer 发 —— 桌面端 token 正好走这条路, 但必须去掉 desktop: 前缀(那是取数层的标记,带进请求头会变成 Bearer desktop:xxx,必然 401)
2src-tauri/src/lib.rs checkin_credential() WorkBuddy 分支:先试 workbuddy::desktop_tokens()(取第一个可用), 拿不到再退回 wb_session_of()。两处都拿不到才报「未登录」
3src-tauri/src/lib.rs checkin_state() 的 note 文案 把「在渠道卡上登录一次」改成同时提桌面端:「打开一次 WorkBuddy 桌面端(它会自动续期), 或在本卡片点「重新登录」」—— 与 fetch.rs::expired_credential_msg 同口径

4.2 伪代码

// checkin_credential(),WorkBuddy 分支
checkin::CheckinAuth::WebSession => {
    // ① 桌面端凭据优先 —— 与取数同口径(它活得久、能续期)
    if let Some(tok) = workbuddy::desktop_tokens(now_ms()).into_iter().next() {
        return Ok(checkin::Cred::Web(tok));   // 不带 desktop: 前缀
    }
    // ② 退回网页会话(手动粘贴的密钥 / 浏览器 Cookie)
    let session = wb_session_of(app, def.id)
        .ok_or_else(|| "未检测到 WorkBuddy 登录 · 打开一次桌面端即可(或在本卡片点「重新登录」)".to_string())?;
    Ok(checkin::Cred::Web(session))
}
两个实现细节别踩:
  • 前缀必须剥掉。desktop_tokens() 返回裸 token,但取数层会自己加 desktop: 前缀再解析;签到层不要加前缀。
  • 只取第一个候选在当前是够的,但更好的是401 时轮换下一个候选 —— 本机就有 3 份桌面端凭据(一份是 6 月的明文备份)。取数路径已经是「按 401 换下一份」, 签到路径照抄即可,别只试第一份就放弃。

4.3 为什么不改用「手动粘贴访问密钥」那条路

v0.1.40 的排查已经取证过:官方「访问密钥」页创建按钮对免费账号是门控的 (i18n 明文「该功能为标准版以上用户可用」)。所以不能把修复押在那条路上 —— 桌面端凭据才是免费账号唯一稳定可用的凭据。

5. 顺带发现的两个次要问题

5.1 拿不到凭据时「不留痕」,导致失败被静默吞掉

10-16 / 10-17 workbuddy 完全没有流水记录 —— 不是失败,是一次都没试。

机制(从代码路径读出):run_checkin() 在拿到凭据之前就 ? 提前返回 ——

let cred = { … checkin_credential(&h, def) … .await.map_err(…)?  };   // ← 这里 Err 就直接返回
…
let store = lock_rw(&state.store);
store.record_checkin(…)                                              // ← 落库在后面,到不了

而节拍器对这个 Err 只做一件事:

if let Err(e) = run_checkin(&app, def.id, false).await {
    eprintln!("签到 {} 跳过: {e}", def.name);   // 绿色版从托盘启动,这行没人看得到
}
后果:凭据拿不到的那几天,在 checkin_log 里是空白 —— 与「没到点」无法区分。 用户(和排查的人)只看到「今天没签上」,却看不到「今天连试都没试」。 这与项目自己立过的红线相冲突(「取数失败绝不渲染成余额归零」的同族问题: 失败必须留下痕迹)。

建议:凭据获取失败也要落一条流水(outcome=no_cred 之类),让「没试」和「试了失败」在数据里可区分。 这条与 Qoder 的 10:00 跨日设计(见 design-qoder-channel-2026-10-20.html §3.3)无关, 但同属「签到状态要能还原现场」这一类,可以一起改。

5.2 复登放行只覆盖了 auth,没覆盖「凭据换源」

wb_finish_login() 会清掉当天的 auth* 让用户能补签 —— 这个逻辑是对的。 但它只挂在「网页登录成功」这一个事件上。如果修复后改用桌面端凭据, 就没有这个事件了(桌面端续期是后台静默发生的)。

建议:把「清 auth 放行补签」也挂到「桌面端凭据刷新成功」的时刻上, 或者更简单 —— 在 checkin_credential() 成功拿到桌面端凭据时,顺带清一次当天的 auth*。

6. 验证清单(修完这么验)

#验什么怎么验期望
1签到能拿到凭据点渠道卡「领积分」不再报 auth;返回 200 或 already
2落库正确查 checkin_logoutcome 为 claimed / already,不再 auth
3到账对比签到前后余额+100 积分(接口 today_credit 也是 100)
4桌面端没装时不崩临时改名 auth 目录退回网页会话或如实报「未检测到登录」,不 panic
5不重复领同一天连点两次第二次 already,接口幂等不重复发币
6余额不受影响看快照照常每分钟出数(签到是写操作,不该动取数)

7. 结论

判定
Trae 是否正常正常。10-18/19/20 连续三天 claimed,凭据路径单一,没有分叉
WorkBuddy 打卡是否正常不正常。连续 3 天 auth,根因是签到路径没接桌面端凭据
是否用户操作问题不是。余额一直在正常出数,说明账号与桌面端都是好的
修复难度低。不动请求构造、不加依赖、不新增接口 —— 只是把凭据来源对齐(约 20 行)
修复后能否立刻生效能。桌面端凭据现在就是活的,实测签到接口 200
一句话提醒:这个 bug 的形态是「同一渠道的两条路径用了两份凭据,其中一份悄悄死了」。 只要两者不共用同一个凭据解析入口,以后还会以别的形式复发(比如手动密钥过期、桌面端卸载)。 根治做法是让签到复用取数的凭据候选链,而不是各写一份。

# 豆包工作自动签到移除复盘 —— 710010702「系统错误」

**日期**:2026-11-14
**结论**:豆包工作渠道的自动签到(claim)被豆包服务端整体拒绝(业务码 **710010702**),
直连路线无解,随 **v0.3.44** 移除该功能;渠道保留**取数**(体验额度读数,一直正常)。
指纹保鲜模块 `core/src/doubao_client.rs` 保留 —— 服务于活动接口的取数请求。

---

## 1. 现象与证据链

**挂件侧**(诊断日志 `%APPDATA%\com.wacil.tokenscope\diag.log`,2026-11-14):

```
00:31:49  动作 status · HTTP 200 · 平台码 0        ← 查状态正常:任务在、未签、可领 +200
00:31:50  动作 claim  · HTTP 200 · 平台码 710010702 ← 领取被服务端拒绝
00:31:50  动作 status · HTTP 200 · 平台码 0        ← 回查:仍是未签 → "claim 未见生效"
          (00:36 / 00:41 / 00:51 / 01:06 同样,共 5 次,全部 710010702)
```

- 同一份 Cookie 打 detail(取数/状态)一直是 `code 0` 正常出数 —— **不是登录态问题**。
- 数据库 `checkin_log`:豆包渠道**从未有过 `claimed` 记录**。2026-11-13 是 11 次
  `no_cred`(未登录),用户登录后 12:34 的 `already · 200` 是用户当天已在客户端自己签过。
- 挂件发起的 claim 是 11-14 00:31 第一次真正发生,一发就被拒。

**官方客户端侧**(用户实测,2026-11-14 凌晨):

- 本机安装的豆包工作版(DoubaoWork.exe)FileVersion = **2.36.15**(Chromium 内核
  147.0.7727.149,与挂件 10-19 抓包 UA 里的内核一致)。
- 用户在豆包工作版里手动点「领取」同样失败,界面文案**「签到失败,请稍后重试」**。
- 用户确认 **11-13 在客户端里签到是正常的** —— 即服务端收紧发生在 11-13 → 11-14 之间。

**服务端请求形状**(从本机 DoubaoWork 2.36.15 自带资源取证):

- 客户端自带 SDK(`local_webcontents/.../73978.js`)里,官方 claim 请求体是
  `{scene, biz_params, AgwCommonParam}`;detail 是 `{campaign_group_code, AgwCommonParam}`。
  `AgwCommonParam` 由原生层构造,本地拿不到 schema。
- 客户端 web 层仍有 `version_code:20800` 的用法(web 平台常量),说明 20800 本身
  不是"过期数字",而是**服务端对请求整体形状的校验**在拒绝非官方形状的写请求。

采取完全不同的路线 —— CDP 驱动**真实客户端**点按钮,自己不伪造任何请求,理由是

AGENTS.md 2.4 的高权限能力(启动并驱动其它客户端),且在官方客户端自身被拒的
当天同样救不了;**本版未采用**,留作后续选项(需要用户明确拍板)。

## 3. 曾做的修复(保留在库里)

指纹保鲜 `core/src/doubao_client.rs`(v0.3.44 内实现):

- 运行时探测本机豆包客户端(原版 Doubao 优先,DoubaoWork 兜底;路径全部来自
  环境变量,不写盘符),读 PE 版本资源(version.dll FFI,零新依赖)派生
  `version_code` 与 UA 版本段;Chrome 内核读客户端 `User Data/Last Version`。
- 探测失败回落 2026-10-19 抓包钉值(会写诊断日志说明)。
- 双向验证:编码规则有 Golden(2.32.6→23206 / 2.36.15→23615),畸形版本拒收
  (四段 / 段越界),兜底 UA 与钉值逐字节一致有测试钉住。
- 实测:修复部署后 detail(取数)在新指纹下正常出数,未破坏读路径。

修复没能治好 claim —— 因为官方客户端自己的请求也被拒,这不是挂件请求形状的问题,
是服务端在拒绝(活动故障或风控批次)。但它让挂件的取数指纹保持新鲜,
若未来读路径也被收紧,不会重演"钉值腐烂"这一课。

## 4. 移除的范围

| 保留 | 移除 |
|---|---|
| 渠道卡、登录窗(`doubao_web.rs`)、手动粘贴 Cookie、体验额度取数与展示、登出清会话、指纹保鲜 | `CHECKINS` 表的 doubao 项、`CheckinAuth::DoubaoWeb` / `Cred::Doubao`、checkin 凭据链、`parse_doubao` 及其状态机测试、claim 专用常量与地址 |

「今日签到 已签/未签 · 可领 +200 额度」的展示摘要保留在取数里 —— 用户需要知道
去客户端里领。

## 5. 经验教训(已同步 AGENTS.md)

1. **凡是跟客户端版本联动的参数,抓包钉死必腐烂**(10-19 钉、10-24 死,一个月)。
   `doubao_client` 的运行时探测是这个教训的落地。
2. **直连伪接口是在跟平台风控打追赶战**:今天免签名,明天 a_bogus/msToken/AgwCommonParam。
   依赖单一路径的功能要有"平台一收紧就下线"的预案,而不是无限堆修补。
3. **门禁测不出服务端的变脸**:mock 桩与 Golden 全绿不影响服务端开始拒人。
   对"写路径依赖第三方平台配合"的功能,失败面要在设计期就承认。

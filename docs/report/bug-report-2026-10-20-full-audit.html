#01P0签到结束后，把一份"旧的"整份设置写回磁盘，用户刚改的设置被吞掉

app/src-tauri/src/lib.rs:2324-2380

现象你在设置页改了东西（比如关掉某个渠道、把刷新间隔改成 5 分钟），几秒后设置又变回原样；面板上显示的是新值，但重启后又"变回去"了。
原因签到任务开始时把整份设置拍了个快照存进变量（let mut cfg = lock_rw(&state.config).clone()）。签到要走 2~3 个网络请求，每个最多等 20 秒，这期间是30~70 秒的窗口。你在这段时间里改了设置，签到结束后执行 cfg.save(&store) —— 写回去的是那份旧快照，把你的改动整个盖掉了。内存里的 state.config 同样被换回旧值。
修复后保存时只改"签到进度"这一个字段，绝不整份覆盖。签到写盘前先读一遍当前的配置，只把 checkin[id] 合并进去再存。这样无论签到跑多久，你在设置页做的任何改动都不会丢。顺带把这段写盘也挂到已有的串行闸上，避免和普通保存互相覆盖。
#02P0WorkBuddy 续期时，如果上游没换新令牌，代码反而把旧令牌擦成空

app/core/src/workbuddy.rs:1439-1455

现象WorkBuddy 桌面端能正常续期，但续期一次之后，自动续期能力就断了 —— 用户以为能"永不过期"，实际用着用着就掉线，得手动去桌面端重新登录。
原因函数注释白纸黑字写着「空 refresh 表示上游没轮换，沿用旧的」，但代码直接 refresh.unwrap_or("") —— 上游没给新令牌时，它把空字符串写进去，原来那份还能用的 refresh token 被彻底覆盖没了。注释承诺的"沿用旧的"根本没实现。
修复后上游没给新令牌时，先读回已存的那份，把旧令牌原样留着。写盘时改成"有新值用新值，没新值读旧值顶上"，让代码和注释一致。用户的自动续期就不会莫名其妙断掉。
#03P0WorkBuddy 取数的时间窗开了 100 年，把过期旧包也算了进来

app/core/src/providers.rs:893-902

现象挂件里显示的 WorkBuddy 积分，比 WorkBuddy 官方网页控制台上的数字偏大，用户对不上账。
原因取数请求体的时间窗结束时间是 现在 + 100 年。而同一个函数上方的注释明确写着"窗口开太宽会把上几个周期用剩的旧包也捞回来，本周期发放/已使用就会比官方口径大（实测宽 7 天多出 4 个包、400 积分）"—— 注释写的规则，代码自己没遵守。项目里另一处 workbuddy::billing_body() 用的是上游真实的 36.9 天窗口，两者对不上。请求体里的 Status（[0,1,2,3] vs 上游 [0,3]）和 PageSize（200 vs 100）也不一致。
修复后取数请求体和上游完全对齐：时间窗 36.9 天、Status [0,3]、PageSize 100。两处 body 合并成一个公共函数，以后不会再走偏。修完之后，挂件上的数字和官方控制台对得上了。
#04P0诊断日志不遮盖带点的令牌（也就是 JWT）

app/core/src/diaglog.rs:183, 214-217

现象用户按官方指引把诊断日志发到群里问问题，日志里可能明文躺着 access token，等于把账号凭据贴给所有人看。
原因遮盖规则里有三条"不遮"的例外，第三条是"含 . 的串当域名放过"。但 JWT 令牌天然带两个点（头.载荷.签名），所以整条令牌会被当成"域名"原样写进文件。代码注释里写"真令牌极少含 ."——这个前提是错的，每个 JWT 都有点。目前所有调用方都还好没直接传令牌进去，所以今天没出事，但这个"保险丝"其实是断的。
修复后先按"这串像不像令牌"判断，再考虑是不是路径/域名。具体做法：点数 ≥2 的长串一律按令牌遮盖；"像路径"这个判断改成看形状（域名只有一个点），而不是"有没有点"。再补一条 JWT 专用规则（三段用点连起来）强制遮盖。保险丝接上了，以后任何调用方手滑都不会泄密。
#05P0诊断日志的限流漏了"渠道"这一维，多个渠道一失败，日志就被刷爆

app/core/src/diaglog.rs:314-352（调用点 fetch.rs:1959, 2049）

现象诊断日志文件一天涨到几 MB，稍微一两周就把有用的历史记录冲掉；而且日志里看不到"这个错误重复了多少次"这句本来最有用的话。
原因限流表 SEEN 的键只有"事件名"（比如 "channel"），没带渠道 id。而实际调用是 write_keyed(渠道id, "channel", ...)——渠道 id 被当成了"分组名"丢掉了。结果：9 个渠道共用同一张限流表。渠道 A 写完，渠道 B 因为消息内容不一样被判成"状态变了"，于是每 60 秒每个渠道都写一行，限流等于没开。
修复后限流键改成"渠道 id + 事件名"组合。这样每个渠道各算各的：同一个渠道重复报错会被正确合并成"又重复了 N 次"，日志量回到设计目标的 1/9 左右，重复次数的统计也终于能用了。

#06P1界面上的时间全错了：把"秒"当成了"毫秒"

app/src/app.js:96-100（调用点 809-811、822-825）

现象"今日数据自 16:40 起"这类提示、最近变动台账里的每一行时间，显示的都是 1970 年附近的离谱时间。
原因后端给的时间戳是 Unix 秒（快照表里存的就是秒），而 fmtClock() 写的是 new Date(ts) —— JavaScript 的 new Date(数字) 一律当成毫秒。同一个文件里另外三个时间函数（toDateInput、fmtDay、relTime）都老老实实乘了 1000，只有它漏了。
修复后乘上 1000 再交给 Date。修完，"今日数据自 10:23 起"和变动台账里的时间会变成真实时刻，用户终于能对上自己什么时候开的机、什么时候充的额度。
#07P1Qoder 早上开机时不会补签当天的积分

app/core/src/checkin.rs:280-291

现象Qoder（国际版 + 国内版）每天早上开机（比如 8 点）时不会补签，要等到当天 10 点之后才行；如果电脑晚上关机，第二天 10 点前才开机，就只能等下一个周期，当天的 100 积分直接没了，也没有任何提示。
原因Qoder 的"周期"是 10:00 → 次日 9:59。判断"该不该签"的代码 due_now() 拿的是"北京时间的当天已过分钟数"，跟 10:00 + 抖动 比。早上 8 点时当天已过 480 分钟，阈值是 600 多分钟，比不过 → 判定"还没到时间"。但早上 8 点其实还在上一个周期里（周期到 9:59 才结束），本该补签。Trae/WorkBuddy 用的是 0 点翻日，早 9 点开机被判成"该补签"是对的 —— 只有 Qoder 这个非零翻日点的渠道漏了。
修复后改成"距离本周期开始过了多少分钟"来比，而不是"今天过了多少分钟"。对 0 点翻日的渠道这个公式和现在完全等价（现有测试照过），对 Qoder 则能正确识别"还在昨天那个周期里"。开机补签恢复了，当天积分不会再白丢。
#08P1Qoder 把"上上个周期已领过"当成了"今天已领过"

app/core/src/checkin.rs:601-639

现象界面显示"今日已签"，但今天的积分其实没领到。代码里把当天标成"已完成"，当天再也不会重试。
原因Qoder 返回的是一个活动列表，里面同时躺着往期活动和本期活动。代码遍历时只要看到任何一个 CLAIMED 就置 already = true，完全不看这个活动是不是属于当前周期（返回体里明明有 startAt/endAt）。项目自己的单测 qoder_claimable_wins_over_older_claimed 就证明了"往期 CLAIMED 和本期 CLAIMABLE 同时存在"是常态。
修复后先按当前周期的时间窗把活动筛一遍，只看窗内的。窗外的活动既不算"可领"也不算"已领"。这样"今日已签"这句话才是真的，当天该领的积分不会因为往期记录而被误判跳过。
#09P1YAML 里"引号 + 行内注释"没脱引号，导致同一个模型被写了两遍

app/core/src/yamledge.rs:448-467

现象往 DSH 写模型配置时，如果你的 cordis.patch.yml 里写了 - id: "claude-sonnet-5" # 我自己加的，挂件找不到它，就再追加一条同 id 的。DSH 按 id 取第一条，你更新模型的结果被静默丢掉，配置文件里还多了一条重复。
原因strip_scalar() 脱引号的条件是"整串以引号结尾"。加了行内注释后整串变成 "claude-sonnet-5" # 我自己加的，不以引号结尾 → 走不到脱引号分支 → 注释被切掉了，引号却留了下来。于是 id 变成了 "claude-sonnet-5"（带引号），跟要写的 claude-sonnet-5 对不上。
修复后先切掉行内注释，再判断要不要脱引号。这样带注释的条目也能被正确识别，DSH 配置里不会再出现重复 id，你的模型更新能真正生效。
#10P14SAPI 兜底分支不检查业务返回码，"失败"被当成"余额正常"显示

app/core/src/providers.rs:130-157（对比 168-169）

现象4SAPI 返回 {"code": false, "data": {"total_available": 93500000}} 这种"业务失败"时，界面照样显示 ¥187.00，还会被写进历史快照，把"申请跳升"检测器也带偏。

#11P1「跳过此版本」会被下一次保存设置悄悄撤销

app/src-tauri/src/lib.rs:186-194（前端 app.js:3592）

现象用户点了「跳过此版本 0.1.48」，之后改了个无关设置（比如换个刷新间隔），0.1.48 的更新提示又冒出来了。
原因后端合并配置时的规则是"前端没传（null）才用后端的值"。但前端启动时读了一次配置就再也不更新 skippedVersion（跳过后只是调了个后端命令，本地那份还是旧的）。所以下次保存时前端会传旧的非空值，后端就老老实实用了旧值 —— 跳过记录被覆盖。这正是代码注释里说"已修（报告 P1-3）"的那个坑，只是没修干净。
修复后这两个字段（跳过版本、上次检查时间）完全由后端说了算，前端传什么都以后端为准。跳过的版本再也不会被覆盖，更新提示不会反复骚扰用户。
#12P1设置保存失败时，内存里的新值已经生效了，磁盘上的还是旧值

app/src-tauri/src/lib.rs:76-94

现象保存设置失败（磁盘满、数据库被锁）时，弹了错误提示，但挂件的行为已经按新设置在跑，重启后又变回老样子。用户会以为"保存失败 = 什么都没变"，其实变了一半。
原因save_config_off_main() 里，mutate(&mut cfg) 是直接改内存里那份配置（cfg 就是 state.config 的锁守卫），然后才去落库。落库失败时函数返回错误，但内存已经被改了。更糟的是自定义渠道那条路：写失败后代码会把凭据删掉，内存里却还留着那个渠道，内存和磁盘对不上。
修复后先在副本上改、落库成功后再发布到内存。落库失败时内存保持原样，界面提示和实际状态一致，不会出现"显示一套、运行另一套"的分裂状态。
#13P1前端"保存失败就回滚"这个操作，实际上什么都没回滚

app/src/app.js:2491-2531（调用方 2902-2918、3023-3031 等）

现象保存设置失败，弹了"保存设置失败"的红色提示，但开关还是停在改后的位置、隐藏的渠道还是消失着。用户被界面骗了 —— 注释里自己写着"界面等于在骗人（F6）"，但这个回滚是无效的。
原因所有调用方都是先改状态再调用保存（CFG[key] = !CFG[key] 然后才 saveCfg()）。而 saveCfg() 里的备份是在函数入口才拍的 —— 这时候新值已经写进去了。所以"回滚"是把新值又赋回去，等于没回滚。注释还专门解释了"快照必须是拷贝"——拷贝是对的方向，但拷的是已经改过的状态。
修复后让调用方在改动之前拍快照，把快照传给保存函数；或者把"改"和"存"合成一步。保存失败后开关会真的弹回去、渠道会真的回来，界面和实际状态一致，用户不会再被误导。
#14P1"这个渠道用过几把密钥"按密钥去重，两个渠道共用一把密钥就数错

app/core/src/fetch.rs:2198-2210（自定义渠道同形：2268-2283）

现象如果同一把 API key 同时填给了两个渠道（很常见，比如 4SAPI 和一个指向同一站点的自定义渠道），两个渠道会显示一样的密钥数量，而且永远错下去。
原因缓存的键只有"密钥指纹"，但查出来的值是 fingerprint_count(渠道id) —— 按渠道统计的。第二个渠道命中了第一个渠道的缓存，直接拿了别人的数字。而且这个缓存永不失效。
修复后缓存键改成"渠道 id + 密钥指纹"。每个渠道各算各的，共用一把密钥也不会串。数字对得上，缓存还能继续当性能优化用。
#15P1自定义渠道的颜色没做转义，能往界面里塞进任意样式

app/src/app.js:296-302（配合 app/core/src/custom.rs:73-87）

现象在自定义渠道里把颜色填成 red">
原因整个前端里所有来自接口的字符串都老老实实过了 esc()，只有 c.color 是直接拼进 style="..." 属性的。后端的 CustomChannel::validate() 校验了名字、地址、路径，唯独没校验颜色（注释只写了"#rrggbb"，代码没强制）。

#16P1上游轮换过的新 refresh token 存下来了，但从来没人用它

app/core/src/workbuddy.rs:1200-1209、1260-1271

现象WorkBuddy 桌面端登录能撑约 28 天，之后自动续期就断了 —— 而代码注释里明明写着"续期成功就等于永不过期"。
原因上游每次续期都会换发新的 refresh token、把旧的作废（项目注释里写明了这一点）。续期成功后新 token 存进了凭据管理器，但读取那一档时只取了 s.access，s.refresh 存了但从来不用。下一次要续期时，代码还是拿桌面端文件里那个已经被作废的旧 token 去刷，必然失败。而且每次失败都会踩到 30 分钟冷却，之后一直拿同一个死 token 重试 —— 有些服务端还会因为"重放已用过的令牌"把整个令牌族作废，连用户在 WorkBuddy 官网的登录都可能掉。
修复后续期时把"已存的新 refresh token"和"桌面端文件里的旧 token"一起当候选，优先用新的那个。轮换链就接上了，"永不过期"的承诺成立，用户不用每隔 28 天跑去桌面端重新登录。

现象每分钟一次的自动刷新和你手动点的「领积分」撞在同一个分钟时，会发出两个续期请求。
原因续期动作外面没有互斥锁，冷却机制只在失败之后才起作用。两个请求抢同一个 refresh token：一个成功并轮换了，另一个要么失败（还会把整个区域的 30 分钟冷却污染掉），要么两个都成功、第二次把刚存好的新 token 又作废了。

修复后把上一条（脱敏后的）文本也存下来并打印它。用户一眼能看出到底是哪件事在重复。
#45P3自定义渠道的探活地址没校验，{key} 没转义，还允许明文 http

app/core/src/custom.rs:73-87、151-181

原因三个小问题叠一起：① 校验只看 url 不看 probeUrl，探活模式下能存进一个根本不可用的地址，每轮都在失败；② 请求体里的 {key} 直接贴原始密钥，密钥里带引号就会生成非法 JSON，用户只看到"响应不是合法 JSON"；③ 允许 http://，而每个请求都带 Authorization: Bearer 密钥 —— 明文发出去，局域网里就能嗅到。
修复后校验实际生效的那个地址；{key} 按 JSON 规则转义；默认要求 https。自定义渠道不会存进去一个必然失败的配置，密钥不会因为一个引号就整条链路报错，Bearer 也不会明文裸奔。
#46P3查看/清空诊断日志时在异步命令里做阻塞文件操作

app/src-tauri/src/lib.rs:3442-3477

原因这两个命令直接 fs::read_to_string 整个日志文件，而同文件里其它重 IO 命令都规规矩矩用了 spawn_blocking。日志大的时候会卡住运行时线程。
修复后包一层 spawn_blocking。看日志时界面不会卡住，和其它命令的做法也统一了。
#47P3"体检报告"读的是数据库里的旧配置，不是正在跑的配置

app/src-tauri/src/lib.rs:1402-1405

原因其它命令都从内存里读配置，只有体检命令重新去数据库读一份，还用 unwrap_or_default() 把解析错误吞成"全部默认"。
修复后统一从内存读，并把解析错误显示出来。体检报告说的就是挂件现在的实际状态，不会给出误导性的结论。
#48P3多显示器下窗口位置总是被拉回第一块屏

app/src-tauri/src/lib.rs:1892-1919

原因保存的位置不完整落在任何一块屏内时，直接用 monitors[0] 夹。而 Windows 上 available_monitors() 的顺序不保证第一块是主屏，也不保证是用户原来那块。
修复后选"离保存位置最近"的那块屏。多屏用户重启后窗口还在自己那块屏上。
#49P3保存设置时不跑一遍范围检查，导致当前值和重启后的值不一致

app/src-tauri/src/lib.rs:180-247 + app/core/src/config.rs:230-263

现象比如把"危险阈值"设得比"警告阈值"还低，当前界面按新值算颜色，重启后被夹回一个不一样的值。
原因Config::sanitize() 只在读的时候跑，set_config 写的时候不跑。间隔设成 0 也会变成忙轮询。
修复后保存前也调一次 sanitize()。存下去的和当下生效的永远一致，不用等到重启才"变"。
#50P3WorkBuddy 登录监听可能同时跑两个

app/src-tauri/src/lib.rs:597-645、655-687

现象快速关掉再打开登录窗口时，会同时有两个监听在每 6 秒打一次 WorkBuddy 的真实 HTTP 请求，还可能重复触发刷新。
原因"用户关掉了窗口"这个标记只每 1.2 秒查一次，在这 1.2 秒的空隙里重新打开，旧监听就永远看不到关闭标记。
修复后用自增的"代次号"代替布尔标记。任何时候只会有一个监听在跑，请求量减半，事件不重复。
#51P3YAML 里出现重复键时，工具改的是第一个，YAML 实际生效的是最后一个

app/core/src/yamledge.rs:46-48

原因Node::get() 用 find 返回第一个匹配；标准 YAML 语义是"后者覆盖前者"。
修复后要么在解析时直接拒绝重复键，要么让 get 返回最后一个。手改过的配置也不会出现"改了没反应"。
#52P3回滚时会把备份目录里的所有文件都写回客户端目录

app/core/src/inject.rs:1035-1067

原因回滚是"把备份目录里有什么都复制回去"，而不是"把当初写过的文件恢复回去"。备份目录里多出的杂物会被一起塞进第三方客户端的配置目录。带清单的变体（restore_layered）做对了，平铺的那个没有。
修复后备份时记一份文件清单，回滚严格按清单来。回滚只动我们改过的文件，第三方目录保持干净。
#53P3写 JSON 时会重排第三方文件的缩进风格

app/core/src/inject.rs:760-811

原因读进来解析成 JSON 再序列化回去，缩进固定 2 空格、末尾不补换行。用户原本 4 空格的配置文件会被整份重排，diff 大得吓人。
修复后检测并保留原缩进和末尾换行。改动最小化，用户看得懂我们到底改了哪几行。

## 一、结论

**本地网关有可复现的 bug。现有门禁全绿，但覆盖不足，不能据此认定网关没有问题。**

优先关注：

1. **上游错误帧绕过脱敏**：合成密钥会原样到达网关输出。若真实上游在报错时回显凭据，局域网调用者可能拿到上游凭据。
2. **搜索后重绘再保存，可能把其他模型无意下架**：只搜索、查看诊断，也会影响随后保存的模型许可。
3. **流式完成判断不严谨**：一个候选结束就可能把另一候选的截断判为成功；末帧同时携带正文和完成标志时，思考标签拆分会出错。
4. **异步刷新与用户配置混在同一个对象里整条回写**：源码可达路径显示，迟到刷新可能撤销刚保存的代理、端点、别名和关联密钥。生产 IPC 的受控竞争测试尚未运行。
5. **性能没有证据支持大重构**：本机小 JSON 回环的中位数额外转发耗时约 0.6 ms；SSE 行解析在有限样本中接近线性。更值得做的是响应缓冲保护、少做重复读取、避免诊断刷新重绘整个编辑页。

### 证据标签与严重度

- **R / 已运行复现**：本轮执行了真实维护源码或前端维护源码的隔离测试，并观察到现象。
- **S / 源码确认**：已追到可达入口、变化顺序和失败出口，但没有运行生产 Tauri IPC 或 Windows 凭据失败注入。
- **U / 待验证**：契约或真实运行证据不够，不作为确定 bug。
- **P1**：应优先修复的核心行为、保存一致性或安全边界问题。
- **P2**：条件性正确性、诊断或资源保护问题；不能把“非主路径”理解为无需修复。
- **P3**：低影响一致性问题。

本报告没有确认 P0。这个结论不等于已证明不存在其他高严重度问题。

## 二、范围、契约和方法

### 2.1 已锁定的行为契约

- 客户端继续使用 `/v1/chat/completions`，同时兼容无 `/v1` 前缀的路由；**Responses 只作上游选项**。
- 模型目录与推理连通性独立；外部模型 ID 是 `别名/裸模型ID`，上游接收裸模型 ID。
- 旧配置默认 Chat Completions。Responses 的单候选、函数工具及不保留加密推理状态等限制已有 README 披露，不作为 bug。
- 保留局域网监听；局域网模式必须鉴权。不能以“优化”之名改为仅回环。
- 上游密钥与网关密钥分离；错误、诊断和导出不能泄漏上游凭据。
- 写操作失败应保持一致状态并给用户可见结果；后台同步不应撤销期间已保存的用户设置。

单一事实源：`AGENTS.md` §5/§8.6、根 `README.md` 的“本地模型网关”、生产源码及 workflow。`DESIGN.md` 没有独立的本地网关/Responses 规范，不能把其中其他渠道的“网关”内容误当本模块契约。

## 四、缺陷清单

### G01 — P1 / R：上游错误输出绕过既有脱敏

**位置**：`app/core/src/gateway_proto/stream.rs:336-340`；`app/src-tauri/src/gateway_http/responses.rs:63-78`。

**条件与实际影响**：Chat 上游 SSE 在错误消息里回显密钥。错误分支直接序列化原对象，没有走 `openai_error_value`/脱敏。HTTP 200 的 error JSON 也直接读取返回。可能把上游凭据暴露给只持有网关密钥的调用者；没有观察真实凭据泄漏。

**复现**：喂入包含“Invalid key + 合成 sk 前缀字符串”的 SSE error，再结束。观察 `contains_synthetic_key=true`；同一字符串经现有错误信封函数处理后不再保留，证明是调用路径绕过而非脱敏函数不会识别。正确脱敏断言变红。

**建议**：在协议错误出口统一清洗错误字段，并覆盖 SSE/200 JSON/Responses error。不要对正常模型正文做盲替。正式验证还应在真实 HTTP 输出中搜索合成敏感串，检查响应、诊断和日志。

### G02 — P1 / R：筛选重绘后保存，无意取消其他模型许可

**位置**：`app/src/gateway-view.js:217`、`:287-295`、`:815-823`、`:1042-1057`。

**条件**：全允许模型 `gpt-4o-mini` 与 `deepseek-r1`；搜索 `deepseek`，刷新诊断造成重绘，再清空搜索、保存渠道。

**实际**：重绘只创建筛选匹配的复选框；清空筛选只能显示现存节点；保存从当前 DOM 生成完整许可列表：

```text
filter_after_redraw DOM=["deepseek-r1"]
filtered_save allowedModels=["deepseek-r1"]
```

用户没有明确取消另一个模型，却会使其不可调用。复现单独重复成立，正确行为断言变红。

**建议/回归**：完整许可状态与搜索显示分离，或完整生成节点、仅隐藏。覆盖搜索→重绘→清空→保存；另测明确取消一个模型必须生效，不能为防漏选而永远全选。

### G03 — P1 / R：多候选流有一个完成就判整流成功

**位置**：`app/core/src/gateway_proto/stream.rs:165`、`:220-228`、`:277-293`、`:371-378`。

**条件**：Chat 请求可使用多候选；首帧有 index 0/1 的正文，随后只有 index 0 给出 `finish_reason=stop`，index 1 截断。

**实际**：全局布尔 `finish_seen` 为 true，EOF 产生 `completed_cleanly=true`、`saw_error=false` 和 `[DONE]`，没有不完整错误。客户端以为第二候选也完整。正确行为断言变红。

**建议/回归**：按候选索引记录完成状态，至少所有已观察候选都须完成。完全未出现的候选需要把请求 `n` 带入验证，单独明确范围。Responses 明示只支持单候选，不能据此解释 Chat 的漏洞。

### G04 — P1 / R：末帧带正文时，思考标签拆分顺序错误

**位置**：`app/core/src/gateway_proto/stream.rs:371-422`。

**条件**：Auto 模式第一帧正文 `<thi`；第二帧正文 `nk>synthetic reasoning</think>OK` 同时 `finish_reason=stop`。

**预期**：推理为 `synthetic reasoning`，正文为 `OK`。**实际**：先结束切分器、再处理当前 delta，正文成为完整带标签串，推理为空。正确行为断言变红。

若末帧本身留下不完整标签，尾部还可能被放到完成帧之后输出。常见官方末帧 delta 为空，但兼容 chunk 没有必须为空的约束；不能把常见顺序当唯一合法顺序。

**建议/回归**：先处理本帧 delta，再刷尾部，最后输出候选完成标志；断言内容重组及帧顺序。

### G05 — P2 / R：HTTP 200 的错误 JSON 被返回并记成成功

**位置**：`app/src-tauri/src/gateway_http/responses.rs:63-78`；`gateway_http.rs:759-819`、`:998-1112`。

**条件**：非标准上游返回 200 和 `{"error":{"message":"synthetic upstream failed"}}`。正常 Chat JSON 读取分支不验证错误对象或完成结构。

**实际回环输出**：`status=200`、`diag_status=200`、`diag_error=None`，并在 error 对象中插入外部 model 字段。可能误导调用者重试、监控和“测连通”；正常联调 JSON 分支也直接设置 `ok=true`。

**建议/回归**：成功响应也检查非空 error 和基本补全结构，协议错误映射为 502，保留可理解且脱敏的摘要。检查不能误拒合法 usage/候选结构。该条为坏上游防护问题，不声称标准上游会正常这样返回。

### G06 — P1 / S：迟到刷新整条回写，撤销新配置/密钥关联

**位置**：`app/src-tauri/src/gateway.rs:494-524`、`:1035-1055`、`:930-936`、`:1019-1029`；快捷代理入口 `gateway-view.js:827-842`。

刷新先克隆包含用户配置的 `Published`，await 后仅凭 channel ID 整条替换。刷新期间快捷代理可保存新值；自动密钥同步也不受前端忙碌锁约束。旧结果能覆盖新 alias、proxy、Base URL、allowedModels 或 vault 关联，撤销已经提示成功的操作。

**建议**：刷新只提交它拥有的派生字段，并核对配置/凭据版本；目标改变时丢弃或重刷。不能靠把网络等待放进全局锁来“解决”，那会阻塞其他操作。

**待补测试**：屏障暂停旧 A 凭据/端点刷新→保存 B 与新代理→释放旧结果，断言 B 不被撤销；再测两轮逆序、下架及端点变化。生产 IPC 尚未执行。

### G07 — P1 / S：既有凭据变更失败，不恢复旧凭据

**位置**：`app/src-tauri/src/vault_sync.rs:102-115`；`app/src-tauri/src/lib.rs:2885-2912`；实时读取入口 `gateway_http.rs:299-309`。

先写凭据、后写 SQLite 索引；索引失败时仅新建条目尝试删除，更新已有条目不恢复旧凭据。用户看到“保存失败”，实际请求却已使用新凭据，尾号和更新时间仍是旧值。自动导入重试若发现凭据已相等，也可能不补写索引、不发刷新。

**建议/待验**：用可注入合成凭据后端保留旧状态，失败补偿或明确返回“部分生效”；测试 upsert 失败、补偿失败和第二次导入。不可使用真实 Windows 凭据做破坏性失败注入。

### G08 — P1 / S：配置损坏当作首次安装，自动启动可能覆盖原值

**位置**：`app/src-tauri/src/gateway.rs:186-192`、`:697-701`、`:737-746`；调用 `lib.rs:5955-5959`。

设置读取错误、解析错误通过 `.ok()` 折叠成缺省，初始化成功获得默认空渠道。自动启动绑定成功后保存默认设置，可能覆盖损坏但可恢复的原记录。不是“没有记录”和“读取失败”应有的区别。

**建议/待验**：只有无记录才默认初始化；读取/解析失败保留原值并提示，禁止自动保存。临时 DB 的坏 JSON、一次读取失败和首次安装三类夹具须分别验证。

### G09 — P1 / S：重启失败丢掉旧服务，前端可能仍显示运行

**位置**：`app/src-tauri/src/gateway.rs:774-782`；`gateway-view.js:991-1004`、`:1094-1095`。

先停止旧服务，再启动新参数。新端口被占、凭据读取失败或保存失败，没有恢复旧服务；前端只在成功后刷新状态，失败 toast 后可能仍保留旧 running=true。

**建议/待验**：预先完成可做的校验，定义失败恢复或明确“旧服务已停止”；失败也校准 UI。用临时端口 P 服务、测试占用端口 Q，验证 P→Q 失败后的真实服务与 UI。固定 120 ms 等待不是监听器释放证据。停止后已接收请求继续完成是 graceful shutdown 的合理行为，不另报 bug。

### G10 — P2 / R：400 修复把值错误当不支持，删除输出预算再请求

**位置**：`app/core/src/gateway_proto/request.rs:231-242`、`:277-287`；`gateway_http.rs:446-459`。

回环请求带 `max_completion_tokens=0`，上游返回参数值必须大于零的 400。修复器只看参数名位于名单，就删除再发：

```text
repair_budget calls=2 first_has_budget=true second_has_budget=false
```

原本应失败的请求变成使用模型默认预算的请求，可能带来意外输出/额度消耗。它不是已披露的 Responses 不支持参数主动转换。

**建议/回归**：值错误、业务约束错误不重试；只对明确“不支持/未知字段”修复，预算/stop 等约束特别保守。此项实际观察成立，但尚未单独执行“应不重试”的红色断言。

### G11 — P2 / R：客户端中途断开，诊断漏记

**位置**：`app/src-tauri/src/gateway_http.rs:645-688`。

诊断只在 unfold 读到终止/EOF/error 后记录，状态被 drop 没有收尾。真实回环读取第一段正文后关闭响应流，等待后诊断仍为空：`disconnect diagnostic_count=0`。

已确认的是漏诊断，**没有证明后台上游永久泄漏**：流被丢弃通常会释放上游连接。建议收尾显式区分“客户端取消”和“上游失败”，完成/取消只记一次；再测取消后的上游取消传播及不误计成功。

### G12 — P2 / S：合法 refusal 被诊断成零输出

**位置**：`gateway_proto/responses/output.rs:12-37`、`responses/stream.rs:147-155`；`thinking.rs:334-456`；`gateway_http.rs:473-495`。

拒绝内容正确保留为 refusal，但统计只看正文、推理、工具，故会提示“未返回文本或工具调用”。容易把正常拒绝误认为网关故障。应区分有效拒绝与真空输出，不把拒绝强行伪装成普通正文。待补 JSON/SSE refusal-only 与诊断联动测试。

### G13 — P2 / S：前端旧状态读取能覆盖新状态

**位置**：`app/src/gateway-view.js:163-178`、`:1087`、`:1106-1108`。

多轮读取结束后无条件赋全局 GW，没有统一请求代际；页面重复加载、快捷代理和返回状态可并发。旧读取晚到能画回旧渠道/代理/运行状态，后续操作也据旧 GW 决策。

建议统一响应版本/请求序号；旧读取成功或失败都不得覆盖较新结果。待补延迟 A→成功 B→释放 A 的前端测试。

### G14 — P2 / S：诊断/状态重绘丢失已有配置草稿

**位置**：`app/src/gateway-view.js:143-207`、`:544-557`、`:934-941`。

整页重绘只保存添加向导草稿和展开状态，没有保留已上架渠道的未保存 alias、URL、手动模型等；异步开始时捕获的添加草稿也可能覆盖等待期间新输入。输入框未因忙碌全部冻结。

建议诊断局部刷新，或明确保存完整当前草稿、焦点、选区；待补编辑中刷新与等待时继续输入测试。不要通过强行清空或禁止用户编辑掩盖问题。

### G15 — P2 / S：后台同步保存失败没有可见结果

**位置**：`app/src-tauri/src/gateway.rs:522-534`；`vault_sync.rs:130-138`。

导入/网关保存错误被条件分支忽略，原凭据操作可以成功返回；用户不知道自动同步未落地。建议凭据保存和网关同步结果分开，有 pending/error、可见错误和有界重试；待补仅网关保存失败的注入与重试恢复。

### G16 — P2 / S：上游 SSE 行/事件缓冲无限额

**位置**：`app/core/src/gateway_proto/stream.rs:35-38`、`:88-101`、`:126-153`、`:260-265`；`responses/stream.rs:233-243`。

无换行时 line_buf 一直追加，无空行时 data_lines 持续积累；请求 8 MiB 限额不限制上游响应。`non_sse_buf.len()<1024` 只在追加前判断，单条长行可越界。有限解析基准证明可处理长行，不是内存峰值测试，也不是 DoS 实证。

建议先定合法大工具参数兼容预算，再做行/事件限额、准确截断与可见错误；不能随意给很小上限截断合法补全。没有无限负载测试或攻击生产监听。

## 五、性能结果与优化资格

### 5.1 有限本机基准

测试为 **debug 构建、回环、免密合成渠道**，固定小 JSON 补全，连接预热，串行有限请求。非生产容量、非真实模型 TTFT（首字耗时），没有发布版 CPU/RSS 测量。

P50 是一半样本不超过的耗时，P95 是约九成五样本不超过的耗时。最终同轮观测如下；此前重复结果趋势一致：

| 路径 | P50 | P95 | 最大观测 |
|---|---:|---:|---:|
| 直接访问合成上游 | 0.357 ms | 0.483 ms | 0.654 ms |
| 经维护 HTTP 转发代码 | 0.918 ms | 1.212 ms | 1.530 ms |

中位数之差约 **0.561 ms**。不同测次差值约 0.56–0.61 ms。这是测次指标差，不是逐请求配对开销或生产性能保证。测试替身跳过真实鉴权/凭据 RPC，所以生产开销不能由此上推。

SSE 行读取器仅测长度增长趋势：64 字节分块，长行约 8/32/64 KiB，重复取中位数。最终耗时约 **148/616/1474 μs**；此前同条件约 **145/611/1237 μs**。总体随字节量近似线性，没有看到反复扫描累计整行的二次复杂度证据。该基准不是完整 JSON/SSE 转换吞吐或分配测量。

### 5.2 可考虑的局部优化

| 项 | 证据与收益 | 准入结论 |
|---|---|---|

## 六、已有合理保护与不应误报的行为

- 普通设置多数先写盘再换内存；下架失败不会先删除内存渠道。跨凭据/索引例外见 G07。
- 模型网络等待没有持有主要 inner/store 锁；本轮没有依据报告这些路径死锁。

2. 本轮新增的 30 个问题

P0 · 会悄悄改坏数据或弄丢凭据

N01P0新增引用模式下点「删除密钥」，密钥根本删不掉

app/src-tauri/src/lib.rs:338-376（delete_key）

现象渠道的密钥改成"引用密钥箱"之后，去渠道卡点「删除密钥」，弹了"已删除 XX 的密钥"，但这个渠道照样能取到数、照样能用。
原因密钥箱打通后，一个渠道的密钥有两个来源：直接填的（存在凭据管理器的 TokenScope/<渠道id>）和引用（存在 TokenScope:link/<渠道id>，值是 vault:<条目id>）。delete_key 只删了前者，没删引用指针。而读取时优先看引用，所以指针还在 = 密钥还在。
修复后删除密钥时把引用指针和索引行一起清掉。点「删除密钥」之后，渠道真的变成"未配置密钥"，取数立刻失败并如实告诉你原因。SQLite 里的 vault_refs 索引行也要跟着清，否则密钥箱列表还会说"正被这个渠道使用"。
N02P0新增删掉自定义渠道，密钥和引用都留在凭据管理器里

app/src-tauri/src/lib.rs:1453-1457（custom_remove）

现象删掉一个自定义渠道后，它的密钥还留在 Windows 凭据管理器里；密钥箱列表里还会显示"🔗 正被 custom-1 使用"，但 custom-1 这个渠道早就不存在了。
原因同 N01：只调了 secrets::delete()，没调 link_clear()，也没清 vault_refs 索引行。而且这里用的是 let _ = …，连删失败都被吞了。
修复后删除渠道时把三样都清干净：直接填的值、引用指针、索引行。密钥箱列表的"正被谁使用"就变成真的了，删除渠道后也不会有孤儿凭据留在系统里（这是一条凭据纪律问题）。
N03P0新增换密钥时先清引用后写值，中途失败 = 密钥配置全没了

app/src-tauri/src/lib.rs:319-328（set_key）+ app/core/src/secrets.rs:64-72

现象渠道本来在用密钥箱里的那把，用户改填一把新的。保存时如果失败，这个渠道就变成"既没有引用、也没有值" —— 什么密钥都没有了，用户得从头再来一次。
原因代码顺序是"先清引用 → 再写新值"。而写值这一步会因为密钥为空被拒（secrets::set 里 if key.is_empty() { return Err("密钥不能为空") }）—— 也就是说，最常见的一次失败，正好发生在引用已经被清掉之后。用户看到"保存失败"，但原来那份能用的引用已经没了。
修复后改成"先写新值、再清引用"。读取时优先看引用，所以"两份都在"的短暂状态完全无害；一旦写值失败，旧的引用还在，渠道继续正常工作，不会丢配置。
N04P0新增【回归】签到把旧配置整份写回磁盘 —— 这次改得更频繁了

app/src-tauri/src/lib.rs:2496、2571、2575（run_checkin）

现象你在设置页改了东西（关掉某个渠道、改刷新间隔），几秒后设置又变回原样。这个问题是上一轮的 #01，一直没修。
原因签到开始时把整份设置拍快照（let mut cfg = lock_rw(&state.config).clone()），结束时 cfg.save(&store) 把这份旧快照整份写回去。你在签到跑的那 30~70 秒里做的任何修改都被盖掉。
本轮变严重了：节拍器从"启动后先睡 5 分钟"改成"启动立刻跑一轮"（checkin_tick_once 挪到了 sleep 前面），签到跑得更频繁，撞上这个窗口的概率明显变大。
修复后保存时只改"签到进度"这一个字段，绝不整份覆盖。写盘前先读一遍当前配置，只把 checkin[id] 合并进去。签到跑多久都不影响你改设置 —— 而且现在签到跑得更频繁了，这个修复的收益比上一轮更大。

P1 · 用户肉眼能看见的错

N05P1新增读密钥没有走新的统一入口：8 处仍在用旧接口，同一张卡片两套真相

secrets.rs 的 resolve() 注释写着"所有要用这把 key 发请求的地方都该走这里"——但有 8 处没走

现象渠道引用了密钥箱里的密钥之后：
· 点「显示密钥」→ 说"还没有保存密钥"（可卡片上的掩码明明显示着尾 4 位）
· 点「复制密钥」→ 同样失败
· 模型页 → 读不到 4SAPI 的密钥，价目表和可用模型都出不来
· 引用模式的自定义渠道 → 根本不发请求，一直"未配置密钥"
· 「测试连接」→ 说"还没填密钥"
· 体检报告 → 说"还没填密钥"
· 隐藏的渠道 → 显示"未配置密钥"
原因8 处还在直接调 secrets::get(渠道id)：
lib.rs:284 自定义渠道指纹 · lib.rs:1483 测试连接 · lib.rs:1599 体检 · lib.rs:2856 写进客户端用的密钥 · lib.rs:3048 模型页读 4SAPI 密钥 · lib.rs:3519 显示/复制密钥 · fetch.rs:1903 隐藏渠道的"有没有密钥" · fetch.rs:2152 自定义渠道取数。
更糟的是：取数走的是新接口、自定义渠道取数走的是旧接口 —— 同一个渠道里两个来源互相打架。
修复后把这 8 处全部换成 secrets::resolve()。引用模式 everywhere 一致：能取到数、能显示密钥、能复制、能写进客户端、模型页能出价目表、测试连接和体检说的是真话。掩码和明文也不会再自相矛盾。
N06P1新增"引用的条目被删了"被说成"还没填密钥"，把人引向错误的页面

app/core/src/fetch.rs:1959-1967、1792-1798

现象密钥箱里那条被删了之后，渠道卡上同时出现两行互相打架的话：
· 来源行：「引用的密钥箱条目已删除」（对）
· 错误行：「还没填 4SAPI 的密钥」（错）
用户跑去渠道卡重填密钥 —— 但真正该去的是密钥箱。
原因Resolved 枚举特意分出了 Dangling（断链）和 None（没配），注释还专门写了"界面必须能区分'没配过'和'引用的条目被删了'——两者该去的地方相反"。但 credentials() 拿到 Dangling 时当成了 None，不产生任何错误信息，于是落到了兜底文案"还没填密钥"。
修复后把"断链"这个信息从 credentials() 一路传到取数失败的文案里。错误行会说「引用的密钥箱条目已被删除（去密钥箱看）」，和来源行一致。两种情况该去的页面不同，用户就不会跑错地方。
N07P1新增「删除前拦截」只做在浏览器里，而且用的是可能已经过期的索引

lib.rs:490-497（vault_ref_channels 注册了但没人调用）· app.js:1818-1820、3919-3939

现象删一把正被渠道用着的密钥时，有时连提示都没有，直接就删了，渠道当场变断链。
原因拦截逻辑完全在浏览器里，靠 SQLite 索引 vault_refs 判断"有没有人在用"。而：
① 索引读取失败时 loadVaultRefs() 把错误吞掉、把列表清空 → 提示彻底消失；
② 索引和真实指针可能已经不一致（见 N08）；
③ 后端明明有现成的 vault_ref_channels 命令（注册在 invoke 列表里），前端从来没调用过。
而且 vault_delete 本身完全不检查有没有人在用。
修复后把检查搬进后端 vault_delete，用真实指针而不是索引来判断。删除前一定会拿到"这把正被 XX、YY 使用"的确切清单；索引坏了也不影响判断。读取失败时至少要提示"读不到引用关系，没法确认能不能删"，而不是默默放行。
N08P1新增首页徽标上那个"可领"按钮，点了完全没反应

app/src/app.js:4083（按钮）vs 2328-2378（#list 的点击委托）

现象首页渠道卡上出现一个"可领 +100"的蓝色小按钮。点它什么都不发生 —— 不领、不提示、连卡片都不展开。
原因这个按钮带 data-act="ckrun"，但 ckrun 只在设置页的委托处理器里（app.js:2724）被处理。首页列表的委托只认 ckstripopen / open-manage / open-models / range 四个动作，ckrun 落进去就 return 了 —— 而且因为前面调了 e.stopPropagation()，连展开卡片都没有，用户得不到任何反馈。
修复后把 ckrun 的处理逻辑抽成一个函数，设置页和首页都调它。首页就能一键领积分，不用先跑到设置页 —— 这正是这个徽标设计稿里主打的那一下。
N09P1新增"可领"这个状态根本到不了 —— 那枚可点的徽标是死代码

app/src-tauri/src/lib.rs:2465-2486 · app/src/app.js:4079

现象徽标的"可领"分支永远不会被触发。实际能看到的只有：已签 / 本期无活动 / 待签 / 需登录 / 异常 / 未就绪。
原因平台返回"可领"时，落库的是 retry:ready；但 run_checkin 总是立刻把 ready 消费掉去领取，然后落库的是领完之后的结果（claimed/already）。所以 last_code 永远不会是 retry:ready，徽标里那个分支是死代码。
（顺带：设置页里"今日可领"那几个分支同样是死的。）
修复后让"可领"成为一个真实存在的状态。两个方向：① 自动签到时把"可领"这个结论记下来（retry:ready），让徽标能显示"可领 +100"并可点击；② 或者更省事：把徽标的"待签"也做成可点的「领积分」按钮（反正 N08 修好之后点击就能用），配合后端已有的 can_try 判断该不该让点。
N10P1新增已领到但平台没给数额时，徽标只剩一个光秃秃的「✓」

app/src/app.js:4073

现象渠道卡上显示一个小小的 ✓，没有别的字。用户不知道这是"已签到"还是别的什么。
原因徽标渲染成 ✓${n}，而 n 在没有数额时是空串。而 Trae / WorkBuddy 的签到接口恰恰经常不返回数额（本机 10-20、10-21 两天都是 credits = null）—— 所以这才是生产环境下的常态渲染，不是边缘情况。挂件宽度只有 380px，tooltip 要悬停才看得到。
修复后没有数额时出「✓ 已签」，有数额时出「✓ +100」。一眼就能看懂，不用悬停。提交信息里写的是"徽标同步:没有数额时出「✓ 已签」"，但徽标代码没跟着改 —— 现在补上。
N11P1新增顶部"今天还有 N 个没签"提示条，把隐藏渠道也算进去了，永远消不掉

app/src/app.js:4037-4049（ckPendingStrip）、1258-1268（peekCheckinLine）

现象把 Trae 隐藏之后，首页顶部一直显示"今天还有 1 个渠道没签到 · 去查看"，但界面上没有任何徽标，而且今天也不会再去签它了。
原因隐藏渠道不会关掉签到开关（隐藏只改 CFG.hiddenChannels），但节拍器会跳过隐藏渠道（lib.rs:2735），徽标也不给隐藏渠道画（app.js:4065）。提示条却没排除隐藏渠道，于是一个"永远不会发生"的任务被一直挂在最显眼的位置。
修复后提示条和胶囊速览都排除隐藏渠道（以及不在渠道列表里的 id）。提示条只在真的有渠道待签时出现，签完了就消失 —— 它本来的设计就是这样（注释里写着"全部签完就消失，'全部已签'是噪音不是信息"）。
N12P1新增"正在重新确认凭据"这个状态既没有按钮，文案还会说谎

app/src/app.js:4019 · app/src-tauri/src/lib.rs:2408、2732

现象设置页里那个渠道的签到行显示"正在重新确认凭据…(马上会再试一次)"，但连一个按钮都没有。而且如果自动签到是关着的，"马上会再试一次"是假的 —— 什么都不会发生，这个状态会一直挂到第二天。
原因ckText() 的 recheck 分支只返回了一个 text，没返回 btn → ckRowHtml() 就不渲染按钮。而后端这个状态下 can_try 是 true（陈旧的 auth 不挡当天），手动点完全是可以跑的 —— 只是界面没给入口。
修复后给 recheck 一个「立即重试」按钮；文案按 s.auto 分开说。自动签到开着就说"马上会再试"，关着就说"自动签到已关闭，点这里手动重试"。后端本来就允许跑，界面把入口露出来就行。

P2 · 边界情况与数字偏差

N13P2新增引用索引和真实指针没有对账机制，五条路径会让它们永久不一致

app/core/src/store.rs:1247-1308（vault_refs）· lib.rs:455-472、327-328、484

现象密钥箱列表里的"正被谁使用"会说谎：说某把没人用其实有人用，说某把有人用其实没人用。删前拦截也跟着失灵（见 N07）。
原因设计里说得很清楚："这张表里没有任何密钥值，只是 id 之间的关系"、"它只是索引，权威来源是凭据管理器里的指针"。但没有任何一处代码在两者之间做对账，store::vault_ref_of 更是全项目零调用。能走偏的路径至少五条：
① 切换引用时索引写失败 → 索引指旧的、指针指新的；
② 索引清失败 → 索引说有、指针没了；
③ 删自定义渠道时索引没清（N02）；
④ 数据库被删/重装但凭据管理器还在 → 索引空了，密钥箱列表全空，可那些密文永远列不出来、也删不掉；
⑤ 凭据管理器被清但数据库还在 → 索引说有，渠道其实没密钥了。
修复后加一个"按指针重建索引"的动作，启动时跑一次；索引写失败不让命令失败而是记下来等重建。索引会自愈，"正被谁使用"永远是真的，"删前拦截"也就靠得住了。
N14P2新增密钥来源写进了已经脱离页面的节点，界面不更新

app/src/app.js:1870-1889（fillKeySources）

现象渠道卡上的"密钥来源"那一行不更新，还是旧内容或空的，最多要等下一次轮询（最长 60 秒）才对。
原因代码先 document.querySelector(".ksrc[data-src=...]") 拿到 DOM 节点，然后才 await invoke("key_source")，回来后往那个旧节点上写。而 renderChCards() 会把整个 #chList 重建 —— 等待期间只要发生一次重建（轮询、保存密钥、切渠道可见性…），手里那个节点就成了"游离节点"，写进去永远看不见。
这个坑项目在别处已经踩过并写了注释（app.js:2413："手里那份 body 成了游离节点，写进去永远看不见…按当前 DOM 重新查一次"），而且紧挨着的 fillKeyHints() 就做对了。新代码把已经修好的模式又犯了一遍。
修复后await 之后重新查一次 DOM 再写。和 fillKeyHints() 保持一致，来源行永远是最新的，不会出现"看着像没生效"。
N15P2新增读密钥来源失败被伪装成"直接填"，用户被推去重配

app/src/app.js:1881-1887

现象凭据管理器抽风（服务停了、组策略禁用）时，所有渠道卡都显示成"没配来源"的样子，还弹出「或从密钥箱选一把」的下拉框。用户以为自己没配过钥匙，跑去重新配一遍 —— 而实际是系统故障。
原因catch 里把错误吞掉，写成 { mode: "inline" }，还缓存在模块级的 KEYSRC 里。注释说"不显示未经验证的引用状态"，但效果正好相反 —— 显示的是一个假的、且指向另一个方向的状态。

N16P2新增删掉密钥箱条目后，渠道卡还显示"正在使用这把"

N17P2新增切换引用前只查索引不查密文，可能把能用的密钥换成一个死引用

N19P2新增徽标提示用本地时间判断北京时间的 10:00 边界

N20P2新增首页首屏被一次很重的 IPC 卡住

修复后先 render() 再 await loadCheckin(); render();，或者把凭据探测的结果缓存起来。余额和卡片立刻出来，签到徽标晚 200ms 补上 —— 体验上察觉不到，但首屏不再被 3 秒的 Cookie 超时拖着。
N21P2新增引用查询是同步命令，在主线程上抢数据库锁

原因这两个命令没有 async、没有 spawn_blocking，直接在主线程上抢 store 锁。而同一个文件里专门写过这条纪律："同步命令是在主线程上跑的，而这里要写 SQLite 并等 store 锁，90 天清理正持着那把锁时会整窗卡住"。vault_list 当时就是为了这个才改成 async 的，这两个新命令没跟上。而且 vault_ref_map 每次渠道卡渲染都调一次。

N22P2新增开机时所有签到请求挤在头几秒

现象开机后签到集中失败，提示"当前参与用户太多"。

修复后开机这一轮加随机抖动，或者每轮只处理一个渠道。既保留了"开机立刻判一次"的好处（那正是这次改动的目的），又不会把所有请求堆在开头。
N23P2新增【同时是好事】节拍器开机立刻跑一轮 —— 这条本身是对的

app/src-tauri/src/lib.rs:2711-2718

现象以前启动后要干等 5 分钟才判第一次签到，界面这期间挂的是上次运行留下的结论（"早已过期的凭据失效"），把用户引到死胡同。现在开机立刻判。

5. 这轮顺便确认过、没问题的部分

  • 密钥箱的"两种来源互斥"规则——服务名分成 TokenScope / TokenScope:vault / TokenScope:link 三个，删渠道密钥不会碰箱子，删箱子不会碰别处的值。裁决 5（一个渠道一把）和裁决 6（一个条目可被多个引用）都守住了。
  • 断链故意不退回手填值——Resolved::Dangling 的行为和文档完全一致，避免了"我明明删了箱子里的，它还在用旧密钥"这种诡异现象。
  • resolve() 本身——先看引用再看手填，vault: 前缀能挡住"用户手输一把以 vault: 开头的密钥"被误判成指针；key() 让上层不必关心来源。
  • 陈旧 auth 的判据方向是对的——只对 auth 生效、claimed/already 不受版本影响（那俩是平台给的既成事实），这个设计判断正确，只是漏了日期维度（N24）。
  • done_for_day 的三个调用点都换成了 blocks_today——界面和节拍器口径一致，不会出现"界面说不能试、节拍器却在跑"或反过来。
  • 签到结果不参与余额渲染——徽标的颜色绝不改金额和状态点；签到失败不会让余额显示成 0。
  • "开签到默认关"没被破坏——没开的渠道一个请求都不发，徽标也不画。
  • 金额数额只信平台给的字段——Trae/WorkBuddy 不返回数额时，界面明说"平台未返回数额"，不编数字（74afd32 修对了大部分，只漏了一处 N18）。

6. 一句话总结

新功能的方向和实现质量都不错——密钥箱用"引用"而不是"复制"是对的（同一把钥匙不存两份、改箱子渠道立刻跟着变）， "陈旧 auth 要重判"也是对真问题的正确诊断，签到徽标把结论交给后端算（避免前端算日期算错）同样是对的。

但这轮改动都停在了"最后 10%"：密钥箱这套的读路径没有统一（8 处还在用旧接口，同一张卡片两套真相）， 写路径的收尾没做（删密钥不清引用、切引用先删后写）， 签到徽标的点击没接上（首页的委托不认 ckrun）、状态到不了（retry:ready 永远不会被落库）。

建议下一步就做两件事：① 把密钥箱的读写收口到 resolve() 一个入口，并加一次启动对账（能一次解决 6~7 个问题）； ② 把签到徽标的"可领"这条链路打通（状态落库 + 首页点击），再把"待签"也做成可点的。 这两件做完，这轮新加的两个功能才算真正落地。

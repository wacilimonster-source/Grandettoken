隐藏渠道恢复 + 密钥查看/复制 + 本地密钥箱

2026-10-13 · 产品设计（未写代码）。前两项是修复与补齐,第三项是一个新小工具。取证来源:本仓库代码 + 本机真文件;凡是没能在真机上复核的,下面都标了「待真机确认」。
三件事,一句话各说清

① 隐藏渠道恢复:入口其实在(渠道卡右边的眼睛),但隐藏后它变成一个「–」破折号,既不像"恢复"也不像按钮 —— 先按可发现性修(隐藏时给一条整行的「已隐藏 · 恢复」),同时把"万一卡片真的不在列表里"的兜底也补上。

② 看/复制已保存的密钥:现在只回显尾 4 位(`key_hint`),前端拿不到明文。补两个动作: 「复制」(明文不回前端)与「显示」(明文回前端一次,8 秒自动隐)。

③ 本地密钥箱:按平台分组、一个平台可存多把。**密文进 Windows 凭据管理器,SQLite 只存索引**(平台/标签/尾号/时间), 所以列表渲染不需要解密;只有你点「查看/复制」才读那一把。不导出、不进日志、不参与任何自动取数或写入。

一、① 隐藏渠道恢复:先查真因

代码取证(本仓库,2026-10-13)

隐藏这件事的链路是通的:renderChCards() 遍历的是 全部渠道(currentOrderIds() → CHANNELS), 隐藏的那条照样渲染卡片,并带 已隐藏 标签;眼睛按钮的处理 chvis 也就是把 id 从 hiddenChannels 里摘掉再重取一轮 —— 功能上应该能恢复。

问题出在它长什么样:隐藏后那个按钮的文案从 👁 变成 –(一个破折号),提示语只在 hover 时才出现 (title="显示(恢复取数)")。所以"没法恢复"最可能是找不到入口,而不是点不动。 待真机确认:这一步我没能在你机器上复核(挂件当时是正常模式、没开调试端口,我没有为了这个再打断它)。 真机上只需看一眼:进「设置 → 渠道」,那条隐藏渠道的卡片在不在、那个 – 点下去是否恢复。

1.1 三处一起改(不管真因是哪个都覆盖)

改哪现在改成解决什么
渠道卡上的隐藏/显示 👁 / – 一个 26×22 的小方块 隐藏时按钮上直接写「恢复」两个字(.btn.s),卡片整条加一层黄色描边;显示时保持 👁 图标不变 恢复入口一眼可见,不用 hover 猜
渠道页顶部 没有汇总 有隐藏时出现一条:「已隐藏 2 个(Trae、Hapi) · 全部恢复」,点「全部恢复」一次清空 hiddenChannels 藏了好几个时不用逐个找
展示面的空态卡片 「已配置的渠道都被隐藏了 → 去设置」(只打开管理页) 按钮改成「去恢复」:打开管理页 → 渠道页签 → 滚动到第一条隐藏渠道并高亮 1 秒(复用 .flash 与 +N 徽标已有的做法) 从"自己去翻"变成"直接指到那一条"

1.2 兜底:万一卡片真的不在列表里

还有一种可能(待真机确认):隐藏 + 当前没有可用凭据时,App 型渠道的占位视图 hasKey=false (隐藏时刻意不读本机登录凭据),若卡片渲染上有任何依赖 hasKey 的分支,那条就会"看起来消失"。 所以上面第 2 条(顶部「已隐藏 N 个 · 全部恢复」)既是便利,也是兜底 —— 它从 CFG.hiddenChannels 直接算, 不依赖任何渠道视图,只要配置里还有 id 就给得出恢复入口。

二、② 查看 / 复制已保存的密钥

先说清楚这条与现有契约的关系

产品的既有规矩是「密钥永不回前端」(Rust 现读现写,界面保存后不回显,只给尾 4 位)。 你要的"看/复制"必然要破这一条 —— 破得有边界就不算破:明文只在你明确点「显示」那一次回前端并渲染, 8 秒后自动隐;「复制」这条路根本不回前端(后端读出来直接进剪贴板,沿用「复制三件套」那套 clip.exe + UTF-16LE)。 两条都不会写进日志、数据库或任何文件。

动作行为明文去哪为什么这样设计
复制
推荐默认动作		 点一下就把这把密钥送进系统剪贴板,界面只弹一行 toast(不渲染明文) 凭据管理器 → 后端内存 → 剪贴板 日常 90% 的场景就是"我要粘到别处";这条路径前端拿不到明文,破口最小
显示 明文渲染在那一行里,8 秒倒计时后自动隐;再点一次立即隐 凭据管理器 → 后端 → webview 一次性渲染 你要"看一眼确认是不是那把"时用;自动隐藏避免截图/录屏/路过的人
尾号回显保持现状(••••3f7a)—不用点就能确认"是不是那把新换的"

三个细则:① 「显示」只影响当前这一行,切页签/刷新/轮询重建都立刻收回(明文不留在 DOM 里过夜); ② 剪贴板写入会提示"剪贴板对其他程序可见"(与「复制三件套」同一句); ③ 密钥型渠道(Trae/Codex 这类复用本机登录态的)没有可复制的密钥,按钮不出现。

三、③ 本地密钥箱(新工具)

3.1 需求与不做什么

要的不做的
按平台分组、一个平台多把密钥;每条可带标签与备注 不导出(明文导出等于把密钥写进文件;要迁移就手动重录)
平时加密存放,只有人点「查看/复制」才出现明文 不自动使用:不参与余额取数、不参与模型写入、不自动填任何输入框
查看是显式动作,带倒计时自动隐藏 不做多设备同步/云(与本产品"无遥测、无云同步"一致)
增 / 改 / 删(删要内联确认) 不设主密码(取舍见 3.3)

3.2 存在哪:密文进凭据管理器,索引进 SQLite

Windows 凭据管理器                          SQLite(可备份、可分享)
┌────────────────────────────┐            ┌──────────────────────────────┐
│ 服务名  TokenScope:vault    │            │ vault_items                  │
│ 账户名  <条目 id>          │            │  id / platform / label       │
│ 内容    密钥明文(由当前     │            │  hint(尾 4 位) / note        │
│          Windows 账户的     │            │  created_at / updated_at     │
│          DPAPI 保护)        │            └──────────────────────────────┘
└────────────────────────────┘              ↑ 列表界面只读这张表,**不解密**
        ↑ 只有「查看 / 复制」读它
项取舍
为什么用凭据管理器 它本来就是加密的(DPAPI 绑当前 Windows 账户),而且这是本产品已经在用的唯一密钥存放处 —— 不新引加密库、不自己写 AES/HMAC。对照:自建 AES-GCM 需要新增依赖(锁文件里没有 aes-gcm/hmac), 手写 CBC+MAC 更是"自己造加密",两个都不值得。
条目上限 凭据管理器单条 blob 上限约 2.5 KB(实测过的经验值 ~1280 字符),密钥都是几十字符,够用;数量上没有硬门槛。
索引为什么可以明文 平台名、标签、尾 4 位、备注不是秘密;列表因此不需要解密就能渲染 —— 这一点很关键: "看一眼列表"和"取出明文"被彻底分开。
删条目先删凭据管理器里那条,再删索引;任一步失败都不留"半条"(失败会把索引一起回滚)。
必须写进界面的两句:① 密钥箱保护的是"这台机器 + 这个 Windows 账户" —— 换成别人登录这台电脑、或你关掉 Windows 登录保护,它就不再安全;② 复制到剪贴板后, 剪贴板历史/其他程序都看得到。两句都放在密钥箱页脚的一行小字里,不藏在 README。

两张原型说明

  • 左:密钥箱 —— 按平台分组、组内按建立时间倒序;每行四个动作(复制/显示/改/删);搜索跨平台匹配标签与备注。
  • 右:渠道页的两处修复 —— 顶部「已隐藏 2 个 · 全部恢复」;隐藏卡片上的按钮直接写「恢复」,整条降透明度保持"它是停用的"这层语义。
  • 渠道卡里那行密钥:尾号 + 复制 / 显示 / 删除;显示点开后是绿框里的明文,带倒计时自动隐。
  • 不需要新颜色、新形状:全部复用现有 .btn / .krow / .tagn / .restorebar 这套变量,窗口仍是 380 宽。

3.4 数据与代码契约

层改什么
core/store.rs 新表 vault_items(id TEXT PRIMARY KEY, platform TEXT, label TEXT, hint TEXT, note TEXT, created_at INTEGER, updated_at INTEGER) + 索引 (platform, created_at DESC);方法:vault_upsert/vault_list/vault_delete/vault_get。 表里没有密钥字段 —— 这点写进注释,免得以后有人顺手加一个。
core/secrets.rs 扩一个命名空间:现有 set/get/delete(provider_id) 之外加 vault_set/get/delete(id)(服务名 TokenScope:vault)。 密码箱里的 hint(尾 4 位)与渠道卡用的是同一个掩码规则。
core/vault.rs(新) 纯逻辑:平台/标签的校验(非空、同平台内标签不重复)、排序、搜索匹配、掩码。可挂单测。
src-tauri/lib.rs 命令:vault_list / vault_save(条目) / vault_delete(id) / vault_reveal(id)(一次性返回明文)/ vault_copy(id)(后端直接进剪贴板,不回前端)。全部 async + spawn_blocking(凭据读写是阻塞活)。 渠道密钥复用同一条路:key_reveal(id) / key_copy(id)。
前端 管理页第 6 页签「密钥箱」;渠道卡的隐藏/显示按钮改造 + 顶部恢复条;渠道卡里加密钥的复制/显示。倒计时用现成的 setTimeout,不留驻。
不动 密钥箱不接入取数与模型写入;hidden_channels 的语义与落库方式不变。

  1. 隐藏恢复的改造范围?
    A(推荐):三处一起改(按钮写「恢复」+ 顶部「已隐藏 N 个 · 全部恢复」+ 空态直达高亮)。
    B:只把按钮文案改成「恢复」(最小改动),顶部汇总与空态直达不做。
  2. 渠道密钥的默认动作?
    A(推荐):两个都要 —— 复制为主(明文不回前端),显示为次(8 秒自动隐)。
    B:只给「复制」(明文永不回前端,显示一律不做)。
  3. 「显示」的自动隐藏时长?
    A(推荐):8 秒;再点一次立即隐。
    B:5 秒;C:不自动隐(点一次显、再点一次隐)。
  4. 密钥箱放哪?
    A(推荐):管理页新开第 6 个页签「密钥箱」(在「关于」之前)。
    B:并入「关于」页签的下半部分(不加页签,但那个页签会变长)。
  5. 密钥箱要不要主密码?
    A(推荐):不要 —— 边界就是 Windows 账户。加了主密码,忘了就等于全部密钥永久丢失,风险大于收益。
    B:加一层可选主密码(要设计"找回=全丢"的提示与二次确认)。
  6. 密钥箱与渠道/客户端的关系?
    A(推荐):本期纯记事本 —— 只存、看、复制,不自动填任何地方(与你说的"只允许人工查看复制"一致)。
    B:同时支持"一键填入某渠道的密钥"(多一步显式确认),列入 V4。
  7. 「1 个平台多把密钥」怎么定"当前用哪把"?
    A(推荐):**不设"当前"** —— 密钥箱不知道也不猜哪把在用,避免出现"显示的那把其实不是渠道里那把"的错位。渠道自己在「渠道」页里管自己那把。
    B:标一个"主用"标记(好看,但会和渠道页的真实状态打架)。

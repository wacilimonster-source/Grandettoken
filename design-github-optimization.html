这个仓库现在的功能链是健康的（19 个 release、每个三件套齐全、更新链路实测通），病在"门面"和"自动化"： 别人点进 github.com/wacilimonster-source/Grandettoken 看不到一句介绍（无描述、无 topics、无许可证、无根 README）， 首页直接铺着 20 个内部文档（bug 报告 / 设计稿 / 原型 / AI 工作日志）； 发版靠 RELEASE.md 里 5 步手工流程（那套流程自己已经记了 3 个踩坑），没有任何 CI。

三、方案

A. 门面（P0，约半天）

  • 根 README.md（中英文按裁决）：一句话定位 + 当前版本截图（build/shot-panel-0923.png 是 9 月的，实施时用现在这版重新截）+ 下载入口（直接链 Releases）+ 安装/更新说明（per-user 免管理员、自动更新走 latest.json）+ 渠道与额度模型表（从 app/README.md 提上来）+ 数据位置与隐私一句（数据库在 %APPDATA%、密钥在凭据管理器、不采集任何东西）+ 已知边界（WorkBuddy 网页会话约 7 天、Trae/Codex 读本机登录态）。
  • 仓库元数据：description（一句话：常驻桌面的多平台 AI 额度监控小组件）、topics（tauri rust windows desktop-widget token-usage ai-tools）、homepage 指 Release 页；关掉空的 Wiki/Projects 标签页。
  • LICENSE：见裁决 1。
  • 命名统一：README 标题用产品名 Grandettoken，正文加一句"早期叫 TokenScope，旧的文档与凭据条目仍用旧名"，把 app/README.md 与根 README 合并（app/README.md 保留为开发者视角的模块说明）。

B. 仓库结构（P0/P2，约半天）

  • 文档归位：新建 docs/，把 20 份 design-*.html / bug-report-*.html / 原型 / 研究稿按前缀搬进去（docs/design/、docs/report/）；根目录只留 README.md / LICENSE / RELEASE.md / 两个 DESIGN + PROGRESS（或一并进 docs/，见裁决 3）。
    代价与做法：PROGRESS.md 与部分代码注释里引用了这些文件名（如 app.js:954 提到 design-pill-restyle-5.html），搬迁时用脚本统一改成 docs/design/… 并 grep 复核 0 处旧路径残留；历史 commit 不受影响（旧版本里的路径本来就指旧版）。
  • 停止跟踪工具目录：.workbuddy-ai/（AI 工作日志）、.workbuddy/、.zcode/ 加进 .gitignore；已在库里的那份 AI 日志按裁决 4 处理。

C. 自动化（P1，1~2 天，含一次 CI 可行性验证）

  • CI 检查（push / PR）：windows-latest + GNU 工具链 + mingw，跑 app/core 的 cargo test（55 项）与 src-tauri 的 cargo check --all-targets。公开仓库的 Actions 分钟数免费。
    注意：本项目是 Windows-GNU 非官方路径（Tauri 官方只覆盖 MSVC），release 构建还依赖 build/make-webview2-static.ps1 生成的静态加载器归档（build/webview2-static/out/ 是 gitignore 的，CI 里要现生成）。所以这一项在实施时要先跑一次 spike：core 测试几乎肯定能上；src-tauri 的 check 若被工具链卡住，就先只上 core 测试 + 把结论写进 RELEASE.md。
  • 发版自动化（tag 触发）：三种做法，推荐 C2——
    C2. 推荐 普通 workflow，直接复用现有三件套：装工具链（rust GNU target + mingw）→ 跑 build/build.ps1 bundle（它已带 PATH/CC 装配与单 exe 导入表断言）→ node build/make-latest-json.js → gh release create 传三件套（permissions: contents: write + 内置 GITHUB_TOKEN）。好处：每一段都是你手工跑过的命令，出问题能在本地原样复现。
    C1. 用官方 tauri-apps/tauri-action：tauriScript 指包装脚本、projectPath 指 app/src-tauri、uploadUpdaterJson: true 由它生成 latest.json。少写一段 YAML，但它是为 JS 工程设计的（本项目没有 package.json），单 exe 断言仍要自己补一步，等于把 build.ps1 的逻辑拆成两处。
    C3. 保持手工，只把回滚预案与"发版前自检清单"补进 RELEASE.md。

    签名私钥进 Actions Secret：gh secret set TAURI_SIGNING_PRIVATE_KEY < C:\Users\wacil\.tauri\tokenscope.key（值不回显、不进聊天记录），密码项显式设空串；版本号四处一致里，Cargo.toml / tauri.conf.json 两处由 build.rs 编译期断言，tag 与 latest.json 由 workflow 同源生成。C1/C2 的密钥用法相同。

  • 回滚预案（写进 RELEASE.md）——先说清楚：默认没有降级通道。实测 tauri-plugin-updater 2.11.0（updater.rs:576）：无自定义比较器时判据就是 release.version > current_version，把 latest.json 指回旧版本号不会让任何人降级。所以发坏了只有两条路：
    ① 止损：立刻把坏 Release 转成 prerelease 或删除 —— releases/latest 会跳过它，还没更新的人不会中（已更新的人停在坏版本）。
    ② 救回：发一个版本号更高的修复版（坏了的是 0.1.20 就发 0.1.21），已更新的人靠它回来。
    因此真正的闸门在发版前：RELEASE.md 加一份自检清单（本机覆盖安装一次、更新弹窗点一遍、面板出一个真数），比任何回滚都便宜；能落成 build/preflight.ps1 更好。

    备选（不建议现在做）：给应用装自定义 version_comparator 换取降级能力 —— 那会改应用的更新语义，收益不抵风险。

D. 治理与安全（P2，半小时）

  • 红线（写进 README/CONTRIBUTING 级别的说明）：仓库必须保持 public（私有仓库的资源需鉴权，更新插件拉不到）；release 资产名必须保持 Grandettoken_<版本>_x64-setup.exe / .sig / latest.json 三件套且 releases/latest 永远指向最新可用版 —— 这两条是已装用户的更新命脉，任何"重命名/整理发布"的优化都得绕开它们。
  • Dependabot：cargo + github-actions 两条，周更 PR（rustls / reqwest / tauri 这些值得跟）。
  • main 分支保护：只加"要求 CI 通过"这一条，不要求 review（单人项目会卡自己）。
  • Issue 模板：一个 bug 模板（版本号 / 渠道 / 面板截图 / 是否刚更新过），一个"渠道失效"模板（哪个渠道、报什么文案、key_hint 尾号）。

    B. 自定义"源码公开、保留所有权利"（一段短声明，明确只读、不可再分发）
    C. 暂不处理，只做其余项
  2. README 用什么语言？

    B. 中英双语（英文在前，方便被 star / 被推荐）
    C. 英文为主
  3. 文档搬到哪一步？

    B. 更彻底：连 PROGRESS.md / DESIGN.md / RELEASE.md 一起进 docs/，根目录只有 README / LICENSE
    C. 只搬 bug 报告与研究稿，设计稿留根目录
  4. 那份 AI 工作日志（.workbuddy-ai/memory/2026-09-17.md，已在公开仓库里）怎么办？
    A. 推荐 停止跟踪 + 进 .gitignore（它已经是仓库历史的一部分，公开可查；不在历史里抹除 —— 改写历史要 force-push，会牵连 tags/release，风险大于收益）
    B. 移进 docs/notes/ 保留（当作开发日志的一部分，反正内容没泄密）
    C. 连历史一起清（我需要你明确知道这要 force-push 并重建 tag，且 Release 资产要重新核对）
  5. CI 做到哪一步？
    A. 推荐 先落 core 测试 + src-tauri check（含一次 GNU/MSVC 工具链 spike，结论写文档）
    B. 只跑 core 测试（最稳，5 分钟能上）
    C. 先不做 CI，只做发版自动化
  6. 发版自动化要不要上？（需要把签名私钥放进 GitHub Secret）
    A. 推荐 全自动：push tag → 构建+签名+发布+更新清单，一条链跑完
    B. 半自动：Actions 只负责构建产物并留出下载，gh release create 仍手工（私钥仍要进 Secret）
    C. 保持手工，只把回滚预案和两个坑补进 RELEASE.md

五、明确不做的（避免越做越重）

  • 不把仓库改成私有：会让所有已装用户彻底收不到更新（RELEASE.md 已写明），这是硬约束不是偏好。
  • 不做 GUI 冒烟 CI：Tauri + WebView2 在 runner 上跑不出可靠结论（本机都踩过"反复强杀把 WebView2 搞崩"），收益远不及成本；窗口/形态验证继续靠 build/verify-form.js 那套本地脚本。
  • 不引入 wiki / discussions / 贡献指南 / 行为准则：单人项目，维护不动的东西等于负债。
  • 不动 release 资产名与 tag 命名规则（更新命脉，见 D 的红线）。
  • 不改写 git 历史（除非裁决 4C）。

六、实施顺序与验收

步做什么验收方式
1仓库元数据 + LICENSE（裁决 1/2 决定文案）匿名 curl 读 api.github.com/repos/…：description / topics / license 都有值
2根 README（含新截图、下载入口、渠道表、数据与隐私、已知边界）用无头浏览器渲染 README 的 Markdown 预览截图核对：图片能显示、三个链接可点、版本号与当前 release 一致
3docs/ 归位 + 引用改写 + .gitignore 补工具目录git ls-files 根目录只剩约定的 6 个文件；grep -rn 旧文件名 0 处残留；git status 干净（不再冒出 .zcode/.workbuddy）
4CI（core 测试 + check）一次真实 push 触发 workflow 全绿；再故意改坏一个断言验证它真能红
5发版自动化 + 回滚预案 + RELEASE.md 重写用 0.1.20 或下一个版本走一遍：tag → workflow → release 三件套齐全、latest.json 签名与本地 .sig 一致、装机实测能收到更新；再演练一次"删 Release 看 latest 是否回退"
6Dependabot / 分支保护 / Issue 模板Dependabot 首轮 PR 出现；直接 push 一个坏提交被 CI 拦下；开 issue 页能看到两个模板

顺序理由：1~3 是纯文档与文件移动，零风险、当天能验收；4~5 碰构建与密钥，放后面且各自独立；6 最后（分支保护必须等 CI 绿了再加，否则会把自己锁在门外）。

调研方式：gh api 读仓库元数据与 release 列表；git ls-files 清点入库文件；按 build/scan-secrets.ps1 的口径复扫 77 个入库文本文件（PAT / sk- / JWT / AWS / 私钥 / Bearer / 密码赋值 0 命中）； 读 build.rs、RELEASE.md、tauri.conf.json、make-latest-json.js 核对更新链路的硬依赖。本次未修改仓库任何文件、未改任何仓库设置。

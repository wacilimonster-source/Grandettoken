停在设计待裁决。你要的两件事都摸清了底：4SAPI 的模型清单怎么拿（含单价换算口径，已和站点自己的前端逐行对齐），以及四个客户端各把模型配置存在哪、长什么样（四个都本机取证到位，非推测）。

一句指令就能解锁下一步：1A 2A 3A …（按第九节逐项裁决）或 按这个方案写代码（全部照推荐项执行）。发版另说，我不会自己推。

有 6 项必须真机才能定（最要紧的两条：WorkBuddy 的“选中项”键前缀、Trae 的 modelId 中段），第十节单列，实现时在你机器上跑探针才算数。

说人话版结论

① 模型清单不用求人：站点自带一份公开价目表，160 个模型，不用密钥就能拉。再配你的密钥拉一次 /v1/models，就知道这 160 个里你这把 key 真能调哪些。两条合起来，就是“可用模型”的完整答案。

② 单价能直接折成 ¥，和你面板上的余额同一个货币。站点自己的前端算的是 单价 = 2 × 模型倍率 × 分组倍率（每百万 token），而它的换算常量（quota_per_unit=500000）跟挂件现有的 4SAPI 渠道用的 500000 积分 = ¥1 是同一个数。所以“这个模型我还能跑多少”将来能直接算，不需要新口径。

③ 但“配置到客户端”不是一个功能，是四份完全不同的写入契约。WorkBuddy 是明文 JSON、ZCode 是两份 JSON、Trae 是 SQLite 的 ItemTable。四条路都得守着同一套规矩：先备份 → 写完读回校验 → 目标程序没在跑。任何一条做不到，就退回“把三件套（地址/模型名/密钥）摆出来让你自己粘”。

④ 必须把一件事说明白：把模型配进客户端，等于把你的 4SAPI 密钥明文写进那些程序自己的配置文件（它们本来就这么存，你已有的 4SAPI 条目就是明文）。挂件自己的原则是“密钥只进凭据管理器”，所以这一步要逐客户端点确认，界面上写明落到哪个文件的哪一行，而且挂件永远不留副本。

1.2 单价换算口径（已与站点自己的前端对齐）

站点 pricing 页的 JS 里，模型价格是这么算的（原文摘录）：

let e = 2 * t.model_ratio * d;   // d = 分组倍率 → “输入价格 … / 1M Tokens”
补全价格 = 2 * model_ratio * completion_ratio * 分组倍率      // 同为每 1M Tokens

货币符号取自 quota_display_type，本站实测为 CNY（符号 ¥）。所以：

输入单价(¥/百万 token) = 2 × model_ratio × 分组倍率
输出单价(¥/百万 token) = 输入单价 × completion_ratio
按次计费(quota_type=1)   = model_price ¥/次
模型（真取回的数据）倍率标签单价 @ 一key分组(×2)
claude-sonnet-51.0 / 5.01M,多模态,文本入 ¥4.00 · 出 ¥20.00
gpt-5.3-codex0.875 / 8.01M,文本,多模态入 ¥3.50 · 出 ¥28.00
gemini-3.6-flash0.375 / 5.01M,多模态,文本入 ¥1.50 · 出 ¥7.50
grok-4.737.5 / 1.0500K,文本 阶梯计价入 ¥150.00* · 出 ¥150.00*

最后一行的 * = 该模型是 34 个阶梯计价模型之一（按上下文长度分档，站点原文：len < 200000 ? tier("Short",…) : tier("Long",…)）—— 倍率只是某一档的值，所以单价后面永远跟着星号与徽标。而 gemini-3.6-flash 的 ¥1.50 和 grok-4.7 的 ¥150.00 摆在同一列里，价差 100 倍，这就是为什么价格列不能藏在第二屏：“选哪个模型”和“余额还能撑几天”本来就是同一件事。

分组倍率从哪来？站点有 25 个分组，各自倍率写在 group_ratio 里（claude-官方5 · gpt-官方5 · default2 · 一key官方中转全模型2 · claude-code1 · 国产组 0.8…），另有 usable_group 给出每组的说明原文（站点自己写的“官方 28.5% 折扣”之类）。界面默认取 auto_groups[0]（一key官方中转全模型，×2），并在口径行里写清“按哪个分组估算、可以在下拉里改”，不代替你猜你的分组。

两条不许越界的口径纪律（沿用挂件“不误报”的第一原则）：
  • 阶梯计价的 34 个模型，倍率只是“某一档”的值 —— 一律打「阶梯」徽标，单价后加 *，展开里给出站点原文表达式，不给出“确定价”。
  • 分组倍率是站点声明的，不是我们算出来的。界面显示“站点价目表：入 ¥4.00/百万 · 分组 ×2”，而不是“你每百万要花 4 块”。

1.3 顺带确认的：现有 4SAPI 渠道没被改动

GET /api/usage/token（挂件已经在用的余额接口）与上面三个互不相干，本次设计不碰取数路径：模型查询是独立的一条只读链路，失败不影响余额显示，余额取数失败也不影响模型页。

2.2 界面侧现成的扩展点（不改架构就能挂上去）

  • 管理页已是四个页签（渠道 / 显示 / 刷新与启动 / 关于），加第五个页签是既定扩展方式（index.html 的 .mbody.panel[data-p] + .tabs）。
  • 多选芯片 .picks/.pick、分段控件 .seg、小徽标 .tagn 现成可复用（胶囊渠道选择就是 .pick）。
  • 事件一律走 data-act 委托（#manage 上两个监听器），新动作只需加一个 data-act 分支。
  • 所有插值都过 esc()；窗口固定尺寸不可拖大，长列表只能靠内层滚动（.mbody{overflow-y:auto}）—— 模型列表必须自带搜索，不能靠翻。

原型说明

  • 四个客户端按钮就是主操作：T 实心绿 = 已配置；空心 = 未配置；WB 黄框 = 配置过但目标在运行（点了会拒写并说原因）；灰淡 = 未检测到该客户端。
  • 单价并列在行内，超过阈值染黄/染红（与余额用同一套状态色）—— 因为“哪个模型烧最快”和“哪个渠道先没钱”是同一类判断。
  • 不弹新窗口：写入预告就长在列表下方（沿用「删除密钥」用内联 .cfrm 确认、不用 confirm() 的既定做法）。
  • 页脚常驻一句密钥契约：“密钥永不经挂件落盘”，任何时候都看得见。

3.4 交互与状态语义

环节规则
默认过滤只显示 supported_endpoint_types 含 openai 或 anthropic 的模型（覆盖 159/160），并默认排除 tags 含「图像 / 视频 / 音频 / 向量 / 图像生成」的条目。提供「显示全部 160 个」芯片，不偷偷藏东西。
搜索命中 model_name（不分大小写子串）、厂商名、标签、说明。搜索框非空时忽略折叠状态，平铺结果。
排序默认：已配置到任一客户端的模型置顶 → 其余按厂商分组（组内按名称）。不做“热度排序”这类没有数据支撑的排序。
“可用”的定义/v1/models 返回 = 这把 key 的分组能调。没拿到 key 时整页降级为“价目表浏览”并置顶一条提示「配置 4SAPI 密钥后可知哪些能用」，不把 160 个都说成“可用”。
价格缺失拿不到倍率（如按次计费）→ 显示“¥X/次”；阶梯计价 → 加 * + 「阶梯」徽标。绝不用 0 或空白顶替。
分组不含所选分组不在模型的 enable_groups 里 → 黄字提示，并且价格改按含有它的分组折算并标明是哪个分组。绝不显示一个本分组用不上的价。
客户端状态四态：未检测到安装（置灰，仅“复制三件套”可用）/ 已安装未配置 / 已配置 N 条（点开看落到哪个文件、哪次写的）/ 已配置但目标在运行（黄）。状态来自读文件 + 进程探测，不来自缓存猜测。
写入三步①点客户端按钮 → ②看预告（目标文件 / 改什么 / 密钥明文 / 备份路径 / 前提是否满足）→ ③确认写入 → 读回校验 → 结果条（新增几条、怎么生效、可否回滚）。没有“静默写入”这条路。
撞名同名模型已存在且内容一致 → 显示「已配置」不重复写；内容不同 → 预告里写明“更新现有条目”，并列出差异（地址/密钥变化）。
批量「同步到所有已配置客户端」= 把当前选中的 地址/密钥 覆盖到所有已配过 4SAPI 的客户端（换 key 场景）。同样逐客户端走预告。
失败文案四类分开说，不混成“写入失败”：
· 目标在运行 → “先退出 X”（并给出退出按钮/说明，不代杀进程）
· 文件被占用/无权限 → 报原样错误 + 备份路径
· 结构不认识（版本变了）→ 放弃写入并原样保留文件，提示“X 的配置格式已更新，本次不写”
· 读回校验不过 → 自动回滚到备份并如实说明。

四、四个客户端的写入契约

共同前提四条（缺一不写）：① 目标进程不在运行；② 先备份（含 SQLite 的 -wal/-shm）；③ 只增改自己写的那条，不动内置/账号/其它 provider；④ 写完读回校验，不过就回滚。

六、安全与信任契约（六条，写进 DESIGN.md）

  1. 只增改自己写的那条：自定义模型条目。不碰账号、登录态、内置模型、其它 provider。
  2. 密钥外流必须显式同意：明文目的地逐个客户端写明（~/.workbuddy/models.json 的 apiKey、Trae 的 ak、ZCode 的 apiKey）。挂件自身：只从 Windows 凭据管理器现读现写，不落盘、不进数据库、不进日志、不进备份（备份只备份目标客户端的文件）。
  3. 先备份，再写，写完读回校验，不过就回滚：备份留在客户端自己的目录下（backup-inject/<时间戳>/），保留最近 5 份，界面给出路径与一键回滚。
  4. 目标在跑就拒写：Trae（SQLite 被占用 + 内存态覆盖）、WorkBuddy/WB AI/ZCode（内存态落盘）四家一律。不代杀进程，只给指引。
  5. 认不出来就放弃：目标配置结构/版本号与取证时不符 → 不写、不改、不猜，如实报“格式已更新”。
  6. 出网只到 4SAPI 自己的域名；新增的两个接口都是元数据接口，不产生 token 计费；不引入任何遥测。
与 DESIGN.md 现有“非目标”的关系（必须显式表态）

DESIGN.md 1.4 写着「不做余额不足的代申请/代充值 —— 只展示状态，不代替用户执行外部动作」。本功能确实在写别人的文件，属于这一类动作的第一次出现。建议把那条非目标收紧成：

不做平台侧的外部动作（代申请额度、代充值、代改账号）。
本机客户端配置写入 = 用户逐次显式发起、可备份可回滚的本地文件操作，单列第六节契约。

理由：不做代申请是为了“不替你承担后果”；而“把这把 key 配到我的编辑器里”后果就在本地、可回滚、且是你主动要的 —— 两者的风险性质不同，不该用同一条禁令盖住。这条改写要你点头（第 9 节 · 5）。

七、明确不做（非目标）

  • 不做模型试跑/连通性测试。发一条最小请求确实能验证“这把 key 真能调这个模型”，但那会产生真实计费。用 /v1/models 的 200/401 回答“key 有没有效、这批模型能不能调”已经足够，零计费。
  • 不做客户端的模型增删管理。挂件只负责自己写进去的那条（改/删/回滚），不接管客户端里其它模型的排序与清理。
  • 不做 4SAPI 的充值/申请/分组切换代理。（沿用原非目标）
  • 不写 Claude Code / Codex CLI / OpenCode（虽然本机有 ~/.cc-switch 与 ~/.codex/config.toml）—— 本轮四个客户端之外的，列 P3 候选，不扩大战线。
  • 不做“自动选中”。除了真机取证通过的客户端，一律“写入条目 + 你去点一次”。猜另一个程序的内存态键 = 埋一个“看着配好了其实没生效”的坑。

12.3 真机自检顺手挖出的一个坑(已修)

第一次真机打开模型页,界面停在「正在取 4SAPI 的价目表…」不动 —— 但后端其实早就返回了 (get_model_catalog 被单独调用时 9 秒内就回了完整数据)。 真正的原因是前端 renderModels() 里引用了一个不存在的函数名而抛异常, 而调用方的 try/finally 只把"加载中"的标记复位、异常本身被吞在未处理的 Promise 里, 于是界面永远停在加载态。

修法两条:一是把函数名对齐(relTime), 二是给 renderModels 套一层 try/catch —— 渲染出错就把错误写在口径行上, 不许把界面留在"正在取"里。这条经验值得记住:后端成功 + 前端抛异常, 表现出来和"请求还没回来"一模一样,只看截图是分不出来的。

顺着这条线还挖出更贵的一个:非 async 的 Tauri 命令跑在主线程上, 而模型页的命令要起 tasklist 探进程、读客户端配置、读凭据管理器。 真机表现是——点过一次"写入预告"之后,所有新命令都不再返回(连 inject_state 也超时), 而且 WorkBuddy 渠道那一行从面板上消失了(它读会话 Cookie 要回主线程,主线程被占住就超时, 渠道退化成"没有凭据")。修法:五条命令全部改成 async fn + 阻塞段放进 tokio::task::spawn_blocking,并给 tasklist 加 5 秒超时。 这跟项目早就写在取数路径上的那条教训是同一条。

#要验什么为什么没验
1"点一次写入"的完整链路(Trae 是当前唯一不占用的目标) 写入会改另一个程序的配置文件,规矩是"用户逐次显式确认",所以这一步留给你点。 预告本身已真机验过(Trae 那条给出了两个安装的完整预告且按钮可用), 写入路径由单测覆盖同一段代码(备份 / 读回校验 / 回滚 / 幂等)。三个正在运行的客户端 本来就会被拒写 —— 那是设计行为,不是缺陷。
2写入后客户端真能跑起该模型(发一条最小请求) 会产生真实 token 计费 —— 挂件不去花这个钱,留给你用的时候顺便验。

1. 先说人话

这两个平台的积分是「每天点一下就发」的，不发就会过期：Trae 每天点左下角头像签到，WorkBuddy 有个「Buddy 加油站」每天领一次。你漏签一天就少拿一笔，漏一个月按社区实测口径是 3000～6000 积分。

挂件已经在每 60 秒读一次这两个平台的积分余额了，用的就是它们客户端自己在调的账务接口。所以「顺便每天替你把该领的领掉」在技术上是一路车：凭据我们已经有了（Trae），或者已经能拿到（WorkBuddy），只是从"只读"变成"每天多发一次写请求"。

代价不是开发量，是性质变化。 挂件现在是纯只读的账本，看完就走，出事最多是"数字不准"；加了签到以后，它会代替用户操作账号，用的是平台没有公开文档的内部接口。真出问题不是"读错了"，而是"这个功能整个失效"或者"平台哪天开始查这种请求"。所以整个方案的核心不是怎么签，而是三件事：签不成功时界面绝不骗人、能一键停、绝不做多账号批量。

4. 凭据现状：一个够用，一个缺半条腿

渠道现在手里有什么签到还缺什么补法
Trae能解出 Cloud-IDE-JWT 令牌（appauth.rs 已实现 tc 容器解密） 缺纯数字设备号和一组 IDE 请求头指纹。设备号就在同一个 storage.json 里（key 名 iCubeAuthInfo://icube-dc:数字），我们现在没读它 扩 appauth::trae_token_from_storage 顺带把 key 名里那串数字带出来，不新增任何文件读取。改动小，只读性质不变
WorkBuddy挂件内网页登录抓到的 session+session_2 Cookie（够打用量接口） 签到接口大概率只认 Bearer accessToken，Cookie 未必认 → 这条是最大未知数 三条路，见下

A 官方 OAuth

5. 四条路线，先说为什么不是别的

路线用户能感知到什么风险 / 代价不做的后果结论
① 挂件内置接口直连完全无感。托盘上"今日未领"自己变"已领 +150"用的是非公开接口，官方一改就失效；需要设备号指纹这类逆向细节；本质是替用户写账号没有自动，只有提醒采纳
② CDP 模拟点击（社区方案 BlueChonk/trae-daily-checkin）每天要把 Trae 带调试端口重启一次，正在写的代码会被打断；抢焦点Electron 单实例限制：Trae 已开着就无效，只能强杀重启；CSS 类名带哈希随版本变；给 IDE 开 9222 端口本机任何进程可连；UI 改版即瞎—— 否决（为了签到打扰用户正在干的活，本末倒置）
③ 云端定时（GitHub Actions / Cloudflare Worker，社区有 Maquer、ethgan）关机也能签要把长期凭据（整份 auth JSON / 设备号）上传第三方；机房 IP 恰恰是最容易被 9074 的那类（L0NE-6 记录 9074 按出口 IP 排队）；与"凭据不出本机"的现有红线冲突机器不开时当天漏签（可用补跑缓解）本期不做（列裁决 5）
④ 只提醒不代签面板显示"今日未领"，点一下跳到官方页面几乎无风险，也几乎无价值——用户还是得自己点—— 保留为降级档（接口失效时自动退回这里，见第 11 节）

6. 推荐方案：分四期，每期都能独立发版

M0 取证（不写功能，只跑一次只读探测）

用户感知：完全没有。

做什么：按第 15 节那张表，用临时 #[tokio::test] 只读打一遍两平台的 status 接口（不打 claim），把响应结构、可用域名/路径前缀、UA 要求、设备号是否被认，全部落到一份文本里。

不做的后果：后面每一层都建在猜的接口形态上，返工概率极高（WorkBuddy Cookie 那条尤其）。

验收：两渠道各拿到一份真实 status 响应；结论回写进本文档第 3 节，把 待取证 全部消掉。

M1 手动签到（一个按钮，不自动）

用户感知：渠道卡上多一行"今日未领 · 150 分 · [领积分]"，点一下变"已领"。这是唯一必须做对的一期：先证明接口在真机上通、且钱真的到账。

风险：手动能看见结果，失败当场就知道，风险最低。

不做的后果：直接上自动 = 在没有验证过的链路上无人值守地写账号。

验收：点完之后，下一次余额刷新里必须出现那一笔新积分包（到账核对，见第 9 节）。

M2 自动 + 重试 + 日志

用户感知：每天开机后某一刻，卡片自己从"未领"变"已领"。设置里能看到"今天几点试过、试了几次、结果如何"。

风险：无人值守。所以必须先有幂等（先 status 后 claim）、独立限流窗口（status 和 claim 的 9074 分开记）、可一键关。

不做的后果：功能仍要人点，"忘记签到"这个痛点只解决一半。

M3 提醒与统计

用户感知：托盘/胶囊能显示"今天还差 1 笔"；连续失败才弹通知；签到中心里有近 30 天日历和"这个月自动领了多少分"。

不做的后果：静默失效没人发现——这是这类功能最常见死法。

8. 调度规则（这套东西决定了会不会被平台当成机器）

规则定成什么样依据
跨天口径「签到日」= Asia/Shanghai 自然日，不是本机时区、不是 UTC。判"今天签没签"用日期串比较并把结果落盘，重启不重跑所有社区实现一致（Trae2api-cn main.py:441、NextAgentX cst.rs）；CreditDaddy 更细：Qoder 是每天 10:00 跨日，其他 00:00 —— 各平台要能配
触发时段不要贴着 00:00。 社区实测 00:00–00:10 是全天最高峰（所有人整点一起签），00:15–00:45 最好签。定 00:23 ± 随机 0–20 分钟；再挂一个"醒来兜底"：开机后若当天未成功，随机延迟 3～25 分钟后补跑L0NE-6 trae_checkin.py:35-36、3338320742 多时段兜底 4 个时间点
先查后领（幂等）status → 可领才 claim → claim 后再回查一次确认。claim 失败也要回查一次（服务端可能已经被客户端自己点掉了）SIMON wb_daily_credit.py、signdock、CreditDaddy:238-262 全都这么做
两个限流窗口分开记status 和 claim 的限流是相互独立的：9074 只给 claim 记冷却，不能因为 claim 被限流就不查状态（那就再也看不到"其实已领"）Trae2api-cn main.py:435

并发闸门同一渠道同一时刻只允许一次签到（进程内锁 + 已签到日期标记）。不与余额轮询共用闸门，但签到请求要能在轮询正忙时排队，不能并发发双份沿用 fetch_shared 的思路（报告 O-4）；社区用 O_CREAT|O_EXCL 锁文件 / AccountRunGuard
网络出口签到请求强制直连、不跟随系统代理。我们现在的余额客户端是默认跟随系统代理的（Codex 那条就靠它），但代理/机房 IP 正是 9074 的高发出口。要给签到单独一个 no_proxy 客户端L0NE-6:23,904。需要你裁决 4：本机走 Clash 时，签到要不要绕代理直连

机器没开怎么办本期：靠"开机补跑"（醒来后随机延迟执行当天那一笔）。可选：注册 Windows 计划任务（要以当前登录用户身份、不加 /RL HIGHEST、勾选"错过后尽快运行"）。挂件自己已经在开机自启里了，所以计划任务是重复建设，只在"经常不开机"时才有意义smart-open user-manual.md:464-468、SIMON setup_task.ps1

9. 结果可信度：不许把"点了按钮"说成"领到了"

  1. 到账核对优先于响应字段。 WorkBuddy 的签到响应可能根本没有数额字段（signdock:676-690），Trae 的数额字段位置也分歧（顶层 vs data.points）。所以"领到了多少"以下一次余额刷新里真的多出来的那一笔积分包为准：签到成功后立即触发一次该渠道取数，把新增包记进日志。
  2. 界面显示两态，不显示一态。 "已领（待确认到账）" → "已领 +150（已到账）"。前者不吹成后者。
  3. 新增一张 checkin_log 表（现在库里只有 snapshots 和 settings）：渠道、北京日期、结果码、领取数额、尝试次数、错误原文（脱敏）、到账确认时刻。它同时是 M3 的日历/统计和排障时"到底哪天断了"的唯一凭据。
  4. 连签天数只显示接口给的 streak_days，接口没给就不显示，不要自己数日志——我们数出来的和平台数的口径不一样，对不上就是自找的解释成本。

10. 安全与合规红线（照现有规矩，加三条）

  • 凭据不出本机、不落盘、不进日志。 令牌/Cookie/设备号在内存里流转；日志与错误原文一律截断脱敏（社区标准做法是 8391…2210 这种形态）。refreshToken 若要持久化（A 路线必须），存进现有 Windows 凭据管理器，和 API Key 同一套位置，不进 SQLite。
  • 域名白名单硬编码：只允许 api.trae.cn、www.workbuddy.cn、www.codebuddy.cn、copilot.tencent.com。签到是"带凭据的写请求"，白名单是唯一能防住"配置被改就把令牌发给陌生域名"的东西（社区同类项目把这条当卖点写：仅允许该 HTTPS 域名，防止凭证外泄）。
  • 不写回客户端任何文件、不刷新客户端令牌。 现有 appauth.rs 顶部那段的理由继续成立：刷新会轮换 refreshToken，把用户踢下线。
  • 只做单账号、本机。 多账号批量是平台明确会风控的一类（"一台设备一天只能签一个账号"在 Trae 侧还是硬机制，做不了）。界面上也不给"多号"留扩展位，避免以后被顺手做成批量。
  • 新增：签到是独立开关，且默认可关。 关了就一个请求都不发（照 hidden_channels 的口径：不显示也不请求）。出问题时的"一句话止损"必须是用户点一下就能做到的。
  • 新增：免责说明写进界面，不是写进 README。 非公开接口、随时可能失效、与本工具无官方关联——社区每个同类项目都在免责声明里写这几句。放在设置页签到区下方，一行小字。
  • 新增：不向第三方页面注入任何脚本。 现有登录窗原则（只观察导航，不注入、不拦导航）继续不变。

11. 失效预案：接口哪天变了怎么办

变化形态怎么发现自动降级成什么用户看到什么
接口路径/字段被改（最常见）status 连续 N 天返回我们解析不了的结构自动关掉该渠道的签到，余额显示不受影响"签到接口有变动，已暂停自动签到"（一次性）
加了签名/设备证明status 从 200 变 20405 一类新错误码同上，不猜签名、不装代理同上 + 详情里写明"官方加强了校验"
设备号不被认（9074 一直不解）status 通、claim 恒定 9074判成"这台设备的签到资格问题"，停止当天重试，退回只提醒"本机设备号未被签到活动接受，需手动在客户端点一次"
活动换季/下线（WorkBuddy 按季）active=false 或 404整行变"本期已结束"，不再请求不通知（本来就没得领）
凭据过期401/1001/1002不重试，直接引导打开一次 Trae / 回挂件重新登录 WorkBuddy

判因原则：永远不看 message 文案。 9074 的官方文案是"当前参与用户太多"，但真实成因可能是设备校验没过；10001 在国区是"今天已签"、在国际版是"活动未开启"。一律按 code + HTTP 状态 + 域名 三元组分支。

高危 #1命令间锁序相反:check_update / skip_update_version 与 set_pin 构成 AB-BA 死锁

app/src-tauri/src/lib.rs:157-164(set_pin) · lib.rs:293-300(check_update) · lib.rs:387-392(skip_update_version)

两个命令以相反顺序拿同一对互斥锁(store / config):

// set_pin:先 config,后 store
let mut cfg = state.config.lock()...;   // 持有 config
let store = state.store.lock()...;      // 再等 store   → A→B

// check_update:先 store,后 config(且持锁跨越 await 之前的 save)
let store = state.store.lock();
if let Ok(s) = store {
    let mut cfg = state.config.lock().unwrap();  // 持有 store 再等 config → B→A
    ...
}

异常表现(修复前)

启动 30 秒后的自动更新检查(或手动「跳过此版本」)恰好与用户点「置顶」/设置页置顶开关并发时:两个命令各持一把锁互相等待,永久死锁。

连锁后果:store 被死锁方永久占用 → 后台 poll_loop 下一轮在 store.lock().unwrap() 上卡死,所有依赖取数的命令(get_channels / set_pin / get_series)全部挂起 —— 挂件界面不再刷新、按钮无响应,只能杀进程。窗口置顶停在半途,出现「按钮亮了其实没置顶」。

修复后的正确效果

更新检查与置顶操作任意交错都各自完成:置顶即时生效并落库,更新检查正常返回/静默,轮询不中断。

修复建议: 统一全局锁序为「store → config」或「先取齐再释放」。最小改法是让 set_pin 对齐 check_update 的顺序:
- let mut cfg = state.config.lock()...;
- let store = state.store.lock()...;
+ let store = state.store.lock()...;
+ let mut cfg = state.config.lock()...;
更稳妥的做法是给 AppState 加一个 fn with_saved_config(f),内部固定按 store→config 拿锁并保存,消灭手写顺序的机会。另建议把 lock().unwrap() 换成 lock().map_err,避免毒化 panic 把后台任务静默杀死。

高危 #2取数失败时没把「实际用过的凭据」传给视图:登录态明明在,却报「未检测到登录信息」

app/core/src/fetch.rs:622-637(chosen 只在成功时赋值) · fetch.rs:651-659(两条失败路径都传 None) · fetch.rs:400-415(auth_label 的 None 分支) → 前端 app.js:469-476、app.js:1100-1103

fetch_all 里 chosen 只在取数成功那一刻赋值;失败降级(用缓存快照)和失败无缓存两条路径都把 chosen=None 传给 build_view,于是 auth_label(def, None) 走「未检测到」分支 —— 哪怕凭据找到了、token 只是过期。

异常表现(修复前)

Trae token 过期是最常见状态(设计上不刷新)。此时:

① 行内错误提示说「登录状态已失效 · 打开一次 Trae 即可」,详情区却拼出病句:
「凭据来自本机已登录的 未检测到 Trae 登录信息 · 只读复用…」 —— 两处互相打架;

② 管理页密钥行显示「凭据来自本机已登录的 未检测到 WorkBuddy 登录信息」,用户被引导去「登录」,而真正该做的只是「打开一次客户端续期」;

③ stale 快照路径同样中招:上次明明读到过 storage.json,失败后来源说明直接丢。

修复后的正确效果

只要凭据被读到过,失败时来源照常显示「Trae · TRAE SOLO CN」/「WorkBuddy · workbuddy-desktop.info」,与错误文案「打开一次 X 即可」一致;真正没找到凭据时才报「未检测到」。

修复建议: 在凭据循环里同时记录「最后一次实际尝试用的凭据」,失败路径传它:
+ let mut last_cred = None;
  for cred in creds.iter() {
+     last_cred = Some(cred.clone());
      ...
  }
  // 两条 pending.push 把 chosen 换成 `chosen.or(last_cred)`
验证:临时改坏 storage.json 里的 token(或在无网环境),展开 Trae 行,详情第一句应含凭据文件名而不是「未检测到」。

中危 #6吸附状态下任何 applyForm:className 整体覆写丢掉 docked/dock-left,还把 8px 竖条强拉回形态尺寸

app/src/app.js:873-874(document.body.className = "form-" + form + … 覆写) · app.js:879-888(setSize/min/max 无条件执行) · 触发路径:app.js:701-705(fitPill 在轮询 render 中触发) 、app.js:1603-1612(Esc 键)

styles.css 注释(376-380 行)专门强调过 docked 规则的同级优先级坑,但 applyForm 用「整体赋值 className」绕过了所有防御 —— 赋值那一刻 docked、dock-left 双双丢失,窗口同时被钳回 SIZES[form]。

异常表现(修复前)

胶囊形态吸附在屏幕右缘(8px 竖条)。轮询到数据、数值文本宽度变化 ≥6px 时 fitPill → applyForm("pill", false):竖条瞬间按面板布局撑开(内容挤爆/溢出屏幕),CSS 侧 dock-body 被隐藏、pill-body 显示,而 DOCK.on 仍为 true —— 状态机与 DOM 脱节,鼠标移入展开/移出收回逻辑全部错乱,只能拖离边缘重新解除。吸附期间按 Esc 同理弹回面板。

修复建议: document.body.classList.remove("form-panel","form-compact","form-pill"); classList.add("form-"+form); 并在 DOCK.on 时让 applyForm 只改类不改尺寸(或先 dockExit)。

低危 #8consumption_since 的基线可越界窗口起点 24 小时,「今日消耗」会把昨晚的花销算进今天

app/core/src/store.rs:96-131(SQL ts >= ?2 - 86400;循环 124-128 对「基线→窗口首行」整段差值直接计入)

允许基线早于窗口起点最多一天,但跨起点的相邻差值不拆分、不 clamp:23:50 的快照 100 元 → 00:10 的快照 80 元,这 20 元几乎全花在昨天,却整笔计入「今日消耗」。

异常表现(修复前)

隔夜挂机 / 夜间批量任务后,清晨打开挂件:「今日消耗」虚高(最多带上前一整天),周/月同向偏差小一些。汇总区注释写着「推算」,但用户按今日预算决策时会误判。

修复后的正确效果

窗口首行只计入 from_ts 之后的那一段(按时间线性拆分,或保守地取「窗口首行 vs 基线中较晚的低者」),今日消耗不再背昨晚的账。

修复建议: 对跨起点的那一对快照,把基线余额按时间比例折算到 from_ts 再求差;同时加一条断言「窗口内无快照时结果 == 0 而非越界值」的单测。
